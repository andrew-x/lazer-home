# Domain: CRM

**Status: growing.** Companies, contacts, and opportunities (data, reads, create, edit, and `/companies` + `/contacts` + `/opportunities` UIs) all exist. **Companies and contacts are now full CRUD (create/read/edit; no delete yet)** — each has a **detail page** at `/companies/[id]` and `/contacts/[id]` — the app's **first drill-down detail views** (see the UI section below) — carrying an **Edit** affordance (for `crm.edit` holders) that opens a dialog wired to `updateCompany`/`updateContact` for the core fields. The optional **staff owner** (the accountable staff member) is **edited in place on the detail page** (`InlineOwnerField`, mirroring the opportunity drawer's per-field edits), not in that dialog. **Contacts now carry person-to-person relationships** — one typed `contact_relationships` junction (`reports_to` / `succeeds` / `related`) that replaced the old `contacts.managerId` self-FK, managed entirely from a Relationships group in the contact page's sidebar, plus a `contacts.isActive` Active/Inactive flag that a succession link sets automatically ([ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md), superseding [ADR 0022](../decisions/0022-contact-manager-self-reference.md); see [Contact ↔ contact relationships](#contact--contact-relationships)). Companies and contacts now live on **two separate pages** (`/companies` and `/contacts`) — the old combined "Companies & Contacts" page was split ([design spec](../superpowers/specs/2026-07-09-split-companies-contacts-design.md)). `/opportunities` now toggles between a **drag-and-drop kanban board** (default) and a **paginated, filterable list view** (`?view=list`), with 14 leaf statuses organized into ordered pipeline groups — see [ADR 0021](../decisions/0021-opportunity-pipeline-groups-and-fractional-ordering.md) and [Board + list views](#board--list-views). Opportunities now carry a **required line of business** (the shared enum, [ADR 0025](../decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)), and their table + junctions now live in **their own schema file** `src/lib/db/opportunities-schema.ts` (split out of `crm-schema.ts`, which keeps only companies + contacts). Clicking a card (board) or a name (list) opens a **detail drawer** — a wide (`sm:max-w-[80rem]`, widened for the planner + the two-column Details layout) two-tab read-first view (**Details** + **Project plan**). The **Details** tab is a responsive two-column layout: the Info fields (line of business, source, company, contacts, owners) sit in a left meta column — each **edits one at a time in place** (per-field pencil → Confirm/Cancel) — while the Tasks + Notes lists fill the right column (columns stack on small screens). The **Project plan** tab is a **weekly Gantt-like staffing planner** over the linked project's roles ([ADR 0031](../decisions/0031-opportunity-project-planner-and-role-status.md)). Companies, contacts, and opportunities each carry a running **notes** log (timestamped, authored free-text "what happened" entries — see [Notes](#notes) and [ADR 0030](../decisions/0030-crm-timestamped-entries-notes-next-steps.md)) **and a list of [Tasks](#tasks)** — assignable, completable to-dos that **replaced the old free-text "next steps"** ([ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md)); the scalar `opportunities.nextSteps` column that predated both is gone. **Tasks now also have a *personal* surface outside the CRM** — a Tasks block in the home dashboard's *Your Status* band listing everything assigned to you, with an Archive dialog for the history, which is also why **the task's assignee may always complete it** even without `crm.edit` ([ADR 0065](../decisions/0065-home-personal-task-list-and-assignee-completion.md)). An opportunity also carries an optional **private Slack scoping channel** (`l-scoping-<slug>`), created or linked from the drawer's Details tab — the CRM's first external-service integration; the *project* channel is a separate slot managed on the project's own page ([slack.md](./slack.md), [ADR 0067](../decisions/0067-slack-channel-links-bot-token-denormalized-pairs-and-record-scoped-gate.md)). Projects now exist too ([projects.md](./projects.md)), and the **Opportunity → Project link inverted**: it lives on **`opportunities.projectId`** (many opps → one project), populated when a project is created from or associated to an opportunity, and a **delivery-stage rule** requires a linked project before an opportunity can advance to Allocating or later ([ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](../decisions/0031-opportunity-project-planner-and-role-status.md)). Manages the companies and people we deal with (clients, partners, prospects) and the pipeline deals we're trying to win, all of which feed delivery.

## Purpose

Track who we sell to and work with, and (eventually) what we're trying to win, so won work flows cleanly into Projects and Allocations.

## Key entities

- **Company** (built) — an organisation we deal with. **`isPartner` is a standalone flag** marking whether the company is a partner (default `false`); it is **not** a client-vs-partner dichotomy — a company may be neither a client nor a partner, and nothing requires it to be either. We deliberately modelled this as *Company* rather than the narrower *Client* the early design assumed — see [ADR 0015](../decisions/0015-crm-company-over-client.md). Fields: `name` (required), `websiteUrl` (optional), an optional free-text **`location`** (`"City, CC"`; see [Location](#location)), `isPartner`, and an optional **`ownerId`** — a nullable FK → **`staff`** (`onDelete: set null`), the staff member accountable for the relationship; cleared (not blocked) if that staff row is removed. This is a CRM company/contact ↔ staff link (mirrors `opportunityOwners.staffId`; see [Connects to](#connects-to)). Table `companies`, id prefix `company`. A company's **status is *derived*, not stored** — a set of tags (**Partner** = `isPartner`; **Client** = has a confirmed project; **Prospect** = has an open opportunity) computed from its relationships, so `isPartner` remains the only stored/manual relationship signal ([ADR 0034](../decisions/0034-company-status-derived-tags.md); see [Company status tags](#company-status-tags)). A company also carries a running **notes log** (`company_entries` — the same authored/timestamped entry pattern contacts & opportunities use; see [Notes](#notes)) and a list of **[Tasks](#tasks)**.
- **Contact** (built) — a person, optionally attached to a Company. Fields: `firstName`/`lastName` (required), `email` (required, **unique**), `phone` (optional; shown as a `tel:` link on the detail page), `companyId` (optional FK → `companies`, `onDelete: set null`), `role` (optional free-text job title, e.g. "CTO"), `linkedinUrl` (optional; validated by the shared `optionalUrl` schema, same as company `websiteUrl`; shown as an external "Profile" link on the detail page), an optional free-text **`location`** (`"City, CC"`; see [Location](#location)), and **`isActive`** — a notNull boolean defaulting true, mirroring `staff.isActive`: `false` marks an **inactive** contact, who keeps all their history (opportunities, notes, the succession chain pointing at them) but drops out of the default `/contacts` list and every picker, badged **"Inactive"** wherever they do appear. **"Inactive", not "former"** — the flag covers two different situations and the row doesn't record which; see [Contact status (active / inactive)](#contact-status-active--inactive). **There is no `managerId` column** — every person-to-person link now lives in [`contact_relationships`](#contact--contact-relationships) ([ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md), superseding [ADR 0022](../decisions/0022-contact-manager-self-reference.md)). Also carries an optional **`ownerId`** — a nullable FK → **`staff`** (`onDelete: set null`), the accountable staff member; cleared if that staff row is removed (same set-null convention as `companies.ownerId`) — and an optional **`relationshipStrength`** — a plain **`integer`** on a **1–5** scale (1 New/Unestablished, 2 Weak, 3 Developing, 4 Strong Supporter, 5 Champion/Trusted Partner), **null = not yet rated**; level meanings live in the pure module `src/lib/crm/relationship-strength.ts` (mirrors `@/lib/performance/feedback-rating`, [ADR 0016](../decisions/0016-junction-table-and-shared-enum-conventions.md)), and it's **edited inline as a star rating** on the contact page (see [Relationship strength](#relationship-strength) below). Table `contacts`, id prefix `contact`. A contact also carries a running **notes** log (`contact_entries` — see [Notes](#notes)) and a list of **[Tasks](#tasks)**. Schema in `src/lib/db/crm-schema.ts`; see [../data-model.md](../data-model.md).
- **Contact ↔ contact relationship** (built) — **one typed junction for every person-to-person link**, `contact_relationships`, id prefix `crel`, typed by the `contact_relationship_kind` pgEnum: **`reports_to`** (directional, same company, ≤1 per contact, reverse = direct reports), **`succeeds`** (directional, the same human's OLD record at a previous employer — creating one marks that predecessor `isActive = false`), **`related`** (**symmetric**, required free-text `description`, stored once). It **replaced `contacts.managerId`**. A data-carrying junction (`description` + `updatedAt`, both FKs `cascade`) whose **cardinality lives in four named partial unique indexes** rather than app checks, plus two CHECKs and two plain read-path indexes. Cross-row rules (same-company / different-company / no cycles) live in `contactRelationshipChecks.ts`. See [Contact ↔ contact relationships](#contact--contact-relationships) and [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md).
- **Company ↔ contact relationship** (built) — a **non-employee** link between one company and one contact, with a short free-text **`description`** of how they relate ("CSM", "FDE"). This is the second, deliberately separate way a person attaches to a company: **`contacts.companyId` remains the sole employer FK**, and this table carries everything else — a partner company's CSM working on one of our accounts, an embedded FDE, a former employee, an investor on a client's board. Table `company_contact_relationships`, id prefix `ccrel`. A **data-carrying junction** (it holds `description`), so it follows the FK/index halves of the [junction convention](../data-model.md#junction-tables--the-first-many-to-many-pattern) like `project_roles`, while keeping a **`unique(companyId, contactId)`** pair — **one relationship per pair**, so "edit the description" is unambiguous and a duplicate add is a friendly "edit the existing one instead" (the constraint is *named* so `isUniqueViolation` can key off it). **Both FKs cascade** (a link is meaningless without both endpoints — deliberately unlike `contacts.companyId`'s set-null, which is an optional attribute of a contact rather than a row whose whole identity is the pair), and it carries a full `updatedAt` because the row is editable (unlike the pure junctions, which are `createdAt`-only). The **suggestion list is not a constraint**: `RELATIONSHIP_DESCRIPTION_SUGGESTIONS` in the pure, client-importable `src/lib/crm/company-contact-relationship.ts` (CSM, FDE, Partner manager, Former employee, Investor) feeds the picker's autocomplete, but nothing validates against it, so a novel wording ("Fractional CTO") persists verbatim — an explicit departure from [ADR 0016](../decisions/0016-junction-table-and-shared-enum-conventions.md)'s tuple→pgEnum convention, which is for *closed* sets (same reasoning as free-text `location`). **A relationship can never duplicate the employer link**: `createCompanyContactRelationship` rejects a contact whose `companyId` already equals the target company, app-side — the same posture the contact-relationship checks take ([ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md); this used to point at the deleted `assertValidManager`). See [ADR 0048](../decisions/0048-company-contact-relationships-beyond-employment.md) and [Relationships](#relationships).
- **Opportunity** (built) — a pipeline deal that always belongs to a Company. Fields: `name` (required), required `companyId` (FK → `companies`, **`onDelete: restrict`** — a company with live opportunities can't be deleted, unlike its optional/set-null contacts), `source` + `status` (pgEnums), **required `lineOfBusiness`** (the shared `lineOfBusinessEnum` — which practice the deal belongs to; a project created from it defaults to the same, [ADR 0025](../decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)), and **`position`** (see below). **No scalar `nextSteps` column** — the old single next-step field was migrated into the `opportunity_entries` log and dropped ([ADR 0030](../decisions/0030-crm-timestamped-entries-notes-next-steps.md)); that log later became notes-only, with next steps reborn as the [Tasks](#tasks) entity ([ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md)). Table `opportunities`, id prefix `opp` — **now in its own schema file** `src/lib/db/opportunities-schema.ts` (split out of `crm-schema.ts`, which keeps only `companies` + `contacts`; [ADR 0025](../decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)). Its people are modelled with **four junction tables** (see below): related `contacts`, `owners` (→ `staff`), and referral sources split into `source_contacts` and `source_staff`. An Opportunity produces a Project once it reaches delivery stages; the link column now lives on the **opportunity** side — **`opportunities.projectId`** (nullable FK → `projects`, `onDelete: restrict`, indexed `opportunities_project_idx`), **many opportunities → one project** (a project can be built up from several deals; an opportunity has at most one project). The old `projects.opportunityId` column + its partial unique index were **removed** in the inversion. `restrict` blocks deleting a project any opportunity references. Populated by the handoff/planner flow ([ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](../decisions/0031-opportunity-project-planner-and-role-status.md)). See [ADR 0019](../decisions/0019-project-opportunity-link.md).
  - **`source`** (`opportunity_source`): `inbound`, `farming`, `extension`, `change_request`, `staff_referral`, `contact_referral`.
  - **`status`** (`opportunity_status`): a **flat 14-value leaf enum in strict pipeline order** — `maturing`, `lead`, `qualifying`, `scoping_awaiting_info`, `scoping`, `scoping_reviewing`, `allocating_awaiting_profiles`, `allocating_introing_profiles`, `negotiating`, `closing_awaiting_contracts`, `closing_redlining`, `closing_awaiting_signatures`, `closed_won`, `closed_lost`. The DB knows only leaves; the two-level **grouping** (below) is derived in code. (Restructured from the old flat 7-value enum, remapping legacy `closing` → `closing_awaiting_contracts`; the drizzle history has since been squashed into a single baseline — read `opportunities-schema.ts` for the definitive enum.)
  - **Pipeline groups** — `src/lib/crm/opportunity-pipeline.ts` (a pure, client-importable module, mirroring `line-of-business.ts`) defines `OPPORTUNITY_GROUPS`: ordered groups → their leaf substatuses. In order: **Maturing, Lead, Qualifying** (single-status), **Scoping** (awaiting info / scoping / reviewing), **Allocating** (awaiting profiles / introing profiles), **Negotiating**, **Closing** (awaiting contracts / redlining / awaiting signatures), **Won** (`closed_won`), **Lost** (`closed_lost`). A **module-load assertion** requires the flattened groups to equal `OPPORTUNITY_STATUSES` in the same order, so they can't drift. Also exports `resolveTargetStatus` (which leaf a card takes when dropped on a collapsed group), `computePosition` (fractional-index midpoint), **`opportunityGroupById(id)`** (a group by its id — how the list view's `stage` filter param resolves to its leaf statuses), **`requiresProject(status)`** — true from the **Allocating** group onward (Allocating → Negotiating → Closing → Won), Closed – Lost excepted: the delivery-stage rule that an opportunity can't advance without a linked project ([ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md)) — and the board-capping constants **`CAPPED_BOARD_STATUSES`** (`maturing`, `closed_won`, `closed_lost`) + **`BOARD_COLUMN_CAP`** (20), see [Board + list views](#board--list-views). See [ADR 0021](../decisions/0021-opportunity-pipeline-groups-and-fractional-ordering.md).
  - **`position`** (`doublePrecision NOT NULL DEFAULT 0`) — a **single global fractional index** for manual kanban ordering. Cards in a column sort by `(position, createdAt)`; a drag writes the midpoint between its new neighbours (one-row update), a new opportunity gets `max(position)+1` (lands at the end of its column). Index `opportunities_status_position_idx` on `(status, position)`. No fractional-index rebalancing — an accepted limitation at this scale ([ADR 0021](../decisions/0021-opportunity-pipeline-groups-and-fractional-ordering.md)).
  - Both enum value tuples (`OPPORTUNITY_SOURCES`/`OPPORTUNITY_STATUSES`), their union types (`OpportunitySource`/`OpportunityStatus`), and their `SOURCE_LABELS`/`STATUS_LABELS` are declared **once** in `src/lib/crm/opportunity.ts` (a pure, client-importable module — no `db`/drizzle, no UI, mirroring `line-of-business.ts`/`currency.ts`), and everything imports them **directly** from there: the `pgEnum` in `opportunities-schema.ts`, the zod schema, and the display components. This fixed the old layering where the tuples lived in `createOpportunity.schema.ts` (imported *upward* by the pgEnum) and the labels in `opportunity-display.ts`. The **back-compat re-export shims are now gone** — `createOpportunity.schema.ts` no longer re-exports the enums, and `opportunity-display.ts` keeps only `STATUS_SELECT_LABELS` (the group-qualified dropdown labels it derives). Per-leaf display labels are `STATUS_LABELS`; group labels live in `opportunity-pipeline.ts`.

## What's built

- **Schema** — `src/lib/db/crm-schema.ts` (`companies`, `contacts`, **`contact_relationships`**, **`company_contact_relationships`**, **`contact_entries`**, **`company_entries`**) + `src/lib/db/opportunities-schema.ts` (`opportunities` + four junction tables + **`opportunity_entries`** + the `source`/`status` pgEnums + `lineOfBusiness`) + `src/lib/db/tasks-schema.ts` (**`tasks`** — see [Tasks](#tasks)), all barrelled by `src/lib/db/schema.ts`. The three `*_entries` tables are now **notes-only** — see [Notes](#notes) and [ADR 0030](../decisions/0030-crm-timestamped-entries-notes-next-steps.md). `company_entries` mirrors `contact_entries` exactly (`id`, `companyId` FK → `companies` cascade, `body`, `authorStaffId` FK → `staff` set-null, timestamps, index `company_entries_company_created_idx` on `(companyId, createdAt)`; row type `CompanyEntry`). **The `crm_entry_kind` pgEnum and the `kind` column were dropped** from all three entry tables when tasks replaced next steps (migration `drizzle/0008_eminent_mandroid.sql`, which deletes `next_step` rows before dropping the column and creates `tasks`); the earlier `company_entries` add was migration `drizzle/0004_blue_terrax.sql`. The opportunities file imports `companies`/`contacts` from `./crm-schema` and `staff`/`lineOfBusinessEnum` from `./staff-schema` ([ADR 0025](../decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)). These earlier CRM migrations were **squashed into the single baseline `drizzle/0000_lethal_rictor.sql`** (read the schema files for the definitive shape): the companies/contacts tables, `contacts.phone`, the opportunities table + four junctions + `source`/`status` enums, the 14-value leaf `opportunity_status` (with `position` backfilled via `row_number()` per status + `opportunities_status_position_idx`), `contacts.linkedinUrl` + the self-referential `contacts.managerId` (**since dropped**, see below), and `opportunities.line_of_business` (NOT NULL, no default). The schema split itself is a pure code reorg (no migration). **`company_contact_relationships`** was added later in migration `drizzle/0012_icy_excalibur.sql` (table + the named unique pair + the reverse-lookup contact index). **`contact_relationships`** came last, in a pair: `drizzle/0014_nasty_krista_starr.sql` (the `contact_relationship_kind` enum + the table with its two CHECKs, **four named partial unique indexes** and two plain indexes, plus `contacts.is_active`) and the **hand-added** `drizzle/0015_rainy_wrecking_crew.sql`, which backfills `manager_id` into `reports_to` rows via `INSERT … SELECT` and *then* drops the column — that order is load-bearing, and cross-company/cyclic legacy links are carried across as-is ([ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md)).
- **Junction tables** — the repo's **first** many-to-many join tables: `opportunity_contacts`, `opportunity_owners` (→ `staff`), `opportunity_source_contacts`, `opportunity_source_staff` (→ `staff`). All follow one convention (documented in [../data-model.md](../data-model.md#junction-tables--the-first-many-to-many-pattern)): a **surrogate `text` PK** via `generateId` (no composite PKs — repo convention), a **`unique(...)` on the FK pair** for set-semantics (no duplicate links), an **`index(...)` on the non-opportunity FK** for reverse lookups, and **both FKs `onDelete: "cascade"`** (a link is meaningless without both endpoints).
- **Server layer** — `src/actions/crm/`:
  - `getCompaniesPage.ts` / `getContactsPage.ts` — server-only reads (per ADR 0010), **server-side offset/limit pagination** with a `count` and a page clamped into range (out-of-bounds query params can't return an empty page). Both share `src/lib/core/pagination.ts`, which exports `CRM_PAGE_SIZE` (20), `clampPage` (the range-clamp arithmetic — there's always ≥1 page, even when empty), and the `Page<T>` envelope (`{ rows, total, page, pageSize, pageCount }`) they return. `CompanyRow` is `{ id, name, location, isPartner, isClient, isProspect }` (`location` a read-only column projection for the table's Location column) — the three **derived status flags** ([Company status tags](#company-status-tags), [ADR 0034](../decisions/0034-company-status-derived-tags.md)): `isPartner` is the stored column, while `isClient` (a confirmed project, correlated `opportunities.companyId → projectId → projects.status = 'confirmed'`) and `isProspect` (an open opportunity, `status NOT IN CLOSED_OPPORTUNITY_STATUSES`) are computed inline as **correlated `EXISTS` subqueries** so the page stays one query. `getCompaniesPage` also takes a **`filters` arg** (`{ query?, status? }`) — a case-insensitive **name search** (`ilike`) and a **single derived-status filter** (partner/client/prospect); the `where` is applied to **both** the count and the row query so the total/page-count reflect the filtered set. The two `EXISTS` expressions (`hasConfirmedProject`/`hasOpenOpportunity`) are pulled out as reusable condition consts, reused **both** as the selected boolean (via `.mapWith(Boolean)`) and as the status filter's `where` (partner filters on the stored `isPartner` flag). Contacts left-join companies to resolve `companyName` (company is optional). `getContactsPage` takes its own **`ContactListFilters`** (`{ query?, city?, nearby?, includeInactive? }` — named to match `searchContacts`' arg of the same name; the two were inconsistent before), assembled by **`contactsWhere`** as a `SQL[]` of conditions `and(...)`-ed together (undefined when none apply) — a **name search** (`query`, escaped via the shared `escapeLike`, matched `ilike` against `firstName`, `lastName`, **and** the `firstName || ' ' || lastName` concatenation, so "jane sm" finds Jane Smith; both columns are `notNull` so the concatenation is never null) plus the [location](#location) filter and **`includeInactive`**. **`includeInactive` is the odd one out: it *widens* rather than narrows** — off by default it pushes `eq(contacts.isActive, true)`, so the list means "the people we deal with" and a contact superseded by a newer record can't appear twice. Like every other condition it feeds **both** the `count()` and the rows, so `total`/`pageCount` follow the toggle; but because it can never *empty* the result, the page deliberately leaves it out of the table's `filtered` prop (only `query`/`city` set that) while the filter bar's "Clear filters" affordance does count it. `ContactRow` is **what the list table renders** — `id`, `firstName`/`lastName`, `role`, `companyId`/`companyName`, the read-only `location` label, **`isActive`** (drives the "Inactive" badge in the name cell), **`successor`** (`ContactRowSuccessor | null` = `{ id, name, companyName }` — the newer record for the same person, so an inactive row can render "Moved to X at Y" instead of being a dead end; only ever set for an inactive contact in practice, and **an inactive contact needn't have one** — a hand-deactivated record is badged with no forwarding line), and **`openTasks`** (the contact's incomplete tasks, `OpenTaskSummary[]` = `{ id, description, ownerId, ownerName }`, oldest first). The open tasks are fetched for the whole page in **one grouped query** via the shared **`openTasksByParent("contact", ids)`** (`src/actions/crm/getTasks.ts`) and stitched onto each row (empty when none); the successors come from the module-private **`successorsByPredecessor(ids)`**, which runs in the **same `Promise.all`** and deliberately **mirrors `openTasksByParent`' shape rather than joining on the row query** — a second relationship join would have to be duplicated onto the paginated `count()`/rows pair, and a map lookup is what the row assembly wants anyway. It selects through an `alias(contacts, "successor_contacts")` inner-joined on `contactRelationships.contactId` plus a left join to `companies` for the successor's employer, filtered `kind = 'succeeds'` + `inArray(relatedContactId, ids)`, and is **keyed by the *predecessor's* id** (`relatedContactId`) because that's the row being rendered. A **flat `Map`** (not a `Map` of arrays) is the right shape: `contact_relationships_one_successor_uq` guarantees at most one successor per predecessor — this replaced the old per-row latest-next-step `DISTINCT ON` subquery (`latestNextStep.ts` is deleted). The **owner fields on the summary exist for the contacts list's in-cell task editor** (`ContactTasksCell`): `updateTask` always takes an `ownerId`, so carrying `ownerStaffId` + the left-joined `staff.name` lets the cell round-trip the owner without a second fetch. Email/phone/linkedin dropped from the row (they live on the detail read); see [Tasks](#tasks), [ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md).
  - `getCompanyDetail.ts` / `getContactDetail.ts` — server-only reads backing the two detail pages (per ADR 0010; **not** `'use server'`, so pages `await` them directly during SSR). Each fetches the entity's core fields, then its related collections in a `Promise.all`, projected to just the columns the view renders; both return `null` on an unknown id (page → `notFound()`). No pagination (an entity's own footprint is small). Neither adds a permission beyond the `(app)` gate — consistent with all CRM reads being open.
    - `getCompanyDetail` returns core fields + **six** collections (the sixth, **`relatedContacts`** (`CompanyRelatedContact[]`), is the non-employee link list — join `companyContactRelationships → contacts` plus a **left join to `companies` for the related person's own employer** (optional, and by definition a *different* company than the one viewed), ordered by last/first name, carrying `relationshipId` (the handle for edit/remove) + `description`. Deliberately **not** fed into `openTasksByParent` — it's a directory of links, not a task surface. Also deliberately **not** filtered against the employee list: if someone's employer later changes *to* this company the now-redundant link stays visible, and therefore deletable, rather than becoming an invisible ghost row.) The other five: Three are tied directly to `companyId`: `opportunities`, `projects` (projects this company *owns* — `projects.companyId`; **that parent is editable from the project side**, so `updateProjectField`'s `company` variant calls `revalidateCompany` for **both** the old and new company to keep this list honest — see [projects.md](./projects.md)), and `contacts` (the company's people directory — each `CompanyContact` also carries its **`openTasks`** via the same grouped `openTasksByParent("contact", ids)` as `getContactsPage`, plus **`isActive`**: **inactive people are deliberately NOT filtered out here** — a company's ex-people are exactly what you want on its page, and a `succeeds` predecessor's employer *is* the old company, so hiding them would hide the history the succession link exists to record. The read also returns the company's **own** `tasks` (a full `TaskView[]`, via `getTasksForParent("company", id)`) for the company detail page's Tasks card. This replaced the previously-inline per-collection grouping.

Each is a **discriminated union on `field`** (mirroring `updateOpportunityField`): `updateCompanyField` handles `owner` | `location`; `updateContactField` handles `owner` | `location` | `relationshipStrength`. Each variant writes **just that one column** through a shared `setCompany`/`setContact` helper, **`.returning()`-guarded** via the shared `assertRowExists` (empty → user-safe "That … no longer exists"), so an inline edit can't clobber a concurrently-edited field and the contact's **email normalisation isn't re-run** on an unrelated change. `owner`/`location` accept `null` to unassign/clear; `relationshipStrength` is a **required 1–5 int** (clicking a star always sets a concrete level — no clear affordance). **There is deliberately no `isActive` variant** — a comment in `updateContactField.schema.ts` says so, because the union is the obvious place to look for it: the Active/Inactive status is edited in the **contact dialog** via `updateContactSchema` (see `updateContact` below and [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md)), so this action is **not** a writer of that flag at all. Both revalidate via the shared `revalidateCompany`/`revalidateContact` helpers (`revalidate.ts`, mirroring staff's `revalidateStaffProfile`: list + detail path). **These two actions replaced the five deleted single-column actions** (`updateCompanyOwner`/`updateContactOwner`/`updateCompanyLocation`/`updateContactLocation`/`updateContactRelationshipStrength`), converging the CRM inline edits onto one discriminated-union action per entity. The schemas are **pure, client-importable `z.discriminatedUnion`s** (so the inline field components share them) and each exports its inferred `Input` type.
  - `createOpportunity.ts` — gated `crm.edit`. **Rejects creating in a delivery stage** (any `requiresProject(status)` — Allocating onward): a brand-new opportunity can't have a linked project yet, so that state is unreachable; the error points the user to create it earlier and add a project as it advances. Otherwise one **transaction**: reads `max(position)` and inserts the opportunity with `position = max+1` (so it lands at the end of its board column), then writes the four people-junctions via the shared `writeOpportunityLinks` (see below). Related entities (company, contacts) are created via their own actions first; this only consumes their ids. `revalidatePath("/opportunities")`.
  - `opportunityLinks.ts` — shared junction helpers (not actions), each **deduping its id list** first so a repeat can't trip the junction `unique` index: **`writeOpportunityLinks(tx, opportunityId, ids)`** inserts all four people-junction rows at once (used by `createOpportunity`); and the per-junction **`replaceOpportunity{Contacts,Owners,SourceStaff,SourceContacts}(tx, id, ids)`** (delete + re-insert one junction), used by the field-scoped `updateOpportunityField` so each people-edit rewrites only its own junction.
  - `createOpportunity.schema.ts` — the shared zod schema. Its field shape lives in the exported **`opportunityBaseFields`** block, which **both** create and update build a `z.object` from (update just adds `id`), so the two can't drift; **required `companyId` sits in that shared base** (it moved in when company became drawer-editable — create and update now enforce the same "Company is required." rule). Imports the enum tuples **directly** from `@/lib/crm/opportunity` (the old back-compat re-export shim is gone). A `superRefine` (`refineReferral`, also shared) enforces the conditional referral rules: `source = staff_referral` ⇒ ≥1 `sourceStaffIds`; `source = contact_referral` ⇒ ≥1 `sourceContactIds`.
  - `createContact.ts` / `updateContact.ts` (+ `.schema.ts`) — create and edit a contact, both gated `crm.edit`. `createContact` is a **single `db.insert(contacts)`** (no transaction) and **returns `{ id }`** (not `{ ok: true }`) so an inline-created contact can be immediately selected in the opportunity form; `updateContact` runs a **transaction** and `.returning()`s by `id` (an empty `returning` → user-safe "That contact no longer exists"). **Neither writes a relationship** — `managerId` is gone from `contactFields`, and `contactChecks.ts` now holds only `mapContactEmailConflict` (`assertValidManager` was deleted with the column; its same-company rule lives on in `contactRelationshipChecks.ts`). **Two things `updateContact` does that are easy to miss:** it **deletes the contact's `reports_to` row when `companyId` changes** — inside the same transaction, reading the old employer first because `RETURNING` on an UPDATE yields the *new* row — since a cross-company manager is invalid by the rule the write path enforces (the old picker got the same effect by silently resetting itself; the edit dialog now warns before you save), and it revalidates the ex-manager's page too, where that link rendered under Direct reports. And **`isActive` IS part of this save** — `updateContactSchema` carries it as a **required `z.boolean()`** and the `.set()` column list writes it, because the Active/Inactive **Status** switch lives in the edit dialog (see [Contact ↔ contact relationships](#contact--contact-relationships)); the form must round-trip it exactly like `ownerId`. *(An earlier design had the opposite arrangement — the column list excluded `isActive` and an inline sidebar switch owned it through `updateContactField`. That's gone.)* **The consequence, called out rather than special-cased:** the other writer of the flag is `createContactRelationship`, which flips the *predecessor* to inactive when a successor is linked, so a **stale dialog** opened before that and submitted after would set it back to active. That's the ordinary last-write-wins of a full-record dialog, not a bug to guard. `mapContactEmailConflict(error)` — shared with `createContact` so the two can't drift — maps the Postgres unique-violation on `contacts_email_unique` to a user-safe "A contact with that email already exists." (returns `never`, used as the whole `catch` body), via the shared **`isUniqueViolation(error, constraint)`** helper in `src/lib/db/unique-violation.ts` (a reusable SQLSTATE-`23505`-on-named-constraint check, extracted from the old inline check in `createContact` so the CRM write actions share it). Both actions accept and write the optional **`ownerId`** (the owning staff member): `createContact` sets it on create, and `updateContact` — as a **full-record** update — round-trips it. **`relationshipStrength` behaves exactly like `ownerId` here** — the edit dialog renders no field for either, but keeps both in its `defaultValues` (RHF v7 includes unregistered defaults in the submit payload) so a full-record save re-sends the current owner **and** rating **unchanged**; a dialog save must not wipe them. Reassigning the owner and re-rating now go through the field-scoped **`updateContactField`** action (the `owner` / `relationshipStrength` variants, below) via their inline fields. Creating a company inline from the contact form is **persist-first** — the new company is saved via `createCompany` first (through `CompanyComboboxField`'s inline dialog), then its id is passed here as `companyId`. This mirrors opportunities and replaced an earlier design where `createContact` created the company itself in a nested `db.transaction` (that `newCompany` path and the transaction are gone). `createContact` `revalidatePath("/contacts")`; `updateContact` revalidates `/contacts` and `/contacts/${id}`. Input schemas live in sibling `.schema.ts` files.

  - **`task-owner-avatar.tsx`** (`TaskOwnerAvatar`) — the shared owner glyph both cells use: a **size-5 initials disc** (`initialsFor`) with the name in a tooltip, and an **empty dashed disc when unassigned** (keeps the column aligned and reads as "nobody owns this"). **Gotcha:** sized off the *default* avatar + a `size-5` class rather than `size="sm"`, because the variant's `data-[size=sm]:size-6` out-specifies a bare `size-5`.
  - **`contact-tasks-cell.tsx`** (`ContactTasksCell`) — the **Next steps cell, worked in place**, on **both** contact tables (the contacts list *and* the company detail page's Contacts tab): tick a task off (`setTaskDone`), edit its description + owner (`updateTask`), delete it (`deleteTask`), or add one (`createTask`) without opening the contact. A client island inside the still-server `ContactsTable` / `CompanyDetailView`; `canEdit` + the viewer's `getCurrentStaffIdentity()` are threaded from `/contacts/page.tsx` and `/companies/[id]/page.tsx` (both already had them for other affordances), and without `crm.edit` it just renders `OpenTasksCell` (the actions gate server-side regardless — `canEdit` only picks what to render). Each task is one compact line (`Checkbox` · description · `TaskOwnerAvatar`) whose **description text is the trigger for an edit popover** — the local `TaskEditorPopover` holds `TaskFields stacked` + Cancel/Save, with **Delete inside the popover**; "Add" opens the same popover empty. Ticked tasks **stay in the cell**, struck through and non-editable, as a one-click undo. See [Tasks](#tasks) for the override-map, per-row-hook and popover nuances.

## Board + list views

`/opportunities` renders **two views of the same pipeline**, chosen by a **`?view=list` URL param** (default = board) — see [ADR 0039](../decisions/0039-opportunities-list-view-and-board-column-capping.md). The switch (`opportunity-view-toggle.tsx`) is **link-based, not local state** — deliberately, so the choice lives in the URL and the board's "Show more" links can deep-link straight into a filtered list. Both views mount for everyone; edit affordances (drag, drawer open) gate on `crm.edit` as before.

- **Board** (`getOpportunitiesBoard`) — the kanban, unchanged in spirit but now **column-capped**: the three high-volume columns (`CAPPED_BOARD_STATUSES` = Maturing, Won, Lost) show only their 20 (`BOARD_COLUMN_CAP`) most-recently-updated cards, since those columns grow unbounded (Maturing accrues early-stage deals; the closed columns accrue every decided deal forever). Every other column shows its full contents. When a capped column holds more than 20, `opportunity-board-column.tsx` renders a **"Show N more"** link to `?view=list&stage=<group>` — the exhaustive browse lives in the list. The board carries **two client-side filters** over the already-loaded cards — a **name search** and a **line-of-business select** (`SelectFilter`, driven by the card's `lineOfBusiness`) — so both deliberately **cannot surface cards beyond a column's cap** (that's the list view's job), and the "Show N more" count stays the *unfiltered* hidden remainder. When a **LOB filter is active**, the deep-link **carries it through** (`?view=list&stage=<group>&lob=<LOB>`) so the exhaustive list applies both filters. `cappedTotals` (from the read) drives the count; the board maps each capped single-status column's `total − loaded` to the link.
- **List** (`getOpportunitiesPage`) — a **paginated, server-filtered table** (`opportunities-table.tsx`), the fallback for browsing the capped/closed columns and searching the whole pipeline. Columns: Name · Company · Stage · Line of business · Owners · Last updated (ordered `updatedAt desc`). The **name cell opens the same `OpportunityDetailSheet`** the board uses (edit-gated, so it only mounts for `crm.edit` users; others see plain text) — **there is no standalone opportunity detail route**, the drawer is the detail affordance in both views. Pagination reuses `PaginationControls` with `paramKey="oppPage"`.
- **List filters** (`opportunities-list-filters.tsx`) — **stage** (by the 9 kanban `OPPORTUNITY_GROUPS`, expanded server-side to leaf statuses), **line of business**, and a **debounced name/company search**, all **URL-synced** (params `stage`, `lob`, `q`, `oppPage`) via `router.replace` so back-navigation restores filters and the server page re-fetches. Reads its current values from the `params` the page already parsed (no `useSearchParams`, so no Suspense boundary). Any filter change resets `oppPage` to 1. The page validates raw params against the known groups / LOB enum before querying (unknown → no filter). Selects reuse the shared `SelectFilter`/`ALL` primitives in `src/components/form/filters.tsx`, and the search box + its debounce-to-URL effect come from the shared `useUrlSearchFilter`/`SearchFilter` in `src/components/form/search-filter.tsx` (see [../ui.md](../ui.md#list-filter-bars)).

## Company status tags

A company's **status is derived, not stored** — a set of tags computed from its relationships, so nothing is persisted beyond the manual `isPartner` flag. Full rationale in [ADR 0034](../decisions/0034-company-status-derived-tags.md); the essentials:

- **Three independent tags, in canonical order** — **Partner** (the manual `companies.isPartner` boolean), **Client** (has ≥1 **confirmed** project), **Prospect** (has ≥1 **open** opportunity, i.e. `status NOT IN (closed_won, closed_lost)`). A company can carry several at once, or none. There's no direct company→project link, so Client correlates through `opportunities.companyId → opportunities.projectId`; and since a project no longer stores a status (it's **derived from its roles** — [ADR 0033](../decisions/0033-line-of-business-on-role-derived-project-status.md), `deriveProjectStatus`), "confirmed" is expressed in SQL as *the project has ≥1 `confirmed` role and no `tentative`/`paused` role* (the "least-committed wins" rule, matched inline in `getCompaniesPage`).
- **Pure shared module** `src/lib/crm/company-status.ts` (`companyStatusTags`, `COMPANY_STATUS_TAGS`, `COMPANY_STATUS_LABELS`) — no `db`/drizzle, no UI — mirrors the derived-field pattern in `project-derived.ts` so the read computing the flags and the table rendering the badges share one definition of the tags/order/labels.
- **`CLOSED_OPPORTUNITY_STATUSES`** (`closed_won`, `closed_lost`) in `src/lib/crm/opportunity.ts` is the single source of truth for terminal statuses; the prospect check negates it.
- **Computed once, in `getCompaniesPage`** as correlated `EXISTS` subqueries (`isClient`/`isProspect`) so the page stays a single query; `isPartner` is a plain column read. Rendered by `companies-table.tsx` as `secondary` badges (`EmptyCell` when none apply).
- **A "Referrer" tag was considered and dropped for now** — referrals are tracked per-contact/per-staff (the opportunity source junctions), not per-company; no clean company→referral link exists yet.

## Notes

**Companies, contacts, and opportunities** each carry a running log of authored, timestamped free-text **notes** (longer prose, "what happened", ≤5000 chars). This is the surviving half of [ADR 0030](../decisions/0030-crm-timestamped-entries-notes-next-steps.md) — the old **next-step** kind was removed and reborn as the [Tasks](#tasks) entity ([ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md)). The essentials:

- **Three concrete tables, not a polymorphic one** — `contact_entries` + `company_entries` (`crm-schema.ts`) and `opportunity_entries` (`opportunities-schema.ts`), each a real FK to its parent (`onDelete: cascade`). Same shape: `id`, `<parent>Id`, `body`, `authorStaffId` (FK → `staff`, `onDelete: set null` — attribution, not ownership), `createdAt`/`updatedAt`, index on `(<parent>Id, createdAt)`. Row types `ContactEntry` / `CompanyEntry` / `OpportunityEntry`.
- **No `kind` discriminator anymore** — the shared `crm_entry_kind` pgEnum and the `kind` column were **dropped** (migration `0008_eminent_mandroid.sql`), the entry indexes lost `kind`, and the length cap is a single `NOTE_MAX_LENGTH` (5000). The tables are otherwise unchanged.
- **No per-entry ownership** — any `crm.edit` holder may add/edit/delete any note (product decision: shared team logs). All nine actions (add/update/delete × contact/opportunity/company) gate solely on `crm.edit`. The author is resolved server-side (`resolveAuthorStaffId.ts`), never trusted from the client.
- **The scalar `opportunities.nextSteps` column is gone** — migrated into `opportunity_entries` as the first entry, then dropped, and removed from the create/update schemas, actions, `updateOpportunityField` union, and the add-opportunity form.
- **Shared plumbing** — schema `entries.schema.ts`, read helper `entryViews.ts` (`EntryView`, epoch-millis timestamps, `editedAt` only when edited, via the shared `selectEntries`), UI `entry-log.tsx` (one `Textarea`-composer component, `variant`-switched across contact/opportunity/company). Note timestamps render with `formatShortDate` (from `src/lib/format/format.ts`).

## Tasks

**Companies, contacts, and opportunities** each carry a list of **tasks** — assignable, completable to-dos that **replaced the old free-text "next steps"** ([ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md)). Full rationale in that ADR; the essentials:

- **One `tasks` table, three concrete parent FKs** (`src/lib/db/tasks-schema.ts`, migration `0008_eminent_mandroid.sql`). Fields: `description` (≤1000), `ownerStaffId` (the assignee) + `creatorStaffId` (both FK → `staff`, `onDelete: set null` = attribution not ownership), `done` (boolean), a nullable `completedAt` (stamped when `done` flips true, cleared on reopen), timestamps, id prefix `task`. The parent is **exactly one** of `companyId` / `contactId` / `opportunityId` (all `onDelete: cascade`), enforced by a DB `CHECK (num_nonnulls(...) = 1)` — the same concrete-FK, no-polymorphic-parent convention the entry tables use, but one table suffices here. Row type `Task`. **Four indexes, not three:** one **per parent** on `(parent, done)` (the CRM read — "open tasks for this parent"), plus **`tasks_owner_done_idx` on `(ownerStaffId, done, createdAt desc)`** (`drizzle/0023_panoramic_ben_parker.sql`) for the [personal list](#the-personal-task-list-on-), which reads the other way round — one *owner's* open tasks, newest-assigned first — and which none of the parent-first indexes can serve. The archive query orders by `completedAt`, which that index can't sort; left to sort in memory deliberately, since one person's closed tasks are a small, capped set.
- **Three of the four actions gate solely on `crm.edit`; completion has an owner path.** `createTask` / `updateTask` / `deleteTask` are the flat capability — rewording or destroying a task *is* editing CRM data, and there is still no per-task ownership over *those*. **`setTaskDone` is different: the task's own assignee may always complete it, and anyone else needs `crm.edit`** (`canCompleteTask` + the `authorizeTaskDone` hook in metadata; the rule itself is the pure, unit-tested `taskCompletionAllowed` in `src/lib/crm/task-completion.ts`, which takes the already-evaluated capability as a boolean rather than re-checking a role). **Why:** `crm.edit` is sales/manager/admin only, but `ownerStaffId` can point at *any* staff row — so under the old gate an engineer or a finance lead handed a task could not tick it off, and their own todo list would be read-only. Same shape as `canEditStaff` ([ADR 0014](../decisions/0014-rbac-better-auth-access-control.md)): own always, others behind the capability, `ownStaffId` with `activeOnly` **off** because this is an ownership check. A **null** owner or a null caller never matches (two nulls read as equal would hand every unassigned task to every unlinked account), and an unknown id denies for non-holders. **No new capability, no matrix change** — see [ADR 0065](../decisions/0065-home-personal-task-list-and-assignee-completion.md) §2 and [permissions.md](./permissions.md). The **creator** is resolved server-side (`resolveAuthorStaffId`); the **owner defaults to the creator** when the composer doesn't pick one.
- **Entity-scoped in the model, personal in one surface.** Every task still hangs off exactly one CRM parent, and it can still only be **created** on one; `@`-mentions remain unbuilt (the owner is set only via the staff picker). But the "no global My Tasks page" cut is spent: the [personal task list](#the-personal-task-list-on-) on `/` reads across all three parents. Nothing is created or reassigned from there.
- **Open tasks surface in list + board + detail views** — `getContactsPage` (`ContactRow.openTasks`), `getOpportunitiesBoard` (each card's `openTasks`), and `getCompanyDetail` (each `CompanyContact.openTasks`) call the shared **`openTasksByParent`** (one grouped query per page, oldest-open first, **left-joining `staff`** so each `OpenTaskSummary` carries `ownerId`/`ownerName`), driving the contacts-table + company-detail Contacts "Next steps" columns and the kanban card's task list. Detail views (`getContactDetail`, `getCompanyDetail`, `getOpportunity`) fetch the parent's own full `TaskView[]` via `getTasksForParent` (open-first, owner/creator names resolved). The **companies list** table deliberately shows no tasks (rolling contact tasks up onto it was declined).
- **Every contact-row Next steps cell is editable in place** (`ContactTasksCell`) — on the contacts list **and** the company detail page's Contacts tab — complete / edit / delete / add, straight from the row, through the same four task actions (`crm.edit`, completion also allowing the assignee). This **reverses the earlier read-only-everywhere stance**: task upkeep is the reason people open a contact at all, so wherever a contact's tasks are listed is where it belongs. `OpenTasksCell` now survives only as this cell's non-editor fallback (the kanban card mirrors the shape inline). Nuances worth knowing:
  - **Each task row instantiates its own `useAction` hooks, deliberately.** `useAction` keeps one in-flight request and drops any superseded result, so a cell-wide hook shared across rows would swallow the first row's error (and clear its pending state) the moment you touched a second. Per-row hooks also make "busy" just `isPending`, with no id bookkeeping.
  - **Errors surface as toasts**, not inline text — a table cell has no room for an error line.
  - **Completing a task does NOT remove it from the cell.** A ticked task keeps rendering below the open ones, struck through, so unticking it (`setTaskDone { done: false }`) is a one-click undo. The state is a **`Map<taskId, { task, done }>` of *overrides*** — tasks whose done-state this cell changed during the visit — not a plain "completed" list, because the server list carries only *open* tasks and lags a `router.refresh()` behind every toggle, so the gap must be covered **in both directions**: a just-completed task is still in `tasks` (render it struck, not twice), and a just-reopened one has left the local pile but hasn't reappeared in `tasks` yet (keep rendering it, or undo blinks the row away). Overrides are **session-scoped** — a navigation or hard reload clears them, which is the intended lifetime for an undo affordance.
  - **Completed rows are deliberately not editable** — plain struck-through text, no popover trigger. The cell is holding the last copy it saw of a task the server no longer returns, so an edit there would silently drift from the row. Only the checkbox stays live (to reopen).
  - **The editor is a popover, not an inline expansion — rows never grow.** A task renders as one compact line (`Checkbox` · truncated description · owner avatar) and the **description text is the popover trigger**; the popover holds `TaskFields` (`stacked`) + Cancel/Save, and **Delete lives inside it**. There are no hover-revealed pencil/trash icon buttons: an earlier inline-expansion editor made a row jump several lines tall mid-table, which is what this replaced. Base UI's `PopoverTrigger` takes a `render` *element*, hence the `trigger: ReactElement` prop.
  - **"Add" is always visible**, not hover-only (on a contact with no open tasks a hover-only affordance would be invisible until you happened to pass over the empty cell), and opens the *same* popover with an empty draft, owner prefilled to the viewer.
  - **Each row's popover state is local to that row**, and re-seeds the draft description + owner from the row on open, so a cancelled edit never lingers and one row's save can't close another's editor.
  - **The owner rides in the row as a `TaskOwnerAvatar`** (initials disc + tooltip, dashed disc when unassigned) — the most compact way to carry "whose next step is this" in a table cell. `OpenTasksCell` was restyled to the identical row so the non-editor fallback matches.
- **Shared plumbing** — schema `tasks.schema.ts` (client-importable), reads `getTasks.ts` (per-parent) and `getMyTasks.ts` (per-owner), parent-column map + revalidation in `taskParent.ts`, the completion gate in `canCompleteTask.ts` + the pure `src/lib/crm/task-completion.ts`, parent labels/hrefs in the pure `src/lib/crm/task-parent-link.ts` (**not** `taskParent.ts` — that one is the server-only kind → FK-column map; the `-link` suffix exists because the two are easy to confuse), UI `task-list.tsx` (composer + completable list), `task-fields.tsx` (the shared description + owner field pair, `stacked` for narrow cells, Escape-to-cancel), `contact-tasks-cell.tsx` (the editable in-row cell used by both contact tables, incl. its local `TaskEditorPopover`), `open-tasks-cell.tsx` (its compact read-only fallback) and `task-owner-avatar.tsx` (the owner initials disc both cells share). The task composer's owner defaults to the viewer via `getCurrentStaffIdentity` — server-rendered on the detail pages **and on `/contacts`** (passed into `ContactsTable`), and bundled into `loadOpportunityDetail`'s `{ detail, currentStaff }` for the drawer.

### The personal task list on `/`

**Every task assigned to the signed-in person, in the home dashboard's *Your Status* band** — the one task surface that isn't scoped to a CRM parent. Full rationale in [ADR 0065](../decisions/0065-home-personal-task-list-and-assignee-completion.md); the layout side is in [../ui.md](../ui.md#--home-dashboard-two-bands-two-time-bases). What matters when working here:

- **The read takes no `staffId`** (`getMyTasks`, `src/actions/crm/getMyTasks.ts`). Like `getMyAllocations`, it resolves the subject from the session, so it is **own-data-only by construction** — no cross-user id to authorize, therefore no gate to get wrong. No linked staff record ⇒ empty lists, never an error. Two queries: all **open** tasks by `createdAt desc` (unbounded), plus **completed** by `completedAt desc` capped at `ARCHIVE_LIMIT` (200), with `completedTruncated` telling the UI to say so. Each row resolves its parent's display name through a left join per parent kind.
- ⚠️ **`MyTaskView` is a disclosure whitelist.** It is a **Client Component prop on `/`**, so every field lands in the page HTML — the same boundary `org-status.ts` documents ([ADR 0063](../decisions/0063-home-dashboard-two-time-bases-and-point-in-time-staffing.md) §5). Fields are copied one at a time and **never spread**; `ownerStaffId`, `creatorStaffId` and `updatedAt` are withheld, and the payload carries **no `staffId`** either (the caller already has its own — a dead field on the wire, the same reasoning that drops `freeFrom` from the org payload). A spread here would ship whatever column `tasks` gains next.
- **Ticking a task off deliberately does not hide it.** The panel holds a `Map<taskId, boolean>` of done-states changed during the visit and passes the key set to the Archive dialog as **`keepIds`**, which exempts those rows from the **status** filter *only* — search text and parent kind still apply, because that's the person narrowing the list rather than the list moving on its own. Without it a tick would unmount the row just clicked (the panel filters to open; the archive defaults to Completed) and the next reflexive click would land on whatever shifted up. **Session-scoped:** a reload is when a finished task drops out. Overrides are applied once in the pipeline (`applyDoneOverrides`), so the status filter, the strike-through and the staleness flag can't disagree; reopening also clears `completedAt`, or the row would read "Done ⟨date⟩" until the refresh landed. (Simpler state than `ContactTasksCell`'s `Map<id, { task, done }>` — that cell's server list holds only *open* tasks, so it must keep the task object; here the read returns both halves.)
- **Two sort orders on purpose.** The panel sorts by **assignment date** (`mergeMyTasks`) so ticking a row never makes it jump under the cursor; the Archive sorts by **most recently completed** (`sortMyTasksByRecency`), which is also the key the read's `ARCHIVE_LIMIT` window selects on, so display and truncation agree.
- **Staleness is open-tasks-only.** `STALE_TASK_DAYS = 7`; at or past it an open task gets an amber left border **plus a labelled "N days old"** (colour alone would be unexplained). A **completed task is never stale** however old — otherwise the archive lights up amber end to end. `nowMs` is stamped in the Server Component and passed down so the threshold resolves identically across hydration.
- **All of the logic is pure and shared** — `src/lib/home/my-tasks.ts` (`taskAgeDays`, `isStaleTask`, `mergeMyTasks`, `applyDoneOverrides`, `filterMyTasks` incl. `keepIds`, `sortMyTasksByRecency`, `STALE_TASK_DAYS`, `ARCHIVE_LIMIT`), unit tested, and used by **both** the panel and the dialog so a change to what "search" means can't apply to one and not the other. Filters are **in-memory, nothing in the URL** — the whole list is already on the client and `/` keeps no URL state (ADR 0063 §6), hence `SearchFilter`, not `useUrlSearchFilter`.
- **An opportunity parent links to `/opportunities`, not a detail route** (`taskParentHref`) — there is no `/opportunities/[id]`; opportunities render only in the board drawer. Don't "fix" it with an invented href: it would 404.

## Slack scoping channel

An opportunity carries an optional link to a **private Slack channel** for the pursuit team,
`l-scoping-<slug>` (slug from the deal name). Stored as the column pair
`opportunities.scopingSlackChannelId` / `…Name` behind a both-null-or-both-set CHECK plus a named
unique index; `drizzle/0026_wide_marten_broadcloak.sql`, no backfill. **The full model, the Slack app
setup and the limitation that shapes it all live in [slack.md](./slack.md)** — read that before
touching this. The CRM-side facts:

- **It is rendered in the drawer's Details tab, divided off below the meta fields** — it's the rail's
  only *external* fact (a pointer out to Slack), not another attribute of the opportunity. Create /
  link / unlink all happen there.
- **`canManage` is hard-coded `true` there**, because the drawer only mounts for `crm.edit` holders
  (the board gates the click), and `crm.edit` is exactly this kind's gate. If the drawer ever opens to
  non-editors, that prop must become a real flag. **A consequence worth knowing:** `canManage` is also
  what decides whether the row survives a missing bot token, so on this surface a token-less
  environment shows every drawer viewer a muted "Slack isn't connected" rather than nothing — the row
  is hidden only from people who couldn't act on it ([slack.md](./slack.md) → *Feature flag*).
- **Only the scoping channel appears here.** A *project's* channel is managed on `/projects/[id]`:
  many opportunities can feed one project, so there'd be no unambiguous owner for the control, and a
  sales-only viewer would face a permanently disabled button. Creating a project also **does not**
  carry the scoping channel over — different visibility, different members.
- **The gate is an `authorize` hook, not a new capability.** `authorizeSlackChannel` resolves
  `crm.edit` from the `kind` on the input, because the project kind needs the disjoint `projects.edit`.
  **No matrix change** — see [Authorization](#authorization).
- **Because the channel is private, the bot can only see it if it was `/invite`d.** So search and the
  inline suggestion are structurally incomplete for scoping channels; the dialog says so under the
  picker. This is the feature's defining limitation, not a bug to route around.

## Relationship strength

A contact carries an optional **relationship strength** — how strong our relationship with them is, on a **1–5** scale, **null = not yet rated**. It's a plain `integer` on `contacts` (migration `drizzle/0001_past_agent_zero.sql`); the level meanings live in the pure, client-importable module **`src/lib/crm/relationship-strength.ts`** — **1** New/Unestablished, **2** Weak, **3** Developing, **4** Strong Supporter, **5** Champion/Trusted Partner — the single source shared by the column comment, the zod schemas, and the star UI (same pattern as `feedback-rating.ts`, [ADR 0016](../decisions/0016-junction-table-and-shared-enum-conventions.md)).

- **Edited inline as stars, no confirm step.** The contact detail page renders `InlineRelationshipStrengthField` (a reusable `StarRating`, `src/components/form/star-rating.tsx`) in its own meta-sidebar section between the [Relationships](#contact--contact-relationships) group and the owner, labelled **"Relationship strength"** (the visible `<Label>` was widened from "Relationship" to match the `StarRating` aria-label and to stop it reading as a shorthand for the Relationships group right above it — the component, the `updateContactField` variant and the column are all still `relationshipStrength`); **clicking a star writes immediately** via **`updateContactField`**'s `relationshipStrength` variant (writes only that column — like the field action's other variants), with optimistic local state that reverts on error. Read-only stars for non-`crm.edit` viewers. (**It is the only write-on-toggle control in the sidebar** — the contact's Status flag was briefly a sibling switch here and now lives in the Edit dialog instead, so don't reach for this shape when adding one.)
- **Round-trips through the full record too.** `updateContact` accepts and re-writes `relationshipStrength`, and the edit dialog keeps it in `defaultValues` (no rendered field) so a full-record save leaves it unchanged — exactly like `ownerId`.
- **Surfaced only on the contact detail page** (as the sidebar rating). Not shown on the contacts list table or company detail Contacts table.
- **Seed** assigns a random 1–5 to ~85% of contacts (`scripts/seed/crm.ts`).

## Contact status (active / inactive)

`contacts.isActive` is a notNull boolean defaulting true. Its **display side is a pure, client-importable module — `src/lib/crm/contact-status.ts`** (no `db`/drizzle, the sibling of `relationship-strength.ts` and the same "one source of truth for a contact attribute's display" role): `ACTIVE_LABEL` / `INACTIVE_LABEL`, `contactStatusLabel(isActive)`, and two explanation strings.

- **The word is "Inactive", never "former"** — and that's the point of the module. "Former" describes only *one* of the situations the flag covers: the person no longer works at the company on the record. It equally covers a record that's **no longer relevant or valid at all** — a duplicate, a bad record, someone we simply no longer deal with. "Inactive" covers both **without asserting a reason**, which matters because **the row doesn't store which reason applies.** (Don't add prose that reintroduces "former" for the flag; the only surviving "former" mentions in the code are the ones explaining why the word isn't that.)
- **Two explanation strings, by how much is known.** `INACTIVE_EXPLANATION` is the long form for the edit dialog: it names *both* cases and adds that inactive contacts are hidden from the contacts list unless included. `INACTIVE_BY_SUCCESSION_EXPLANATION` is the narrower line used when the record was deactivated by a `succeeds` link — there the reason *is* known, so it says it instead of listing possibilities. The dialog picks between them on `contact.successor`.
- **Four badge render sites, one exported constant — that's the drift guard.** `contacts-table.tsx`, `contact-detail-view.tsx`, `company-detail-view.tsx` and `related-contacts-section.tsx` all import `INACTIVE_LABEL` rather than hardcoding the word, so a future rename is one edit. The edit dialog's Status switch uses `contactStatusLabel(field.value)`, and the succession copy is worded to match — `successionSideEffectSentence` and the `succeeds` kind hint in `contact-relationship.ts`, the remove-confirm body in `contact-relationships-section.tsx`'s `removeCopy`, and the sidebar's succession row notes ("Inactive record" / "Active record").
- **Not to be confused with the relationship *description* vocabulary.** "Former employee" (`company-contact-relationship.ts`) and "Former colleague" (`contact-relationship.ts`) are free-text suggestions for [company ↔ contact](#relationships) and `related` links — a different feature, deliberately **not** renamed.
- **The flag has exactly two writers:** the Edit dialog's Status switch (`updateContact`) and `createContactRelationship` marking a succession's predecessor inactive. There is deliberately no `isActive` variant on `updateContactField`. See [Contact ↔ contact relationships](#contact--contact-relationships).
- **Inactive without a successor is normal.** The seed only ever produces inactive contacts *as* succession predecessors, but a hand-deactivated record has no successor, and the UI handles it: badge shown, no "Moved to" line.

## Contact ↔ contact relationships

**One typed junction, `contact_relationships`, carries every person-to-person link** — it replaced the single-purpose `contacts.managerId` self-FK. Full rationale in [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md); the schema shape is in [../data-model.md](../data-model.md). Three kinds, five reading directions:

| `kind` | Sidebar caption (viewed contact's POV) | Cardinality | `description` |
|---|---|---|---|
| `reports_to` (outgoing) | **Reports to** | ≤1 per contact, **same company** | NULL |
| `reports_to` (incoming) | **Direct reports** (read-only) | many | NULL |
| `succeeds` (outgoing) | **Previously** | ≤1 predecessor | NULL |
| `succeeds` (incoming) | **Moved to** (read-only) | ≤1 successor | NULL |
| `related` (symmetric) | **Also connected** | ≤1 per unordered pair | **required** |

- **Direction lives in the caption, never in the row.** Because every caption is phrased from the viewed contact's point of view, a bare list of names is unambiguous without spending 320px of rail on "…reports to them" suffixes. Captions/labels/hints all come from the pure `src/lib/crm/contact-relationship.ts`, which is also the source of the pgEnum tuple, the zod union and the seed.
- **The two reverse groups are read-only.** Their authoritative row is owned by the *other* contact (whose page is one click away), so removing one from here would silently rewrite someone else's record. **Edit** exists only for `related` — it's the only kind with anything editable (its description); endpoints and kind are immutable everywhere.
- **Cardinality is enforced by four named partial unique indexes, not app checks.** A table-level `unique()` can't carry a `WHERE`, and an app check is a read that two concurrent writes can both pass. The names (`..._one_manager_uq`, `..._one_predecessor_uq`, `..._one_successor_uq`, `..._related_uq`) are load-bearing: Postgres reports the *index* name in a 23505, so each rule gets its own message. **The symmetric one is keyed on `(least(a,b), greatest(a,b))`** so (A,B) and (B,A) are the same link — canonicalised in the index rather than the writer, where it could be forgotten or raced. There is deliberately **no** `unique(contactId, relatedContactId, kind)`. **Gotcha:** the enum literals in each index's `where` are inlined, not interpolated — drizzle-kit would emit a `$1` placeholder and broken DDL.
- **`description` is required for `related` and NULL otherwise**, enforced twice on purpose: the zod discriminated union owns the message, the CHECK `contact_relationships_description_kind` owns the invariant. `CONTACT_RELATION_SUGGESTIONS` are autocomplete hints only (nothing validates against them), same free-text stance as [Relationships](#relationships).
- **A succession marks the predecessor inactive, atomically.** `createContactRelationship` sets `contacts.isActive = false` on the old record in the same transaction as the insert, so there's no window where the chain exists but the old record still shows up in the default list and every picker. **Removing the link does not undo it** — `isActive` is an independent fact ("we no longer deal with them"), not a derivation, and the remove-confirm copy says so rather than promising a revival. **The way back is the Edit dialog's Status switch** (`updateContactSchema`'s required `isActive`, written by `updateContact`) — that's what keeps "Inactive" from being a one-way trap, and it's also how you retire someone who simply left with no new record to point at. (That switch's helper line narrows to `INACTIVE_BY_SUCCESSION_EXPLANATION` on a record a succession deactivated, because there the reason *is* known.) Because the dialog is a **full-record** save, a stale one submitted after a succession will re-set `isActive` to true; ordinary last-write-wins, documented rather than special-cased.
- **You can't add "X reports to me" from a manager's page** — accepted, and load-bearing. The viewed contact is always the row's `contactId`, which is what lets "at most one manager / one predecessor" be enforced by **omitting the kind from the dialog's Type select** (with a muted hint saying why) instead of surfacing a server rejection.
- **The dialog** (`contact-relationship-dialog.tsx`) is one component for all three kinds, ordered **contact first, then type** — pick the person, then say how they relate. That order is what makes the contact `EntityCombobox` a **single unscoped candidate set** (everyone but this contact, inactive contacts included via `includeInactive` — hence the placeholder "Search contacts, including inactive…" — always employer-labelled via `withCompany`) instead of three per-kind scopes: the picker can't know what would be valid before the type exists. So the narrower rules — a manager must be a colleague, a predecessor must be at a different company — are enforced **on submit** by `assertValidContactRelationship`, not by making bad candidates unofferable, and the chosen contact is **kept** across a type change rather than cleared (it was picked first; wiping it would undo the user's last action). The `EnumSelect` sits beneath, its `succeeds` option worded *"Same person at a previous company"* rather than anything about "records" — the two rows are one human, and "record" is the part a reader has to decode. Also: a pre-submit warning when a `succeeds` target is chosen (`successionSideEffectSentence` — "Adding this marks X as inactive." — the one write with a side effect on another record), and an inline "New contact" affordance.
- **The rail needed a new primitive.** `ContactRelationshipsSection` deliberately does *not* use `DetailSection` + `DetailTable` (their columns don't fit 320px); it uses the shared **`SidebarGroup`** in `detail-parts.tsx` plus local `RelationshipGroup`/`RelationshipRow`. Direct reports preview 5, then a `Collapsible` (not a nested scroller). The section renders nothing at all when empty *and* the viewer can't edit — a deliberate break from `MetaField`'s always-show-an-em-dash rule, because this is a collection with an action, not a scalar with a stable slot.
- **Seed** (`scripts/seed/crm.ts`) has to honour the same invariants the DB does, or the partial uniques abort it: `reports_to` points only at a **strictly earlier** colleague (structurally acyclic), 5 `succeeds` pairs across *different* companies where the newer record takes over the older one's name and the older is marked inactive, and `related` rows deduped on the **unordered** pair. The predecessor `wipe.ts` list and `seed.ts`'s summary count both cover the new table.

## Relationships

> **Not to be confused with [Relationship strength](#relationship-strength)** (a 1–5 rating of *our* rapport with a contact) or with [Contact ↔ contact relationships](#contact--contact-relationships) (person-to-person links). This section is about a **link between a company and a contact who doesn't work there**.

`contacts.companyId` answers "where does this person work?" — exactly one company, or none. **`company_contact_relationships`** answers the other question: "who else touches this company?" One row = one (company, contact) pair + a short free-text **`description`**. The motivating case is a **partner company's CSM working on one of our accounts**; also an embedded FDE, a former employee, an investor on a client's board. See [ADR 0048](../decisions/0048-company-contact-relationships-beyond-employment.md).

- **One relationship per pair** (a named `unique(companyId, contactId)`). Adding a duplicate returns "edit the existing one instead" rather than silently creating a second row, which keeps "edit the description" unambiguous. Relaxing this later is a one-line migration; adding it later would need a de-dupe, so the strict direction was chosen deliberately.
- **Employment is never a relationship.** The create action rejects a contact whose employer already *is* the target company, and both pickers pre-filter (`searchContacts.excludeCompanyId` on the company side, `searchCompanies.excludeId` on the contact side) so the case is normally unreachable in the UI — the server check is the backstop, the same posture the [contact-relationship checks](#contact--contact-relationships) take. Reads are *not* filtered the same way: a link that becomes redundant after an employer change stays visible, and therefore removable.
- **Free text with suggestions, not an enum.** `RELATIONSHIP_DESCRIPTION_SUGGESTIONS` (`src/lib/crm/company-contact-relationship.ts`, pure + client-importable) offers **CSM, FDE, Partner manager, Former employee, Investor**; nothing validates against the list, so novel wording persists verbatim (≤120 chars). Deliberately *not* a pgEnum — the label set is open-ended, so [ADR 0016](../decisions/0016-junction-table-and-shared-enum-conventions.md)'s tuple→pgEnum convention (which exists for *closed* sets) doesn't apply. The picker is the new **`SuggestInput`** primitive (see [../ui.md](../ui.md#suggestinput-vs-entitycombobox)).
- **Editable from either side, so every write revalidates both.** The row renders as "Related contacts" under the company page's **Contacts** tab and as the contact page's **Companies** tab, and add/edit/remove work identically from either — hence the shared `RelationshipDialog` (one component, `side` picks which endpoint is fixed) and the two-sided `revalidateCompanyContactRelationship`. **Endpoints are immutable once created**: the update action takes only a description, so the edit dialog shows the target as a disabled field and re-pointing means remove + re-add. On the **company** side, a related contact who is himself inactive is badged **"Inactive"** in the name cell (`related-contacts-section.tsx`), matching the employee directory above it.
- **Seed** makes ~30 rows from 35 attempts (`scripts/seed/crm.ts`), biased toward contacts at partner companies so the seeded data reads like the motivating case; it skips self-employer pairs and repeats. Verified against the seeded DB: 0 self-employer violations.

## Location

Companies and contacts each carry an optional **location** — where they're based, a **free-text `"City, CC"` label** (e.g. `"Toronto, CA"`), **null when unknown**. It's a plain nullable `text()` column, **not a FK or enum** (migration `drizzle/0005_secret_zarek.sql`); the full rationale and the shared dataset (which `staff` also uses) live in [../data-model.md](../data-model.md#location-free-text).

- **Picked from a static world-cities list, not typed freely.** The value is chosen through a searchable `EntityCombobox` backed by `searchCities` (`src/actions/cities/searchCities.ts` → the pure `@/lib/cities/cities` module over `world-cities.json`). The label string itself is stored — there's no city id (the combobox's `EntityOption` uses the label for both `id` and `name`).
- **Edited inline on the detail page**, mirroring the owner field: `InlineLocationField` (`inline-location-field.tsx`) reads as text ("Unknown" when unset) until the pencil, then swaps in the city picker with Confirm/Cancel; Confirm calls the field action's `location` variant (`updateCompanyField`/`updateContactField`, `crm.edit`-gated), whose `revalidatePath` refreshes the server-rendered display. **Placement differs per page** — its own sidebar section on the company page, folded into the contact page's contact-method block right under Company (see the detail-pages bullet above).
- **`searchCities` is auth-only, deliberately un-gated by capability** — it exposes only static public reference data (see [Authorization](#authorization)).
- **Edited on the two detail pages** (sidebar), **displayed and now *filterable* on both list tables.** The companies and contacts lists each carry a **location filter** — a city picker + a **"Search nearby"** switch that widens the match to cities within `NEARBY_RADIUS_KM` (~100 km) of the picked one. Both filter **server-side, URL-driven** (params `city` + `nearby=1`), mirroring the companies name/status filter pattern: the pages parse the params and pass `{ city, nearby }` into `getCompaniesPage`/`getContactsPage`, whose `where` pushes `inArray(location, nearby ? citiesNear(city) : [city])`, AND-combined with the list's other conditions (companies: name/status; contacts: the name search). **This gave contacts its first list filter** (`ContactsListFilters` + `ContactListFilters`/`contactsWhere` on the read); the contacts bar has since gained a **name search** too, and now lays out like the companies bar — search + "Clear filters" on the first row, the location filter on a row below. The shared control is `location-filter-control.tsx`; `citiesNear`/`NEARBY_RADIUS_KM` live in `@/lib/cities/cities` — see [../data-model.md](../data-model.md#location-filters). **Seed** assigns a US/CA city to ~80% of companies and ~70% of contacts (`scripts/seed/crm.ts`).

## Authorization

**Reads are open** — any signed-in user can browse all companies, contacts, and opportunities (the `(app)` gate is the boundary). **All CRM writes** are gated by a single capability — **`crm.edit`** (renamed from `contacts.edit` when opportunities landed), granted to `sales`, `manager`, `admin` — **flat, with exactly one ownership dimension: completing a task you were assigned** (see below). It covers creating/editing companies, contacts, *and* opportunities — including the inline company/contact creation and the detail-page inline **owner / location / relationship-strength** edits, the Edit dialog's **Active/Inactive status** (the discriminated-union `updateCompanyField`/`updateContactField`), the opportunity detail drawer's edit/move, **deleting an opportunity** (`deleteOpportunity`, which also detaches/cleans up its project), `loadOpportunityDetail` (edit-only read), the nine notes actions (add/update/delete × contact/company/opportunity, **no per-entry ownership**), **three of the four task** actions (`createTask`/`updateTask`/`deleteTask` — no per-task ownership over those; [ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md)), the three **[company ↔ contact relationship](#relationships)** actions and the three **[contact ↔ contact relationship](#contact--contact-relationships)** actions (create/update/delete each, **no per-row ownership**), and every type-ahead picker (`searchCompanies`/`searchContacts`/`searchStaff`) that backs entry. (**Exception:** `searchCities` (the location picker's type-ahead) and `nearbyCityLabels` (the "search nearby" resolver) are **auth-only with no capability gate** — both serve only static, public world-cities reference data, never user/tenant data.) Declared in action metadata; each page hides its "Add" dialog(s) (via one `canEdit` flag) for users without the capability, the **Next steps cell on both contact tables** (contacts list, company detail's Contacts tab) falls back from the editable `ContactTasksCell` to the read-only `OpenTasksCell` on that same flag (the task actions are the real boundary), the opportunities board renders **static (no drag-and-drop) with no clickable drawer** for non-editors, and the opportunities list view renders **plain-text names (no drawer)** for them (the list read itself, `getOpportunitiesPage`, is ungated like all CRM reads).

**The one ownership dimension inside `crm.edit`: completing a task.** `setTaskDone` is the single CRM write that is **not** a flat capability — the task's **assignee** may always complete it, anyone else needs `crm.edit` (`canCompleteTask` + `authorizeTaskDone`; see [Tasks](#tasks) and [ADR 0065](../decisions/0065-home-personal-task-list-and-assignee-completion.md) §2). It exists because `crm.edit` is sales/manager/admin while a task can be assigned to anyone, so the flat gate made a person's own todo list read-only to them. **It is deliberately narrow:** completion only, not edit or delete, and it adds **no capability and no matrix row**. Don't generalize it to the rest of the domain — notes and the two relationship junctions still have no ownership dimension at all.

**`crm.edit` is also reached through an `authorize` hook, for the Slack scoping channel.** The five
Slack channel actions (`create`/`link`/`unlink`/`search`/`suggest`) declare
`authorize: authorizeSlackChannel`, which parses the channel `kind` off the raw input and requires
**`crm.edit` for `scoping`** and `projects.edit` for `project`. It is a hook rather than a static
`metadata.permission` precisely because those two capabilities are **disjoint** (sales holds only the
first, delivery-manager only the second), so no single static capability covers both kinds. **No new
capability, no matrix row** — and an unparseable `kind` is *denied*, not skipped. See
[slack.md](./slack.md) and [ADR 0067](../decisions/0067-slack-channel-links-bot-token-denormalized-pairs-and-record-scoped-gate.md).

**RBAC note for the audit:** `createContactRelationship` writes a *second* table's column — a `succeeds` link flips `contacts.isActive` on the predecessor. That is **not** an escalation: `crm.edit` is already the capability **`updateContact`** requires to write that same column by hand (via the edit dialog's Status switch), so the two paths need identical permission. (Not `updateContactField` — that action has no `isActive` variant.)

**Cross-domain RBAC nuance (delivery-stage handoff).** Creating a project needs **`projects.edit`**, which `sales` does *not* have (only `crm.edit`). The board is passed a separate `canCreateProject` flag (`projects.edit`): a user who *can* create projects gets the prefilled create-project prompt when they move a card into a delivery stage without one; a user who can't (e.g. `sales`) gets a **toast telling them a delivery manager must create the project first**. No permission was widened — the division of labour is deliberate ([ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md)). See [domains/permissions.md](./permissions.md).

## Key flows

- **Pipeline management** (built) — create Opportunities and move them through the pipeline (`maturing` → `lead` → … → `closed_won`/`closed_lost`) by **dragging cards** across the kanban board (`updateOpportunityPosition`). Multi-substatus groups (Scoping/Allocating/Closing) collapse into one column or expand into subcolumns; dropping onto a collapsed group picks the first substatus (if dragged from earlier in the pipeline) or the last (from later). Non-editors (`!crm.edit`) get a static, read-only board.
- **Browse opportunities (board + list)** (built) — the board caps its three high-volume columns (Maturing/Won/Lost) at 20 cards and offers a **"Show N more"** deep-link into the **list view** (`?view=list`), a paginated table filterable by stage / line of business / name search. The board itself also carries **client-side name + line-of-business filters** over its loaded cards (loaded-only by design — an active LOB filter rides through the "Show more" deep-link so the list applies it too). The list's name cell opens the same detail drawer; there's no standalone detail route. See [Board + list views](#board--list-views).
- **Edit a company / contact** (built) — from the detail page (`/companies/[id]`, `/contacts/[id]`), a `crm.edit` holder opens an edit dialog covering the core fields and — for contacts — the employer. Saved via `updateCompany` / `updateContact` (`.returning()`-guarded by id; an empty `returning` → user-safe "That … no longer exists"), both re-running the **email-uniqueness** map `createContact` uses. **Changing a contact's employer also drops their `reports_to` link** (a manager is a colleague by definition), in the same transaction, and revalidates the ex-manager's page; the dialog warns before you save. Both revalidate the list path *and* the detail path.
- **Link two contacts / retire a contact** (built) — from a contact's page, a `crm.edit` holder opens the Relationships group's one dialog and picks a kind: their **manager**, the **earlier record** of someone who changed employer (which marks that record Inactive), or any other **connection** with free-text wording. Removing a succession link leaves the old record Inactive; the **Edit dialog's Status switch** is the explicit way back, and also how you retire someone who simply left (or drop a record that's just no longer valid). Inactive contacts drop out of `/contacts` (unless "Include inactive" is on) and out of every picker — but an inactive row that *does* appear links onward to its successor ("Moved to X at Y"), and a company's page keeps listing its inactive people, badged. See [Contact ↔ contact relationships](#contact--contact-relationships) and [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md).
- **Reassign a company / contact owner** (built) — the optional **staff owner** is edited **in place** on the detail page (`InlineOwnerField`), separate from the edit dialog — matching the opportunity drawer's per-field pattern. Confirming saves through the field-scoped **`updateCompanyField` / `updateContactField`** action (the `owner` variant), which writes just `ownerId` (or `null` to unassign) so it neither clobbers concurrently-edited fields nor re-runs the contact manager rule; both revalidate the list + detail paths. The edit dialogs still carry `ownerId` in their form defaults so a full-record save round-trips the current owner unchanged.
- **Edit an opportunity** (built) — clicking a card opens the **detail drawer** (`opportunity-detail-sheet.tsx`), which lazy-loads via `loadOpportunityDetail`. Its **Details** tab edits line of business, source, company, contacts, owners (the meta column) **one field at a time in place** (pencil → Confirm/Cancel), plus name and status from the header; each Confirm calls the field-scoped `updateOpportunityField`, which writes only that field's slice. This is CRM's first field-edit flow beyond the drag-move, and the first use of the shared `InlineEditField` primitive. Tasks & notes share the Details tab's right column (see next flows), not the meta fields.
- **Log notes** (built) — on a company/contact detail page or the opportunity drawer's **Details** tab, a `crm.edit` holder appends timestamped **notes** ("what happened", ≤5000 chars), shown newest-first with author + timestamp and inline edit/delete. **Any editor may amend any note** (no per-entry ownership). The author is stamped server-side from the session. See [Notes](#notes) and [ADR 0030](../decisions/0030-crm-timestamped-entries-notes-next-steps.md).
- **Manage tasks** (built) — on the same detail pages / drawer, a `crm.edit` holder creates **tasks** (a description + an owner, defaulting to themselves), checks them off (stamping a completion date), and edits/reassigns/deletes them; **any editor may create, edit or delete any task** (no per-task ownership there). A parent's **open tasks** surface on the contacts list, the company-detail Contacts table, and kanban cards. Tasks **replaced the old free-text next steps**. See [Tasks](#tasks) and [ADR 0043](../decisions/0043-tasks-entity-replaces-crm-next-steps.md).
- **Work your own task list** (built) — on the home dashboard, **anyone** sees every task assigned to them (no `crm.edit` needed to read or to tick one off — the assignee path), searches it by description *or* parent name, filters by parent kind, and opens an **Archive** dialog for the full history. A tick calls `setTaskDone` and **keeps the row on screen** as a one-click undo; the row's parent links back into the CRM (opportunities to the board). Creating and reassigning still happen on the CRM parent. See [The personal task list on `/`](#the-personal-task-list-on-) and [ADR 0065](../decisions/0065-home-personal-task-list-and-assignee-completion.md).
- **Link a non-employee contact to a company** (built) — from either side: the company page's **Contacts** tab ("Add relationship" beneath the employee directory) or the contact page's **Companies** tab. A `crm.edit` holder picks the other end (employees/employer pre-filtered out), types or picks a description ("CSM", or anything else), and saves; the row appears on **both** pages. Editing changes only the wording; re-pointing means remove + re-add. See [Relationships](#relationships) and [ADR 0048](../decisions/0048-company-contact-relationships-beyond-employment.md).
- **Opportunity → Project handoff + delivery-stage requirement** (built) — **transitioning** an opportunity into the **Allocating** group or later (`requiresProject`, Closed – Lost excepted) requires a linked project; creating one directly in a delivery stage is forbidden. Dragging a card into a delivery stage without a project is **blocked** (only on a genuine stage change — an intra-column reorder never prompts); a `projects.edit` holder is shown the **`CreateProjectFromOpportunityDialog`** — a **budget form** since [ADR 0053](../decisions/0053-project-budgets-and-margin.md), replacing the old bare confirm dialog (`createProjectFromOpportunity` still inherits the opportunity's name + company) — and on creation the pending move completes; a user without `projects.edit` (e.g. `sales`) gets a toast pointing to a delivery manager. Enforced server-side at the entry points (creation ban + transition guard in both status-mutating actions). See [projects.md](./projects.md), [ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), and [flows.md](../flows.md).

## Connects to

- **Contacts ↔ Companies, twice.** The two entities are linked **two different ways, deliberately**: `contacts.companyId` (the single optional *employer*, set-null) and `company_contact_relationships` (many *non-employee* links, both FKs cascade, one row per pair + a free-text description). Neither subsumes the other — see [Relationships](#relationships) and [ADR 0048](../decisions/0048-company-contact-relationships-beyond-employment.md).
- **Contacts ↔ Contacts, one table, three kinds.** `contact_relationships` (both FKs cascade) covers management, succession and free-text ties; `contacts.managerId` is gone. It **interacts with the employer link both ways**: `reports_to` requires the *same* employer (and is dropped when it changes), while `succeeds` requires a *different* one. See [Contact ↔ contact relationships](#contact--contact-relationships) and [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md).
- **Staff** — an opportunity's `owners` and referral `source_staff` are `staff` rows (FK, cascade). This is the first CRM ↔ staff link. A **company and a contact also each carry an optional `ownerId` → `staff`** (`onDelete: set null`) — the accountable owner. Deliberately **set-null, not cascade** (unlike the opportunity junctions): an owner is a soft pointer, so removing a staff member should only unassign them, never delete the company/contact. **Notes** (`authorStaffId`) and **tasks** (`ownerStaffId` + `creatorStaffId`) also point at `staff`, all **set-null** (attribution/assignment survive a staff row's removal). `tasks.ownerStaffId` is now also an **authorization input** (the assignee may complete) and the key of the [home dashboard's personal list](#the-personal-task-list-on-) — the first CRM data on `/`.
- **Projects** — a project belongs to a `companies` row (required FK, `restrict`). The opportunity link now lives on the **opportunity** side (`opportunities.projectId`, nullable FK, `restrict`, **many opportunities → one project**), populated by the handoff/planner flow, and `requiresProject` makes a project a precondition for advancing an opportunity to a delivery stage. `project_roles.opportunityId` (set-null) records which deal created each role, and roles auto-confirm on the win. See [projects.md](./projects.md), [ADR 0019](../decisions/0019-project-opportunity-link.md), [ADR 0024](../decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](../decisions/0031-opportunity-project-planner-and-role-status.md).
- **Slack** — an opportunity owns its **private scoping channel** (`scopingSlackChannelId`/`Name`); the
  mirror pair on `projects` is the public delivery channel, and **each record manages only its own**.
  The two kinds share one module and one `authorize` hook but no capability — see [slack.md](./slack.md).
- **Allocations / Timesheets** via the Project a won Opportunity will create (proposed).
- See [../data-model.md](../data-model.md) and [../flows.md](../flows.md).

- **Edit/delete** — **companies, contacts, and opportunities now all have edit** (companies/contacts via a whole-dialog `updateCompany`/`updateContact`; the opportunity detail drawer via per-field `updateOpportunityField` + drag-move), so a contact's `companyId`/`linkedinUrl`/`ownerId` (and a company's owner) can now be changed after creation, while relationships are added/removed on the contact page rather than in any dialog. **Opportunities now also have delete** (`deleteOpportunity`, gated `crm.edit` — the app's **first delete flow**): it cleans up the linked project first (via the shared `detachProjectFromOpportunity` — a sole-owned project is deleted, else this opportunity's roles are removed and it's unlinked), *then* deletes the opportunity row (its people/entry junctions cascade). Running the detach **before** the row delete keeps `project_roles.opportunityId` provenance intact — see [projects.md](./projects.md#delete--detach). **Companies and contacts still have no delete** — the `onDelete: restrict` on `opportunities.companyId` means a company-delete flow must handle live opportunities.
