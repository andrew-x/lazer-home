# Domain: Staff profiles

**Status: partially realized.** The People of the consultancy, and everything that describes their capacity and capability. The core `staff` + `staff_employment` + `staff_pto` tables now exist in code (`src/lib/db/staff-schema.ts`, barrelled by `src/lib/db/schema.ts`), and two local-only **CSV import tools** populate them from Rippling exports — staff and PTO (see *Import tools* below). A self-service **"My profile"** page (`/profile`) surfaces a logged-in person's own record, and a **browse-staff** feature adds a **directory** (`/staff`, which also has an **org chart** view at `?view=org` rendering `staff.managerId` as a tree — see *Org chart* below) and **per-person profile pages** (`/staff/[id]`) that show *other people's* records via the same presentation; both let you **edit profile links, client intro, a free-text résumé, skills, and two profile surveys — a "Manual of Me" and a "Ways of Working"** (the résumé editor can extract text from an uploaded PDF; skills are picked from a hardcoded catalogue on a dedicated edit page; both surveys are guided, autosaving flows on their own pages sharing one engine — see *Manual of Me* and *Ways of Working* below; owner always, others need the `staff.edit` permission — see *Authorization*) and show a **category-agnostic history feed** (see *Key flows*). **Skills are now built** (inline `jsonb`, catalogue-driven — see below) and so is **compensation** (effective-dated on `staff_employment`, import-only, view-gated — see [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md)). A person's **overall performance level (staff rating levels L0–L4)** is also built, but lives in the performance domain (effective-dated, manager/admin-only — see [performance.md](./performance.md#staff-rating-levels-l0l4--per-role-subratings--built) and [ADR 0032](../decisions/0032-staff-rating-levels-effective-dated-manager-only.md)); the distinct "seniority" concept described here is still proposed. The domain also owns one **People-management** screen — the read-only **profile-completeness** table at `/reporting/profile-completeness` (who has filled in which self-service artefact), gated on the existing `staff.edit` capability — see *Profile completeness* below.

## Purpose

Be the source of truth about who works here — their identity, role, line of business, billability, and utilization target — feeding staffing decisions and performance.

## Key entities

- **`staff`** — the *durable* record of a person: `ripplingId` (**notNull, unique** — the external [Rippling](https://rippling.com) HR id; the import's match key), `name`, `email` (**not unique** — duplicates are tolerated), an optional `userId` link to the auth `user` (see below), profile links (`linkedinUrl`/`githubUrl`/`portfolioUrl`), an optional free-text **`location`** (see below), a `clientIntro` blurb (with its own `clientIntroUpdatedAt`), a free-text `resume` (with `resumeUpdatedAt`), a `skills` list (with `skillsUpdatedAt`), an optional **`allocationNotes`** (a manager-only staffing note edited in the planner — see below), and lifecycle dates (`joinDate`, `terminationDate`, `isActive`). Holds nothing that changes role-to-role.
  - **`resume` / `resumeUpdatedAt`** — nullable `text` + nullable `timestamp`, added in `drizzle/0011_boring_big_bertha.sql`, modelled exactly on the `clientIntro` pair. The résumé is **plain text only — the uploaded PDF is never persisted** (it's parsed to text client-then-server and discarded). `resumeUpdatedAt` is stamped **explicitly by `updateStaffResume`** when the text changes, deliberately **not** `$onUpdate` — an import re-sync writing the `staff` row would otherwise bump it falsely.
  - **`userId`** — nullable, unique FK → auth `user.id` (`onDelete: set null`). The optional 1:1 link from a staff record to its login account: **null until the person signs in** (staff can be synced from Rippling before they ever log in), **unique** so at most one staff per user, and `set null` on delete so removing the auth account keeps the durable staff record intact.
  - **`managerId`** — nullable, self-referential FK → `staff.id` (`onDelete: set null`, added in `drizzle/0025_giant_bullseye.sql`). Who this person reports to — at most one manager, optional. A **durable identity fact on `staff`**, deliberately **not** effective-dated on `staff_employment` (no as-of "who was your manager" demand — every reader wants the *current* line). Mirrors `contacts.managerId` ([ADR 0022](../decisions/0022-contact-manager-self-reference.md)); needs the `AnyPgColumn` return annotation to type the self-reference. **Populated exclusively by the staff CSV import** (matched via the `Manager - Work email` column) — there is **no in-app editor**, so re-imports never fight a manual edit. Displayed read-only as "Reports to …" on the profile.
    **This column is now the most load-bearing field on `staff`, and it has escalated twice:**
    1. **Display** — the profile's read-only "Reports to" line, and (since 2026-07-30) the whole **org chart** at `/staff?view=org`, which renders the column as a tree — the first surface that shows the *shape* of the reporting structure rather than one edge of it (see *Org chart* below and [ADR 0054](../decisions/0054-staff-org-chart-dom-tree.md)).
    2. **Scoping** (2026-07-28) — read in the *inverse* direction to narrow the feedback **"Your reports"** tab (`getFeedbackAboutReports` — `recipient.managerId = caller`, one hop, self-excluded), inside the unchanged `feedback.review` capability ([ADR 0047](../decisions/0047-feedback-reports-scoping-not-granting.md)).
    3. **Authorization** (2026-07-29) — it now **decides read *and* write access** to **performance review notes**, with no capability involved. `src/actions/performance/reviewNoteAccess.ts` is the one place that happens ([ADR 0049](../decisions/0049-review-notes-reporting-line-as-authorization-boundary.md), [performance.md](./performance.md), [permissions.md](./permissions.md)).

    So a wrong/missing link is no longer a cosmetic bug: **a bad import changes who can read a private review conversation.** That is why the importer's "unresolvable and column-absent **preserve**, only a blank cell clears" rule is load-bearing (see *Manager resolution* below) and why the access module keeps its own self-guard. Access follows the **current** line — there is still no as-of resolution — so a manager who changes teams keeps only the notes they authored. See [ADR 0026](../decisions/0026-staff-manager-self-reference.md).
  - **`location`** — nullable `text`, a free-text `"City, CC"` home-base label (e.g. `"Toronto, CA"`) picked from the static world-cities list, **not a FK/enum** (migration `drizzle/0005_secret_zarek.sql`; shared with `companies`/`contacts` — see [../data-model.md](../data-model.md#location-free-text) and the CRM inline picker). **Displayed read-only** as a "Location" meta row in the profile sidebar (`profile-view.tsx`, projected by `getStaffProfile`), but there is **no in-app editor** — it's populated by the seed only (US/CA cities via `cityLabelsForCountries(["US","CA"])` in `scripts/seed/staff.ts`). Unlike CRM's contacts/companies, staff has no inline location picker or `updateStaffLocation` action. It **is** filterable, though: the staff **directory** filters on `location` client-side (city + "search nearby") — see *Directory* under *Key flows*.
  - **`allocationNotes`** — nullable `text` (migration `drizzle/0006_empty_whirlwind.sql`), a **plain free-text planning note about a person's staffing** (e.g. "on bench after Aug 15, wants frontend work"). **Not** a profile field: it has **no in-profile editor and no `updatedAt` sibling**, and it lives on the durable `staff` row (not `staff_employment`) because it's a note about the person's staffing, not an effective-dated employment fact. It is **surfaced and edited only in the allocations planner's manager-only Notes column** ([allocations.md](./allocations.md)). Uniquely for a `staff` field its access is **manager/admin-only for both viewing and editing** — read- and write-gated on the **static `staff.edit` capability**, deliberately **NOT** the owner-or-`staff.edit` path every other staff-field edit uses (see the *Authorization* nuance below and [ADR 0041](../decisions/0041-allocation-notes-on-staff.md)).
  - **`skills`** — a `jsonb` column (`StaffSkill[]` = `{ name, level }[]`, **NOT NULL default `[]`**, added in `drizzle/0016_demonic_rick_jones.sql`) — the schema's **first jsonb/array column**. Skills are stored **inline** here, deliberately **not** a normalized `skill` + join table; each entry pairs a skill name from the hardcoded catalogue in `src/lib/staff/skills.ts` with a 3-value proficiency level (`senior`/`intermediate`/`learning`). See [ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md) and *Skills* below.
  - **`skillsUpdatedAt`** — nullable `timestamp` (`drizzle/0021_green_the_call.sql`), modelled **exactly** on `resumeUpdatedAt`: stamped **explicitly by `updateStaffSkills`** when the list is saved, deliberately **not** `$onUpdate` — a Rippling import re-sync writing the `staff` row would otherwise report as a skills edit. It starts **NULL for everyone** and there is **no honest backfill** (`staff.updatedAt` moves on every import), so "no date" means "not saved since the column shipped", not "never had skills". Its only reader today is the profile-completeness table below.
- **`staff_employment`** — the *time-varying* employment facts for a person. **One row per change**, not an update-in-place: each row is keyed by `effectiveFromDate` (notNull) and the **current state is the row with the latest `effectiveFromDate`**. FK `staffId` → `staff.id` (`onDelete: cascade`). Fields: `lineOfBusiness`, `role`, `employmentType`, `isBillable`, `utilizationTarget` (integer percent 0–100), `billableType` (NOT NULL, default `HUB`), **`isManagement`** (bool, default `false`), and **compensation** — `base`, `hourlyRate`, `guaranteedBonus` (all **NOT NULL** `numeric(12,2)`, `mode:number`) + `currency` (**NOT NULL** `currencyEnum`). (The external `ripplingId` lives on `staff`, not here.) **Only ongoing terms live here:** a `discretionaryBonus` column used to, and was **dropped** (`drizzle/0018_flippant_chameleon.sql`) — a one-off bonus is a dated payment, so it moved to `staff_bonus_payment` below. See [ADR 0007](../decisions/0007-staff-employment-effective-dating.md) for *why* employment is split out and history-as-rows, plus the in-place-correction amendment used by bulk-edit.
  - **Compensation is effective-dated like the rest of the row, but import-only, required, and view-gated.** All four columns are **NOT NULL**. Populated **only by the Rippling CSV import** — there is **no in-app edit UI** (not the profile, not bulk-edit). Comp is **required on every import row** — except **guaranteed bonus, which is optional** (a blank cell defaults to `0`): the importer skips a row it can't supply `base`/`hourlyRate`/`currency` for (see *Import tools*), so there is **no carry-forward on the import path**. It *is* still carried forward when a *non-comp* change spawns a new row via bulk-edit. Visibility requires `staff.viewCompensation` (own comp always visible) — see *Authorization* and [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md). Values/formatting live in the pure `src/lib/format/currency.ts` module (mirrors `line-of-business.ts`), the single source shared by the `currencyEnum` pgEnum, the import zod schema, and display.
    - **⚠️ Comp now has a reader outside this domain and outside `staff.viewCompensation`.** Project margin costs each staffing line from the assignee's `base ÷ HOURS_PER_YEAR` (or `hourlyRate`), reaching it through the single module `src/actions/shared/staffHourlyCost.ts` behind the single gate `getProjectCostBasis` / **`projects.viewMargin`** — so `delivery-manager`, who cannot see the Compensation card, *can* see numbers derived from it. That's deliberate and documented in [ADR 0053](../decisions/0053-project-budgets-and-margin.md); the point for anyone editing here is that **a figure derived from comp is still comp**, and a new one needs a gate of its own. See [projects.md](./projects.md#budget--margin) and [permissions.md](./permissions.md).
  - **`isManagement` is orthogonal to `role`.** It is *not* a role value — someone can work a billable role (e.g. `ENGINEER`) and *also* be management for it. It is set **in-app only** (the bulk-edit tool below; never derived from the Rippling CSV), so the staff import **preserves** it across re-syncs (carried forward when a new effective-dated row is written). It does **not** affect billability — `LEADERSHIP` stays non-billable on its own; the flag is independent. It is **not** surfaced on the staff profile view; it's maintained and read via the bulk-edit tool below.
  - **`billableType` is likewise in-app only.** A required `HUB`|`GLOBAL` value (default `HUB`, no longer a "no billable type" state since `drizzle/0010` backfilled nulls and added the NOT NULL constraint). Like `isManagement`, it is never derived from the Rippling CSV, so the import **carries it forward** when writing a new effective-dated row — a re-sync won't reset a `GLOBAL` person back to `HUB`. Set via the bulk-edit tool below.
- **`staff_pto`** — leave records for a person: `startDate`/`endDate` (both date, notNull), `type` (`ptoTypeEnum`), and `isPending` (bool, default `true`). FK `staffId` → `staff.id` (`onDelete: cascade`), plus a **notNull, unique `ripplingId`** — the Rippling "Leave request ID", the PTO import's match key (one record per leave request). Unlike `staff_employment`, this is **not** effective-dated history — each row is a discrete leave span. `isPending` means awaiting approval; it's cleared on approval, or set `false` on insert when the row is synced from Rippling as already-approved. Populated by the PTO import tool (see below).
- **`staff_bonus_payment`** — one **bonus paid on a date** (`paymentDate`, `type` from the `staff_bonus_type` enum, `amount` + its own `currency`, optional `notes`, nullable-unique `ripplingId`; FK `staffId` → `staff.id` **cascade**, `CHECK amount > 0`). Sibling of `staff_pto` in shape and spirit — discrete dated events, **not** effective-dated, destined to come from Rippling. It carries **no line of business or role**: the reporting side derives them from the employment row in force on the payment date. Entered in-app at `/people/bonus-payments` (`staff.edit` **AND** `staff.viewCompensation`) and reported anonymized at `/reporting/bonuses`; per-person it surfaces as the profile **drawer's Bonuses tab** and as `BONUS` entries in the history feed, both behind `canViewCompensation`. The whole slice is documented in [performance.md](./performance.md) → *Bonus payments*; see also [../data-model.md](../data-model.md) and [ADR 0056](../decisions/0056-bonus-type-cross-cut-matrix.md).
- **Skills** — capability + proficiency level. **Status: built**, but **not** the many:many table originally proposed: they live **inline** on `staff.skills` (jsonb), picked from the hardcoded catalogue in `src/lib/staff/skills.ts`. See the `skills` column above, *Skills* below, and [ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md).

### Enums (`src/lib/db/staff-schema.ts`)

- `lineOfBusiness`: `CORPORATE`, `CORE`, `FINTECH`, `COMMERCE`, `DESIGN` — **shared/global**, not staff-specific (top-level export reused by CRM/allocations).
- `role`: `ENGINEER`, `DESIGNER`, `LEADERSHIP`, `SALES`, `SOLUTIONS`, `OPERATIONS`, `ARCHITECT`, `DELIVERY`, `QA` — the value formerly named `MANAGEMENT` was **renamed in place to `LEADERSHIP`** via `ALTER TYPE ... RENAME VALUE` (`drizzle/0009_purple_exodus.sql`; no data migration, existing rows kept their label). drizzle-kit can't detect an enum-value rename, so the generated destructive drop/recreate was replaced by hand — keep that in mind for future enum renames.
- `employmentType`: `FULL_TIME`, `HOURLY`
- `billableType`: `HUB`, `GLOBAL` (NOT NULL, default `HUB` — every employment row has one)
- `currency`: `CAD`, `USD`, `GBP`, `EUR`, `AED` — the compensation currency (NOT NULL). Values are **derived from the `CURRENCY` tuple in `src/lib/format/currency.ts`** (`pgEnum("currency", [...CURRENCY])`), not hand-listed, so the pgEnum can't drift from the shared module. **Gotcha — adding an enum value:** `AED` was added by appending to the `CURRENCY` tuple + `drizzle/0027_flawless_arachne.sql` (`ALTER TYPE "public"."currency" ADD VALUE 'AED'`). `ALTER TYPE ... ADD VALUE` **cannot run inside a transaction**, but drizzle-kit's `db:migrate` wraps each migration in one — so it fails there. It was applied out-of-band via **autocommit plus a manual `_journal.json` record** (the same reason the PTO `ADD VALUE`s above are worth flagging). Expect to hand-apply future enum-value additions this way.
- `pto_type`: `VACATION`, `STATUTORY_HOLIDAY`, `SICK_LEAVE`, `UNPAID_LEAVE`, `PARENTAL_LEAVE`, `BEREAVEMENT_LEAVE`, `COMPANY_RETREAT`, `RELIGIOUS_HOLIDAY`, `JURY_DUTY`, `LEAVE_OF_ABSENCE`, `OTHER_LEAVE` — **enum order matters** (it's the on-disk order). New values (`COMPANY_RETREAT`/`RELIGIOUS_HOLIDAY`, later `JURY_DUTY`/`LEAVE_OF_ABSENCE`) were inserted **before** `OTHER_LEAVE` via `ALTER TYPE ... ADD VALUE`. The `PTO_TYPE` tuple in `src/lib/staff/pto-import/types.ts` is **derived directly** from this pgEnum (`ptoTypeEnum.enumValues`) rather than hand-mirrored, so it can never drift from the schema.

**Display labels — `src/lib/staff/staff-enums.ts` (labels-only; values stay on the pgEnum).** Human-readable labels for `role`/`employment_type`/`billable_type`/`pto_type` live in one pure, client-safe module — `ROLE_LABELS`, `EMPLOYMENT_TYPE_LABELS`, `BILLABLE_TYPE_LABELS`, `PTO_TYPE_LABELS` (each `Record<enumUnion, string>`) plus the `Role`/`EmploymentType`/`BillableType`/`PtoType` union types (derived via `import type` from the schema enums). Every staff/admin render site uses these maps instead of `humanizeEnum()`, which **mangled acronyms** (`QA` → "Qa"). **Deliberate deviation from the [ADR 0016](../decisions/0016-junction-table-and-shared-enum-conventions.md) shared-enum pattern:** for these staff enums only the *labels* were extracted — the enum **value tuples stay defined inline on the `pgEnum`s in `staff-schema.ts`** (consumed elsewhere via `*.enumValues`), NOT hoisted into a standalone tuple module the way `line-of-business.ts`/`currency.ts` do it. The union types still key off the pgEnum, so a value added to the schema forces a matching label entry (type error otherwise) — no drift. The module also carries the **single source for the billable/overhead role split** (not label maps): **`NON_BILLABLE_ROLES`** (the overhead disciplines — `LEADERSHIP`, `SALES`, `SOLUTIONS`, `OPERATIONS`) plus the **`isBillableRole(role)`** predicate (role NOT in that set — i.e. Engineer/Designer/Architect/Delivery/QA bill). Both places that need the split consume it: the **CSV-import derivation** of a staff member's `isBillable` (`staff-import/transform.ts` calls `isBillableRole`, *Derivation rules* below) and the **allocations planner's** default role filter. It lives here, not in `transform.ts`, so the two can't drift. (One further code-level deviation: the hand-rolled staff filter/table selects keep a `labels` prop rather than switching to the shared `EnumSelect`, because `EnumSelect` lacks an "All" sentinel and the size/aria options those selects need.)

## Nuances / gotchas

- **Read the latest employment row.** Don't assume one row per person — query `staff_employment` ordered by `effectiveFromDate desc` (filtered to `<= today` for as-of reads) to get current facts. Inserting a new row is how you "change" someone's role/billability. The ordering itself (`effectiveFromDate desc`, then `createdAt desc` to break same-day ties) lives in **one** shared `.orderBy` fragment — `latestEmploymentFirst` in `src/lib/staff/staff-employment.ts` — spread into every latest-employment read (directory, profile, history, comp summary, bulk-edit, staff import) so it can't drift row-to-row; each call site keeps its own column projection.
- **`utilizationTarget` defaults to 100** for billable staff. Callers must set it to `0` when `isBillable` is false — the DB does not enforce that coupling.
- **PTO `isPending` defaults to `true`.** Rippling-sync inserts of already-approved leave must explicitly write `isPending: false`. Capacity/availability reads should account for pending vs. approved leave deliberately.
- **`staff.userId` is the auth link, and it's often null.** A logged-in user maps to their staff record via `staff.userId = user.id`, but the link is **null** for anyone synced from Rippling who hasn't signed in yet. Don't assume every staff row has a user (or vice versa). `email` is no longer unique, so do **not** match identity for general queries by email. (The legacy `staff_profile` example that was 1:1 with `user` has been deleted.) The **one** place email matching is allowed is the first-login auto-link below, which writes `userId` so subsequent reads go through the FK.
- **Login is gated on an active staff record with employment.** `getCurrentStaffAccess(user)` (`src/actions/staff/getCurrentStaffAccess.ts`) is the gate run by the `(app)` layout: it returns `ok` only for an `isActive` staff row that has ≥1 `staff_employment` row; `incomplete` if active-but-no-employment; `not_setup` otherwise. So a freshly synced staff row with no employment history can't get its person into the app — employment must be populated first. See the auth flow in [flows.md](../flows.md).
- **First-login auto-link (email → `userId`).** `getCurrentStaffAccess` first looks up by `staff.userId`; if none, it falls back to the active staff row matching `user.email` and writes `staff.userId = user.id`, **guarded on `userId IS NULL`** so it fires at most once and concurrent logins are safe. This is the bridge from email-synced staff to authenticated sessions; it's the only sanctioned email-based identity match.
- **A `staff` row is a tenure, not a permanent person.** Leavers are marked inactive (`isActive = false`, `terminationDate` set), never deleted. A rehire gets a **brand-new `staff` row** (new id, fresh `joinDate`, its own employment history) — we never reactivate the old one. So one human can be several staff rows over time, and there's **no cross-tenure "person" entity** linking them. Don't assume `staff` ↔ human is 1:1; queries that must follow a person across stints have to aggregate multiple rows. See [ADR 0007 — Leavers and rejoiners](../decisions/0007-staff-employment-effective-dating.md).
- **Dates/times are timezone-agnostic.** `joinDate`/`terminationDate`, `effectiveFromDate`, and PTO `startDate`/`endDate` are `date()` strings (`"YYYY-MM-DD"`); `clientIntroUpdatedAt` and other instants are `timestamp` without time zone. Do zone conversion at the UI edge only — see [`.claude/rules/database.md`](../../.claude/rules/database.md).
- **Edits are gated by RBAC (owner, or `staff.edit`) — declared in metadata, not the body.** `updateStaffLinks`/`updateStaffClientIntro`/`updateStaffResume` declare `secureActionClient.metadata({ authorize: authorizeStaffEdit })` (`src/actions/staff/canEditStaff.ts`); the `authorizeStaffEdit` hook reads `clientInput.staffId` and calls `canEditStaff` **before the body runs**: a user may always edit their **own** linked profile; editing anyone else's requires the `staff.edit` permission (manager/admin). The action bodies carry no authz call. This closed the former open-edit gap. See [permissions.md](./permissions.md) and [ADR 0014](../decisions/0014-rbac-better-auth-access-control.md).
  - **The one deliberate exception is `allocationNotes`.** `updateStaffAllocationNotes` gates on the **static `staff.edit` capability** (`metadata.permission: { staff: ["edit"] }`), **not** `authorizeStaffEdit` — so there is **no owner path**: a person cannot edit their own allocation note, only managers/admins can. These are cross-person staffing notes on a management planner, so owner-edit isn't the intent; the value is also read-gated on `staff.edit` in `getAllocationsGrid` so it never reaches an unprivileged client. **No new capability, matrix unchanged.** See [ADR 0041](../decisions/0041-allocation-notes-on-staff.md).
- **Cross-person reads are mostly unscoped; five slices are gated.** `getStaffProfile`/`History`/`Avatar`/`Projects` show other people for the directory; the `(app)` layout gate is their only boundary. The gated slices (own always visible where that makes sense) are: (1) **PTO** — another person's aggregated PTO needs `pto.review`, else `getStaffPto` returns `null` and `ProfileView` hides the section; (2) **compensation** — `canViewCompensation` (needs `staff.viewCompensation`) gates both the profile Compensation card and whether `getStaffHistory` appends comp amounts to the employment entries at all (**bonus payments ride this same gate** — `getStaffBonusHistory` calls `canViewCompensation` too, and the history feed's `BONUS` entries are dropped for an unauthorized viewer, since the fact a bonus was paid is itself compensation information); (3) **peer feedback** — `feedback.review` for someone else, the limited *recipient* tier for yourself; (4) **review notes** — the **reporting line**, not a capability; (5) **self-evaluations** — `ratings.view` for someone else, **always visible (and writable) for yourself**. All five use the same shape: **the read returns `null` and the view renders nothing** (see *Viewer-dependent tabs*). Comp lives on the same `staff_employment` row `getStaffProfile` returns, so the card gate is applied by *ProfileView not rendering the card* rather than by nulling the fields — but the history gate is a true read-side filter (client component). See [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md). **Inactive staff profiles are readable by direct `/staff/[id]` URL** (the directory hides them; the read doesn't). Consistent with the internal-only posture.
  - **The one whole-read gate is `getProfileCompleteness`** — unlike the reads above it gates the *entire* result on `staff.edit` rather than nulling a slice, because every row is about someone else and there is no own-row tier to fall back to. It also answers the "how do I add a cross-person read?" question the safe way: gate at the read *and* the route, and project derived signals rather than content. See *Profile completeness* below.
- **`getStaffDirectory` scans the whole `staff_employment` table** and reduces to latest-per-staff in JS (as do `getStaffEmploymentForEdit` and `getProfileCompleteness`, which copy the shape). Fine at company scale; if effective-dating history grows large, switch to `DISTINCT ON (staff_id)` / a lateral join. There is **no composite index on `(staff_id, effective_from_date)`** yet.

## Skills

Skills are stored **inline** on `staff.skills` (jsonb `StaffSkill[]`), not a normalized table — see [ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md) for *why* (and the tradeoffs).

- **Catalogue in code (`src/lib/staff/skills.ts`).** The single source of truth for the pickable skills — a curated catalogue of ~307 skills across **9 top-level dimensions** (`Type of Work`, `Languages`, `Frameworks`, `Hosting`, `Databases`, `DevOps & CI/CD`, `Testing`, `Tools`, `Compliance`). Several dimensions carry sub-groups in the source (e.g. `Languages` → Systems/Mobile/Web3/Functional) purely to organize it, but the picker groups **one level deep, by dimension**: `SKILL_CATEGORIES` flattens each dimension's sub-groups into a single ordered skill list (order is meaningful and preserved in the picker). Also exports `ALL_SKILLS` (the flat list for validation), the fixed 3-value `PROFICIENCY_LEVELS` (`senior`/`intermediate`/`learning`, ordered most→least) + `PROFICIENCY_LABELS`, and the `StaffSkill` type. It is **client-safe** (no `server-only` import) because it's consumed by the client picker, the server validation schema, *and* the Drizzle schema at once — same discipline as `staff-import/types.ts` and the shared CRM enum module.
- **Filter helpers (pure).** `meetsMinimumLevel(level, minimum)` — "is `level` at least as proficient as `minimum`", a `<=` compare on `PROFICIENCY_LEVELS` indices (index 0 = most proficient). `matchesSkillFilter(skills, required, minimum?)` — whether a person holds **every** skill in `required` at ≥ `minimum` (**AND** semantics); an empty `required` matches everyone, and `minimum` defaults to the lowest level (`learning`), so omitting it imposes no level constraint. These back the directory's client-side skill filter (see *Directory* under *Key flows* and [ui.md](../ui.md)); nothing queries skills server-side yet ([ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md)).
- **Read view** (`src/components/staff/skills-section.tsx`) groups a person's skills by proficiency level as badge chips inside a **Skills card** on `ProfileView` (after Résumé). Empty → "No skills yet."
- **Edit** happens on a **dedicated page** `/staff/[id]/skills` (`src/app/(app)/staff/[id]/skills/page.tsx` → `edit-skills-form.tsx`), *not* a dialog like the other profile cards (the editor is too large). The page `notFound()`s anyone who can't edit; the profile only shows its "Edit" link when `canEdit`. The editor is **level-first**: pick a target level with the "Add as" toggle (the 3 `PROFICIENCY_LEVELS`), then click skills from a **searchable catalogue of chips** (grouped one level deep by dimension, already-chosen skills hidden) to add them at that level — so a batch of same-level skills is a few clicks. Chosen skills show in a **"Your skills"** panel grouped by level, each a chip with per-chip **re-level** (▾ dropdown) and **remove** (✕). Adds **dedup by name** (`chosen` set); the schema caps the list at **200 skills**. Save calls `updateStaffSkills` then returns to the profile.
  - **Two-panel layout (`edit-skills-form.tsx`).** On desktop (≥ md) it's a 2-column grid: the "Add skills" editor is the **left** column and "Your skills" is the **right** (via `order` utilities), so it reads left→right as cause→effect. The "Your skills" column is **`sticky top-6`** with its own max-height/overflow so added skills are seen landing while the long catalogue column scrolls with the page. Inside the editor, the "Add as" toggle + search box are **`sticky top-0`** (pinned while the catalogue scrolls beneath); Save/Cancel are a **`sticky bottom-0`** right-aligned action bar (Save last) so they're always reachable. On narrow screens (< md) it collapses to a single stack with "Your skills" **first**, then the editor. The page container is `max-w-5xl` (widened from `max-w-3xl`) to fit two columns.
- **Mutation** `updateStaffSkills` (`src/actions/staff/updateStaffSkills.ts`, schema in `updateStaffSkills.schema.ts`) **replaces the whole list** (stamping `skillsUpdatedAt` in the same `set`, like `updateStaffResume` does for its date) and reuses the existing `authorizeStaffEdit` hook / `staff.edit` capability (own always; others need `staff.edit`) — **no new permission was added, the RBAC matrix is unchanged**. The schema validates every name is in `ALL_SKILLS` and rejects duplicates (guards against a crafted payload since the client only ever picks from the catalogue). `getStaffProfile` projects `skills` and `StaffProfile.skills: StaffSkill[]`.

## Viewer-dependent tabs — Peer feedback + Review notes + Self-evaluations

**The profile's tab set is no longer fixed: it renders 5 to 8 tabs depending on who is
looking.** The fixed four are Overview / Manual of Me / Ways of Working / Resume, plus
History last; **three tabs in between are owned by the
[performance domain](./performance.md)** and appear **only when their read returned
something this viewer may see** — `ProfileView` takes `feedback: StaffFeedbackView | null`,
`reviewNotes: StaffReviewNotesView | null` and
`selfEvaluations: StaffSelfEvaluationsView | null` and renders each (in that order, before
History) iff non-null. **The reads are the gate; the component just hides the section** —
the same posture as `pto`. A `null` also means the *trigger* isn't rendered, so a tab's
presence never discloses that feedback, notes or self-evaluations exist about someone.

- **Peer feedback** — `getFeedbackAboutStaff` (`src/actions/feedback/`): the limited
  **recipient** tier on your own profile (self branch first, even for a
  `feedback.review` holder), **full content** for a `feedback.review` holder looking at
  someone else, `null` otherwise. Panel: `staff-feedback-panel.tsx`. See
  [ADR 0050](../decisions/0050-profile-peer-feedback-tab.md).
- **Review notes** — `getStaffReviewNotes` (`src/actions/performance/`): the **only**
  surface in the app gated on the **reporting line** rather than a capability — the
  person's current manager (or an admin) sees everything incl. drafts and can write; the
  **subject** sees `SHARED` notes only; a manager who **moved teams** sees just what they
  authored. Apart from `admin`, **every** path requires an **active** linked staff member
  — a terminated person's session outlives both the stale `managerId` still pointing at
  their old reports *and* their authorship of past notes, so leaving revokes access where
  changing teams doesn't. Panel:
  `review-notes-panel.tsx` (one of the profile's two *writable* performance surfaces). See
  [ADR 0049](../decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)
  and [permissions.md](./permissions.md).
- **Self-evaluations** — `getStaffSelfEvaluations` (`src/actions/performance/`): the
  person's own dated reflection questionnaires. **Own always (read *and* write); anyone
  else's needs `ratings.view`** and is read-only; `null` otherwise. **The only tab where
  being the subject is the *widest* answer**, not the narrowest — so the read checks self
  **first**, because that's what decides the write affordances. Writes are **author-only,
  with no capability path and no admin override**. Panel:
  `self-evaluation-panel.tsx` (the profile's other writable performance surface — and the
  only one a non-manager can write). **Note the neighbourly hazard:** this reuses the
  `ratings.view` capability that also guards the manager-assigned L0–L4 level a staffer
  must never see about themselves, so **nothing in this tab may render such a level**
  ([ADR 0032](../decisions/0032-staff-rating-levels-effective-dated-manager-only.md),
  [ADR 0058](../decisions/0058-self-evaluations-dated-records-with-snapshotted-answers.md)).

**Both pages wire all three, and `/profile` deliberately does not hard-code them.** It
hard-codes `canEdit = true` and `canViewCompensation = true` (it's your own record), but
passes the *reads'* answers for these three — because for two of them "it's your profile"
is exactly the case that must yield the **narrower** result (the recipient feedback tier;
only the notes your manager has *shared* — a person is never their own note-manager),
while for self-evaluations it's the **widest**. Passing the read's answer is right either
way, which is the point: **the read decides, never the page.**

**Consequences for anything keying off the tab set** (deep links, tests, snapshots): it
must tolerate 5–8 tabs. Tab state is uncontrolled and not in the URL, matching
`/feedback`.

> **Fixed in passing:** `EditResumeDialog` was rendered **unconditionally** on the Resume
> tab while every other profile section guards on `canEdit` — so a viewer of anyone's
> profile saw an Edit button whose write would (correctly) fail at
> `authorizeStaffEdit`. It is now `canEdit`-guarded like the rest. The server gate was
> never the problem; the affordance was.

## Org chart (`/staff?view=org`)

**`/staff` is two views of one read.** A link-based Directory | Org chart toggle
(`staff-view-toggle.tsx`, a server component using `buildListHref`, mirroring the
opportunities board/list switch) puts the choice in the URL; `?view=` is the **only**
`/staff` search param, and an unknown value falls back to the directory. Everything
*inside* each view still filters in memory. See [ADR 0054](../decisions/0054-staff-org-chart-dom-tree.md)
for the *why* on every point below, and [ui.md](../ui.md) for the rendering technique.

- **It reads the reporting line from `getStaffDirectory`, not a new read.** That action
  gained **`managerId`** on `StaffDirectoryEntry`; the grid ignores it. One read and one
  entry type keep "line of business = Fintech" meaning the same people in both views and
  stop a second copy of the two-query + `latestEmploymentFirst` shape from drifting. **If
  you add a `/staff` view, extend this read — don't fork it.**
- **The tree is built defensively, in a pure module** — `src/lib/staff/org-chart.ts`
  (client-importable, no `db`/`server-only`). `buildOrgForest` normalises a
  self-reference, a dangling `managerId` and a cycle (cut iteratively, one edge per loop)
  into **roots carrying an `OrgRootReason`**, and guarantees **every input row appears
  exactly once** whatever the edges do. That contract exists because `managerId` has no DB
  cycle/self guard and the importer only warns (see *Manager resolution* above,
  [ADR 0026](../decisions/0026-staff-manager-self-reference.md)) — this is the app's
  standing "every consumer guards itself" rule, discharged once.
  `src/lib/staff/org-chart.test.ts` (25 tests) pins it — a **deliberate carve-out** of
  [ADR 0037](../decisions/0037-unit-tests-removed-except-rbac-matrix.md), not a return to
  broad unit testing.
- **It is the only surface that shows a malformed reporting edge** — *Reports to self* /
  *Manager not listed* / *Reporting loop* badges. Nothing else in the app ever displayed
  the importer's warnings, so a bad CSV was previously invisible after commit.
- **Filters prune to matches plus their ancestor chain.** A non-matching node survives if
  a descendant matched, flagged `passThrough`, and renders faded with an `sr-only` note.
  `descendantCount` is recomputed over the *surviving* subtree so a `+N` badge counts what
  you'd actually hide, and the toolbar count uses **`countOrgMatches`** (non-`passThrough`
  nodes only) — otherwise narrowing to one person would read "showing 6 of 42".
- **While a filter is active the whole pruned tree renders expanded, with no disclosure
  controls** (and Expand all / Collapse all are hidden, since they'd visibly do nothing).
  Not a heuristic: the prune leaves only matches and the chains to them, so any surviving
  node with reports necessarily has a match beneath it. Force-expanding only
  `passThrough` nodes was the buggy first cut — a *matching* wide manager seeded collapsed
  by the width rule answered "Role = Engineer" with a `+20` badge and no engineers.
  **Derived at render, never stored:** clearing the filter restores the user's own collapse
  state. **`showInactive` is deliberately excluded from "a filter is active"** — hiding
  departed staff is the baseline view, not a narrowing the user asked for; counting it
  would force the tree open on first load and make collapse unreachable.
- **"Show inactive" is a prune predicate, not a pre-filter.** The forest is always built
  from **all** entries; dropping inactive people from the *input* would turn an inactive
  manager into a missing parent and detach her whole subtree to the top level. Test-pinned
  — don't "optimise" it into a pre-filter.
- **Read-only, and deliberately so.** `managerId` stays import-only: an in-app editor
  would be a **permission-granting** write, because the reporting line gates review-note
  access ([ADR 0049](../decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)).
- **No new permission surface, no migration.** Clicking a node opens the existing
  `StaffProfileDrawer` (below), which gates comp / PTO / feedback / review notes /
  rating history server-side; `staffRating.level` is never fetched by this read, so
  `ratings.view` can't be sidestepped by rendering a chart instead of a profile.

## The read-only profile drawer (`StaffProfileDrawer`)

`src/components/staff/staff-profile-drawer.tsx` — a **read-only review pane** for one
staff member, opened from a row elsewhere so a reviewer keeps their place in a list.
**Two hosts today** — the compensation-plan editor (clicking a person's name in a plan
row — see [performance.md](./performance.md)) and the **org chart** (clicking a node — see
above), which is what its plan-agnostic design was for.

- Built on the vendored `Sheet`, following the CRM **opportunity detail sheet**: load
  on open through an action, `sm:max-w-[56rem]`. **Three to nine tabs** — **Overview**,
  **Projects**, *(**Time off**)*, *(**Peer feedback**)*, *(**Review notes**)*,
  *(**Self-evaluations**)*, *(**Evaluations**)*, *(**Bonuses**)*, **History** — the six
  parenthesised ones conditional on their read exactly as on the profile, History always
  present and rendered last (same order as `ProfileView`). **Bonuses** (`BonusList` over
  `getStaffBonusHistory`) is a **drawer-only** surface like Evaluations, on the comp gate
  (own always visible), and shows per-currency YTD totals with **no FX** — summing CAD and
  USD for one person would be a made-up number. **Self-evaluations (the person's own words)
  and Evaluations (the level a manager assigned them) are different things on different
  scales and stay separate tabs**
  — see [ADR 0032](../decisions/0032-staff-rating-levels-effective-dated-manager-only.md)
  and [ADR 0058](../decisions/0058-self-evaluations-dated-records-with-snapshotted-answers.md).
  **Projects, Time off, Bonuses and Evaluations are tabs, not Overview sections**,
  because each is a history in its own right and a review pane is read a tab at a time.
  Overview stacks: a 3-column facts grid
  (**Location / Joined / Reports to** — no email; it was dropped) → **Compensation** →
  Skills → Client intro. The header shows the name plus a four-facet employment line (role · line
  of business · employment type · billable), and **falls back to nothing** when there's no
  employment row. It links out to `/staff/[id]` ("Open full profile") for anything
  editable.
- **It is not a cut-down payload any more — it's a *gated* one.** Comp, bonus payments,
  PTO, feedback, review notes, self-evaluations and rating history are all present **for a
  viewer entitled to them**, and
  the drawer now reaches near-parity with the profile page's read-only content. What it
  deliberately still lacks is every *edit* affordance (bar review notes) and the
  avatar/links rail.
- **The Evaluations tab is the drawer's one piece of genuinely new surface**, not a reused
  profile section: `EvaluationHistory` over `getStaffEvaluationHistory` renders **one
  person's whole dated `staff_rating` history** (level + subratings + who saved it, newest
  first), where the levels dashboards only ever read the *latest* row across *everyone*.
  It carries the **strictest gate in the drawer — `ratings.view`, manager/admin, with no
  owner path at all** ([ADR 0032](../decisions/0032-staff-rating-levels-effective-dated-manager-only.md)):
  unlike comp (own always visible) and feedback (a limited recipient tier), there is no
  self tier to degrade to, so a staffer sees no tab. Note the known, *inherited* wrinkle: a
  capability holder can see **their own** history here, exactly as they already can in the
  `/people/levels` grid — excluding self would diverge from that grid for no real
  gain.
- **The one interactive surface is Review notes**, deliberately: that's where the review
  conversation actually gets written up, so making it read-only would defeat the drawer's
  purpose. It passes `onChanged` so the drawer **re-loads itself** instead of calling
  `router.refresh()` — refreshing the route would re-render the plan editor underneath,
  mid-edit.
- **Self-evaluations render `readOnly` here, and that's a *display* constraint, not a
  gate.** The panel would otherwise offer writes to a viewer who happens to be looking at
  their own profile in the drawer — but a seven-textarea form inside a 56rem sheet layered
  over a mid-edit plan editor is the wrong place to write one, so the drawer passes
  `readOnly` and the header's "Open full profile" is the route to actually writing.
  **The server gate is untouched** (`authorizeSelfEvaluationMutate` still decides), and the
  rejected alternative — forcing `canCreate: false` inside `loadStaffProfileDrawer` — would
  have buried a presentation decision inside a permission answer. Copy this split if a
  future host needs to suppress an affordance it is entitled to.
- **Loader: `src/actions/staff/loadStaffProfileDrawer.ts`** — a `"use server"` +
  `secureActionClient` **interactive read** (the documented exception to the
  server-only-read rule, same shape as `loadOpportunityDetail`;
  [ADR 0010](../decisions/0010-actions-layer-owns-db-access.md)). Two load-bearing
  details, both worth copying:
  - **Every sensitive field is gated at the read, and the payload spells out its own
    shape rather than passing `StaffProfile` through.** That is the reason the type exists,
    and it got *more* load-bearing when comp was added, not less: `getStaffProfile` carries
    comp amounts inline on `employment`, and a server-rendered page may hand a component
    amounts it chooses not to render — a **client-fetched** drawer would **ship them in its
    response** whether or not it rendered them. So the projection splits `employment` into
    money-free **facets** plus a separate **`compensation`** object built only when
    `canViewCompensation(ctx.user, staffId)` passed (own comp always; anyone else's needs
    `staff.viewCompensation`), and `pto` is `getStaffPto`'s own self-gated result.
    **Minimise in the projection, never in the JSX.**
  - **`null` means "not permitted", never "none on file".** The two must not be conflated,
    because `CompensationSection` renders its own *"No compensation on file."* for the
    latter — so a `null` that meant "empty" would silently misreport a gate as an absence.
    The drawer therefore omits the whole section when the field is `null`.
  - **`history` is fetched sequentially, after the `Promise.all`** — `getStaffHistory`
    folds comp amounts into its employment entries, so it can't run until the comp gate is
    known. Same ordering `/staff/[id]` uses, and the reason this read isn't fully parallel.
    (Don't "optimise" it into the `Promise.all`; the gate is an input.)
  - **It requires an *active linked staff row*, not merely a session** —
    `ownStaffId(ctx.user.id, { activeOnly: true })`, else `null`. Sign-in is Google but
    **not domain-restricted**, so a valid session can belong to someone who isn't staff;
    and a **terminated** person's session outlives their employment. `/staff/[id]` is
    protected by the `(app)` layout, which refuses both — but **an action has no layout
    above it** and must refuse them itself. The review-note gate makes the same choice for
    the same reason; see [permissions.md](./permissions.md) → *Resolving the caller*.
  - No capability gate on the *action* otherwise, matching `/staff/[id]` — **seven
    sensitive slices each carry their own gate and return `null` rather than throwing**
    (comp → `canViewCompensation`; bonus history → the same `canViewCompensation`; PTO →
    `pto.review`; feedback → `feedback.review` or the
    recipient tier; review notes → the reporting line; rating history → `ratings.view`,
    no owner path; **self-evaluations → `ratings.view` *with* a full owner path**), so one
    viewer's drawer simply has fewer sections and tabs than another's. The gate table in
    [permissions.md](./permissions.md) enumerates all seven — it is the best worked example
    of this model in the codebase.

## Manual of Me

A short **survey** a person fills out on their profile — 7 free-text prompts ("The basics you should know about me are…", "What helps me thrive at work…", how to give them feedback, etc.) so teammates and managers can work with them well. It is the **first consumer of the generic `responses` table** (Ways of Working, below, is the second) — see [ADR 0028](../decisions/0028-generic-responses-table-app-validated-question-ids.md) for *why* one generic table with app-validated question ids (not per-survey tables / a pgEnum).

- **Source of truth in code (`src/lib/staff/manual-of-me.ts`).** A pure, client-importable module (no `db`/drizzle) exporting `MANUAL_OF_ME_QUESTION_IDS` (7 ids, canonical **display order**), `MANUAL_OF_ME_QUESTIONS` (id/title/subtitle/`type: "text"`), and the `manualOfMeQuestionId` zod enum. Same single-source pattern as `@/lib/staff/skills` / `@/lib/crm/line-of-business`: one module feeds the read, the write schema, and the UI. Ways of Working (below) is the follow-on survey that did exactly this — its own defs module reusing `responses` + `upsertResponse`.
- **Storage grain = current value, keyed by `(staffId, questionId)`.** Answers live in the generic `responses` table (`textResponse` only for this survey), one **upsert** row per question — *not* append-only history. An unanswered question has **no row**; clearing an answer sends `"" → null` and keeps the row. See the `responses` entity in [data-model.md](../data-model.md).
- **Read — not ownership-scoped (`getManualOfMe`).** `src/actions/responses/getManualOfMe.ts` (server-only, `React.cache`) returns **all 7** questions in canonical order with the person's `textResponse` merged in (null if unanswered). Like `getStaffProfile`, it's visible to **any profile viewer** — the `(app)` layout is the only boundary (same posture as the Client intro), so both `/profile` (own) and `/staff/[id]` (others) load it and pass `manualOfMe` to `ProfileView`.
- **Write — reuses `authorizeStaffEdit` (no new permission).** `src/actions/responses/upsertResponse.ts` (`secureActionClient`, `metadata({ authorize: authorizeStaffEdit })`) upserts one answer via `onConflictDoUpdate` on `(staffId, questionId)`; `upsertResponse.schema.ts` validates `questionId` against `manualOfMeQuestionId` (so a crafted id can't write an arbitrary row) and caps `textResponse` at 10,000 chars. Gate is the **same** as every other profile-field edit — own profile always, others need `staff.edit`; **the RBAC matrix is unchanged**. Revalidates `/profile` and `/staff/${staffId}`.
- **Read view on the profile.** A "Manual of Me" card in `ProfileView` (`src/components/staff/manual-of-me-section.tsx`) shows only the **answered** questions (empty state otherwise) plus an "N of 7 answered" line; the "Edit"/"Fill out" link (to the editor page) renders only when `canEdit`.
- **Edit — a dedicated guided page** `/staff/[id]/manual-of-me` (`src/app/(app)/staff/[id]/manual-of-me/page.tsx`, mirrors the skills editor: `notFound()`s any viewer failing `canEditStaff`, since the write action is the real boundary). It renders `src/components/staff/manual-of-me-guide.tsx` — a **one-question-at-a-time** flow with a clickable step rail, **per-question autosave** (on blur, debounced typing ~800 ms, and on navigation/unmount), a subtle inline save indicator (never a toast), and a **"Done"** that flushes and returns to the profile. There is **no big Submit** — deliberately, so a person can answer in any order and come back later (several prompts invite that). **The autosave engine is now the shared `use-response-autosave.ts` hook** (see *Ways of Working* below) — extracted out of this guide so both surveys share one save-queue, and itself now sitting on the app-wide `src/hooks/use-autosave-queue.ts`; the `SaveIndicator` lives in `src/components/form/save-indicator.tsx` (re-exported by `response-save-indicator.tsx`).

## Ways of Working

A second, larger **profile survey** — "Ways of Working" (WOW) — capturing *how* a person likes to work: the editors/tools they reach for, how they learn, and a detailed look at how they use AI (kinds of work, tools, problems, confidence, output kept, plus a seven-question engineering-workflow deep dive). It is the **second consumer of the generic `responses` table**, added exactly as [ADR 0028](../decisions/0028-generic-responses-table-app-validated-question-ids.md) anticipated: a **code-only change, no migration** — the `responses` columns (`textResponse`, `listResponse`, `jsonResponse`) already existed. It mirrors Manual of Me's structure but is richer (multi-selects, single-selects, and a matrix — not just free text).

- **Source of truth in code (`src/lib/staff/ways-of-working.ts`).** A pure, client-importable module (no `db`/drizzle) exporting the option lists (IDEs, learning sources, AI types-of-work / tools / problems, the two confidence scales, output percentages, the seven engineering-workflow questions), `WAYS_OF_WORKING_QUESTION_IDS` (**30** `WOW_`-prefixed ids in canonical order), the `waysOfWorkingQuestionId` zod enum, the `WOW_SECTIONS` **discriminated union** (8 editor sections; `kind` ∈ `multiselect`/`text`/`single-select`/`matrix`) that drives both the editor and the read view, and `WOW_LIST_QUESTION_IDS` (**derived from `WOW_SECTIONS`**, so it can't drift). Same single-source discipline as `@/lib/staff/manual-of-me`.
- **One response shape per question — `textResponse` XOR `listResponse`.** Free-text and single-select answers use **`textResponse`**; multi-selects and each of the six AI-matrix buckets use **`listResponse`** (jsonb `string[]`). `WOW_LIST_QUESTION_IDS` is the membership test. `upsertResponse` writes the used column and **nulls the other**, so a row is never double-shaped.
- **The AI usage/savings matrix is stored as six lists per matrix, reconstructed on read.** Each matrix section (Types of Work, Tools) tags every item with a **usage tier** (critical / common / avoid) *and* a **savings tier** (major / minor / no) — but there is no per-item row. Instead each tier is its own `listResponse` question id (e.g. `WOW_CRITICAL_TYPE_OF_WORK`, `WOW_MAJOR_SAVINGS_TOOL`, …), holding the list of items in that bucket. `ways-of-working-section.tsx` (and the editor) **reconstruct** an item's usage/savings by looking it up across those six lists. That's why a matrix contributes **six** question ids to the 30.
- **Read — not ownership-scoped (`getWaysOfWorking`).** `src/actions/responses/getWaysOfWorking.ts` (server-only, `React.cache`) returns a `Record<WowQuestionId, { textResponse, listResponse }>` (every id present; unanswered → both null) plus `answeredCount`/`totalCount`. **`answeredCount` uses the shared `isResponseAnswered` predicate** (`src/lib/staff/survey-answers.ts`) — see *One definition of "answered"* below. Like `getManualOfMe`/`getStaffProfile`, visible to **any profile viewer** — the `(app)` layout is the only boundary — so both `/profile` and `/staff/[id]` load it and pass `waysOfWorking` to `ProfileView`.
- **Write — the same `upsertResponse` + `authorizeStaffEdit`, no new permission.** WOW answers go through the **same** widened `upsertResponse` action as Manual of Me (`questionId` validated against `z.union([manualOfMeQuestionId, waysOfWorkingQuestionId])`; `listResponse` capped at 200 items × 200 chars). Gate is unchanged — own profile always, others need `staff.edit`; **the RBAC matrix is untouched**. Revalidates `/profile` and `/staff/${staffId}`.
- **Read view on the profile.** A "Ways of Working" **tab** in `ProfileView` (`src/components/staff/ways-of-working-section.tsx`) renders only the **answered** fields (untouched fields and whole untouched sections are dropped) with an "N of 30 answered" line; the "Edit"/"Fill out" link renders only when `canEdit`.
- **Edit — a dedicated guided page** `/staff/[id]/ways-of-working` (`src/app/(app)/staff/[id]/ways-of-working/page.tsx`, mirrors the Manual of Me / skills editors: `notFound()`s any viewer failing `canEditStaff`). It renders `src/components/staff/ways-of-working-guide.tsx` — a **one-section-per-step** flow (step rail) with multiselect pills, single-select dropdowns, textareas, and the usage/savings matrix grid, every field autosaving independently and a **"Done"** that flushes and returns. **No big Submit** — same rationale as Manual of Me, and more important here given the length.
- **Survey autosave hook (`src/components/staff/use-response-autosave.ts`).** Extracted from the Manual of Me guide so both surveys share one save-queue keyed by `questionId`. It handles **both** value shapes (`string` and `string[]`, inferring which `responses` column to write), debounces typing (~800 ms), and force-saves on blur/navigation/unmount/Done. **The queue machinery itself is no longer here** — the dirty-set, per-key debounce and single-flight drain loop were extracted again into the generic **`src/hooks/use-autosave-queue.ts`** once the compensation-plan editor became a second consumer; this hook now just supplies `save(questionId)` and the survey-specific value handling. Behaviour is unchanged: an edit landing mid-save re-queues its field, a failed save re-queues and stops (a later edit retries), the per-field "saved" indicator only lights when the field is genuinely clean (so typing through a save never shows a stale ✓), and `flushAll` returns `false` if any save failed so a caller can refuse to navigate away from unsaved work. See [ui.md](../ui.md) → *Shared autosave engine*. `SaveIndicator` + `aggregateSaveState` now live in **`src/components/form/save-indicator.tsx`**; `src/components/staff/response-save-indicator.tsx` is a **re-export shim** kept for the existing import path.

### One definition of "answered" — `src/lib/staff/survey-answers.ts`

A pure, client-importable module exporting **`isResponseAnswered({ textResponse, listResponse })`** (plus the structural `SurveyAnswerShape`) — the single definition of "this survey question has been answered", shared by **every** reader of the generic `responses` table.

It exists because the two readers **disagreed**: `getWaysOfWorking` counted an answer as given when `textResponse` was non-null **or** `listResponse` was non-empty, while `profile-view.tsx` tested `textResponse` alone — so a person whose only answers were multi-selects counted as answered in one place and unanswered in the other. `getWaysOfWorking` now imports the predicate; so does the profile-completeness read. An **empty `listResponse` is not an answer**: clearing every option leaves the row behind with `[]`, and counting that would report a cleared question as still answered. **Any new survey reader must use this rather than re-testing the columns.**

## Profile completeness (`/reporting/profile-completeness`)

A **read-only table, one row per staff member**, showing which self-service profile artefacts each person has filled in — so whoever chases profile completion can see who's still outstanding. It sits under **Reporting** in the nav (the one entry there owned by this domain, not performance, and the section's only *named per-person* read — it belongs there because nothing in it writes, which is Reporting's axis: [ADR 0055](../decisions/0055-nav-dashboards-vs-people-management.md), 2026-08-03 amendment). It is the roll-up view over everything in the sections above.

It lived at `/people/profile-completeness` under **People management** until 2026-08-03; the old path **does not redirect**. The move changed no gate and no read — but it did change *who can reach it from the sidebar*: under the `ratings.edit`-gated People-management parent, a `staff.edit`-only holder was hidden from a page they were allowed to open; under the ungated Reporting parent the nav matches the page's gate. (`ratings.edit` and `staff.edit` have identical role rows today, so no real audience changed.)

Columns: **Person** (links to `/staff/[id]`) · Line of business · Role · Type · **Links** (n/3 — LinkedIn/GitHub/portfolio) · **Résumé** (✓/—) · **Skills** (count) · **Skills updated** · **Client intro** (✓/—) · **Intro updated** · **Manual of Me** (n/7) · **Ways of working** (n/30). The two date columns are the **first readers** of `skillsUpdatedAt` and `clientIntroUpdatedAt` — before this, both were written and nothing displayed them.

- **The gate is the existing `staff.edit` capability — no new capability, the RBAC matrix is unchanged.** Chasing profile completion is the job of the people who may edit those profiles ({manager, admin}). It's exported once as **`PROFILE_COMPLETENESS_ACCESS`** from the pure module `src/lib/staff/profile-completeness.ts` so the route, the nav entry and the read can't drift — the same shape as `BONUS_PAYMENT_WRITE_ACCESS` / `COMPENSATION_PLAN_ACCESS`. The page `notFound()`s (probe-proof), and **`getProfileCompleteness` re-checks with `requirePermission` in its own right** — an action has no layout above it, and this is a cross-person management read. Like `allocationNotes`, this is a `staff.edit` surface with **no owner path**; unlike it, there's nothing to own — it's a view of everyone. See [permissions.md](./permissions.md).
- **It ships presence, not content.** Résumé and client-intro *presence* is computed **in SQL** (`(col is not null and btrim(col) <> '')`), links are counted in SQL, skills via `jsonb_array_length` — so the free text a manager has no need to receive **never reaches the client**, only booleans, counts and dates. Same "minimise in the projection, never in the JSX" discipline as `loadStaffProfileDrawer`. If you add a column here, add it as a derived signal, not a raw field.
- **Read: `src/actions/staff/getProfileCompleteness.ts`** (`server-only` plain async function — no `secureActionClient`, it's an SSR read). **Three queries:** the `staff` projection above; the whole `staff_employment` table reduced latest-per-staff with the shared `latestEmploymentFirst` + `firstPerKey`, exactly as `getStaffDirectory` does (same whole-table-scan tradeoff — see *Nuances*); and one pass over `responses` filtered to both surveys' question-id tuples, **counted in JS** so the count uses the same `isResponseAnswered` as the per-person reads. If `responses` outgrows a scan, aggregate with a `GROUP BY` — but keep one definition of "answered".
- **Denominators come from the id tuples.** `PROFILE_COMPLETENESS_TOTALS` (in the same pure module) derives `manualOfMe`/`waysOfWorking` from `MANUAL_OF_ME_QUESTION_IDS`/`WAYS_OF_WORKING_QUESTION_IDS`, so adding a survey question moves "14 of 30" with no second edit. Only `links: 3` is a literal (three named columns, not a list).
- **Inactive staff are included in the read**; "show inactive" is a UI toggle, matching `getStaffDirectory`. Employment fields are `null` for a staff row with no employment history, and the row still lists.
- **Filtering and sorting are both in-memory, client-side, nothing in the URL** — name search, line of business, role, employment type, show-inactive — matching the staff directory and the other staff tables. Every completeness column sorts **ascending on first click**, deliberately: zeros and never-updated dates first is the "who still needs chasing" order — which is why the two date columns sort a `null` as **`0` (the oldest)** rather than using TanStack's `sortUndefined` (see the gotcha in [ui.md](../ui.md)), while the enum columns keep `sortUndefined: "last"` because there a null really is *absent*. `showInactive` is excluded from "a filter is active" (so it doesn't light up *Clear filters*), the same call the org chart makes. See [ui.md](../ui.md) for the table component and its cell conventions.

## Admin tooling (localhost-only)

This domain is populated and maintained by **local-only** tools in the `admin` area (outside `(app)`, gated on a loopback host): two CSV importers — `/admin/upload-staff` (people) and `/admin/upload-pto` (leave) — and a **bulk employment editor** (`/admin/bulk-edit-roles`). They live outside `(app)` precisely because importing *creates* the staff records the `(app)` layout gates on — see [architecture.md](../architecture.md) (Admin area, [ADR 0008](../decisions/0008-localhost-only-admin-area.md)) and [flows.md](../flows.md) for the gating rationale and end-to-end steps. The importers follow the same shape: pure client transform → server `compute*Plan` diff → preview tables → commit action that **recomputes the plan server-side** and applies it in one transaction (`publicActionClient` + `assertLocalhost()`, never `secureActionClient`).

### Staff import (`/admin/upload-staff`)

Ingests a [Rippling](https://rippling.com) employee export into `staff` + `staff_employment`. The enum tuples the transform validates against (`LINE_OF_BUSINESS`/`ROLE`/`EMPLOYMENT_TYPE`) are **derived directly** from the pgEnums in `staff-schema.ts` (`*.enumValues`) in `src/lib/staff/staff-import/types.ts`, not hand-copied, so they can never drift from the schema.

Code: client `src/components/admin/staff-import.tsx` (PapaParse + preview tables); pure transform `src/lib/staff/staff-import/transform.ts`; server diff `src/lib/staff/staff-import/plan.ts`; shared types/zod `src/lib/staff/staff-import/types.ts`; actions `src/actions/admin/{previewStaffImport,commitStaffImport}.ts` (both `publicActionClient` + `assertLocalhost()` — local seeding must not require auth/staff).

### CSV column mapping

`Employee - ID`→`ripplingId`, `Employee`→`name`, `Work email`→`email`, `Start date`→`joinDate`, `Last day of work`→`terminationDate`, **`Manager - Work email`**→`managerEmail` (resolved to `managerId` at commit — see *Manager resolution* below). **Compensation:** `Annual base remuneration`→`base`, `Hourly Rate`→`hourlyRate`, `Target annual bonus`→`guaranteedBonus`, `Compensation currency`→`currency` (one-off bonuses are **not** part of this import at all — they live in `staff_bonus_payment`). Column lookup is whitespace/case-tolerant; dates accept ISO (`YYYY-MM-DD`) or US (`M/D/YYYY`), blank → null; money cells go through `parseNumber` (`src/lib/import/csv-import/parse.ts`) which strips currency symbols/separators and yields `null` on blank/unparseable/negative. A row missing any of id/name/email, with an unparseable *date*, **or missing a required comp value** (`base`/`hourlyRate`/`currency`) is **skipped** (surfaced, never persisted) under "Missing/invalid compensation: …". Note: because **both** `base` and `hourlyRate` are required, a row supplying only one of them is skipped. **`Target annual bonus` (`guaranteedBonus`) is the exception — it's optional:** a blank/whitespace-only cell defaults to `0` and the row is kept; only a *present-but-unparseable* value (parses to `null`) skips the row.

### Derivation rules (the non-obvious nuance — keep in sync with `transform.ts`)

- **`lineOfBusiness`:** Department=="Design" → `DESIGN`; else first match in Teams: core→`CORE`, commerce→`COMMERCE`, corporate→`CORPORATE`, fintech/crypto→`FINTECH`. **Unmappable → row skipped.**
- **`role`** (first match wins): Dept Design→`DESIGNER`; Dept Talent→`OPERATIONS`; Dept Sales→`SALES`; Dept Solutioning→`SOLUTIONS`; Title contains Delivery→`DELIVERY`; Architect→`ARCHITECT`; QA→`QA`; Engineer→`ENGINEER`; else `OPERATIONS`.
- **`employmentType`:** "Employment type name" contains "Hourly" → `HOURLY`, else `FULL_TIME`.
- **`isActive`** = no `terminationDate`. **`isBillable`** = **`isBillableRole(role)`** (role NOT in `NON_BILLABLE_ROLES` = {LEADERSHIP, SALES, SOLUTIONS, OPERATIONS}) — the transform imports the predicate from `staff-enums.ts` rather than defining its own set, so the overhead split is single-sourced (see the *Display labels* note above). **`utilizationTarget`** = `isBillable ? 100 : 0` — the non-billable ⇒ 0 coupling runs through `normalizeEmploymentFacts` in the shared `src/lib/staff/employment.ts`, the single home for the billability invariants (see *Bulk edit roles* below).
- **`isManagement` and `billableType` are never derived.** The transform doesn't set them; the commit **carries forward** the existing row's `isManagement` and `billableType` when writing a new effective-dated row (defaulting to `false`/`HUB` for brand-new people), so a re-sync never resets an in-app management flag or knocks a `GLOBAL` person back to `HUB`. (`LEADERSHIP` roles are likewise import-preserved — `plan.ts` keeps a person already in `LEADERSHIP` in that role rather than overwriting from the CSV-derived role.)
- **Compensation is required (except guaranteed bonus), not carried forward.** The transform reads the comp cells (`parseNumber`/`normalizeCurrency`) and **skips any row missing `base`/`hourlyRate`/`currency`** (see column map above); **`guaranteedBonus` is optional — a blank cell defaults to `0`** (a present-but-unparseable value still skips the row). So every surviving row already carries full comp, and `computeImportPlan` (`plan.ts`) diffs it straight from `incoming` with **no overlay from the current record**. A comp field counts as "changed" (→ new effective-dated row) whenever the CSV's value differs from the stored one. (Carry-forward survives only in **bulk-edit** — see below — where comp genuinely isn't part of the edit.)

### Manager resolution (`Manager - Work email` → `managerId`) — see [ADR 0026](../decisions/0026-staff-manager-self-reference.md)

The manager is named by **email** but people are matched by `ripplingId`, and `email` is **not unique** on `staff` — so the manager is carried through the pipeline as a **stable manager `ripplingId` reference**, resolved to a concrete `staff.id` only at commit (when create-ids exist). Pure logic lives in `src/lib/staff/staff-import/managers.ts` (`MANAGER_EMAIL_HEADER`, `buildManagerEmailIndex`, `resolveManager`); `transform.ts` extracts `managerEmail` onto `NormalizedStaff`.

- **Two-pass email index (`plan.ts`).** `computeImportPlan` builds `email → ripplingId(s)` from **the incoming batch first, then the DB**: the batch covers a full-org / first import (the manager is a create in the same file), the DB lookup covers a partial import (the manager lives only in the DB). It also loads each matched person's *current* manager as a ripplingId so a manager change is detectable.
- **Manager change is an update.** The manager is a `staff` identity fact but is **not** in the `ComparableField` tuples (the compared value is a resolved ripplingId, not the raw email); it's tracked on its own `managerChanged` flag, and a **manager-only change counts as an update** (shown as a "manager changed" badge in the preview).
- **Three-state rule — blank clears; unresolvable/absent preserve.** `transform.ts` detects whether the CSV even has the `Manager - Work email` column and encodes three states on `managerEmail`, which `plan.ts` honours per existing person (a brand-new person has nothing to preserve, so it just takes the resolved manager, i.e. `null` when blank/unresolvable):
  - **filled + resolves** (`string`) → set/update the manager;
  - **column present + cell blank** (`null`) → **clear** the manager (`managerId = null`) — the *only* case that wipes a link, and it's authoritative;
  - **column entirely absent** (`undefined`) → the import carries **no** manager info, so **every existing link is preserved** (no resolution is even attempted). This is the fix for the old bug where an absent column read as "everyone blank" and wiped every manager.
- **Filled-but-unresolvable PRESERVES the existing link.** The three warning cases — `not_found` (no staff match), `ambiguous` (>1 match), `self` (names one's own email) — leave an existing person's current manager **untouched** and only emit a non-blocking warning, so a typo/ambiguous/self cell can't silently wipe a correct reporting line. (For a brand-new person with no existing manager, the link is simply left unset — there's nothing to preserve.)
- **Flagging is non-blocking (`managerWarnings`).** Those three cases surface as warnings while the person still imports (only the manager link is affected — and even that is preserved for existing people). Distinct from a `SkippedRow` — the row is not skipped. Warning messages state **only the problem** (e.g. `Manager email "x@y" matched no staff.`), since the outcome differs by case (kept for an existing person, unset for a new one); the UI's "Manager issues" section explains existing links are left unchanged and a blank cell clears. The commit result reports `managersLinked`.
- **`managersLinked` counts relationships actually established or changed this import** — creates that got a manager plus updates whose manager changed to a non-null value. A cleared link, or an unchanged pointer carried past an unrelated field change, does **not** count (so it isn't merely "every written row with a manager").
- **No cycle detection beyond self-reference** — intentional (it matched `contacts.managerId`, but that column is gone and its successor `contact_relationships` *does* guard cycles, so the CRM is no longer a precedent — [ADR 0052](../decisions/0052-contact-relationships-one-typed-junction.md)). **Consumers therefore defend themselves,** and this matters more now that `managerId` gates access: because a `self` warning is non-blocking and a self-pointing row can persist, `getFeedbackAboutReports` explicitly excludes the caller as recipient (else it would surface their own feedback in full — [ADR 0047](../decisions/0047-feedback-reports-scoping-not-granting.md)), and `getReviewNoteAccess` returns on the self branch **before reading `managerId` at all**, so nobody can become their own note-manager and read their own drafts ([ADR 0049](../decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)). The seed applies the same guard, and the **org chart's `buildOrgForest`** normalises self / dangling / cyclic edges into badged roots rather than trusting the column to be a tree — which also makes it the **first place a bad import becomes visible** after commit ([ADR 0054](../decisions/0054-staff-org-chart-dom-tree.md)). Any new `managerId` consumer must add its own guard.

### Persistence (respects ADR 0007 effective dating)

Matching is by `ripplingId`. The server **recomputes the diff** (`computeImportPlan`) — the client preview is never trusted — and commits in one transaction:
- **Create** → new `staff` row + initial `staffEmployment` (`effectiveFromDate = joinDate ?? today`).
- **Update** → `staff` identity fields written in place; a **new** `staffEmployment` row (`effectiveFromDate = today`) inserted **only when an employment fact changed** (the "latest row wins" pattern), so identity-only edits don't churn employment history.
- **`managerId`** rides the same `staff` upsert's `set` clause (`managerId: sql\`excluded.manager_id\``). `commitStaffImport` resolves manager ripplingIds → staff ids across this batch's creates (freshly minted ids) + updates + a DB lookup for managers only in the DB. Because creates and updates share **one** batched `insert(staff)`, Postgres verifies the self-FK at statement end, so an **intra-batch reference (A managed by B, both new in the same file) resolves** (verified against Postgres).

**Gotcha:** duplicate `ripplingId`s *within one CSV* are not de-duped (a Rippling export shouldn't contain them); a genuine duplicate fails the commit transaction on the `staff.ripplingId` unique constraint.

### PTO import (`/admin/upload-pto`)

Mirrors the staff importer (clone of `staff-import.tsx`), ingesting a Rippling **leave** export into `staff_pto`. Code: client `src/components/admin/pto-import.tsx`; pure transform `src/lib/staff/pto-import/transform.ts` (reuses the same `getField`/`parseDate` helpers as staff-import); server diff `src/lib/staff/pto-import/plan.ts`; shared types/zod `src/lib/staff/pto-import/types.ts`; actions `src/actions/admin/{previewPtoImport,commitPtoImport}.ts` (+ `ptoImport.schema.ts`).

The defining difference from the staff importer: rows can **delete** as well as upsert, and matching is **two-level**. See [ADR 0009](../decisions/0009-pto-import-cancel-as-delete.md) for *why* cancellations delete and what "destructive re-sync" implies.

#### CSV column mapping

`Leave request ID`→`staffPto.ripplingId` (the PTO record key), `Employee - ID`→resolves the staff member (`staff.ripplingId`), `Employee`→display name, `Start date`→`startDate`, `Leave end date`→`endDate`. Same whitespace/case-tolerant lookup and ISO/US date parsing as staff-import. A row missing `Leave request ID` or `Employee - ID` is **skipped**.

#### Derivation rules (keep in sync with `transform.ts`)

- **`Leave request status` → action + `isPending`:** `APPROVED` → upsert, `isPending=false`; `Pending` → upsert, `isPending=true`; `REJECTED`/`CANCELED`/`CANCELLED` → **delete** action (remove the record if it exists). Anything else → row **skipped** (unrecognized status).
- **`Leave policy custom name` → `type`** (case-insensitive substring, first match): "unlimited vacation"→`VACATION`; "family medical leave"/"sick leave"→`SICK_LEAVE`; "statutory holiday"→`STATUTORY_HOLIDAY`; "company retreat"→`COMPANY_RETREAT`; "religious holiday"→`RELIGIOUS_HOLIDAY`; "bereavement leave"→`BEREAVEMENT_LEAVE`; "parental leave"/"pregnancy leave"/"paternity leave"→`PARENTAL_LEAVE`; "jury duty"→`JURY_DUTY`; "leave of absence"→`LEAVE_OF_ABSENCE`. **No match → row skipped** ("Unrecognized leave type").
- For `upsert` rows, a missing/unparseable `Start date` or `Leave end date` **skips** the row. `delete` rows skip date/type derivation entirely (a cancelled request may have neither) — they carry only the leave-request id.

#### Persistence (`computePtoImportPlan` → `commitPtoImport`)

Two-level diff: resolve staff by `Employee - ID`, then match the PTO record by `Leave request ID`. The plan buckets are `creates` / `updates` (changed-field marked) / `deletes` / `unresolved` / `unchanged` / `ignoredCancellations`. Commit recomputes server-side and runs one transaction: insert creates, `update` changed rows by **id**, delete cancelled/rejected rows by **leave-request id**.

**Gotchas:**
- **Unresolved, not skipped, when staff is missing.** An upsert row whose `Employee - ID` matches no `staff` row is surfaced as `unresolved` (it can't be inserted without the staff FK) — distinct from the client-side `skipped` rows. Import staff first.
- **Delete is keyed independently of staff.** A `delete` row removes any existing record by its leave-request id even if the employee can't be resolved; with no matching record it's counted as `ignoredCancellations` (a cancel for leave we never imported is a no-op).
- Same intra-CSV duplicate-`ripplingId` guard as staff-import — the transform skips a second occurrence of a `Leave request ID` to avoid a unique-constraint rollback.

### Bulk edit roles (`/admin/bulk-edit-roles`)

Edits the latest employment row for many staff at once, the only in-app way to maintain employment facts (the importers seed them; this corrects/advances them). A filterable, sortable [TanStack](https://tanstack.com/table) table where each row is one staff member's current employment facts — line of business, role, employment type, `isBillable`, `utilizationTarget`, `billableType`, `isManagement` — editable inline (selects, switches, a clamped 0–100 utilization input with 0/50/100 presets, and a `HUB`/`GLOBAL` segmented control for `billableType`). Toggling `isManagement` **on** auto-sets `isBillable=false` and `utilizationTarget=0`. These are two distinct rules, both defined once in `src/lib/staff/employment.ts` (see below): the **management→non-billable default** is a *client-side convenience* applied only at the moment management is enabled (the admin can re-enable billable afterward — a billable manager is valid), whereas the **non-billable ⇒ `utilizationTarget=0` invariant is a standing rule and IS server-enforced** (the commit's schema `.refine` calls `isEmploymentInvariantSatisfied`, so a crafted payload can't slip a non-zero target onto a non-billable row). A floating save bar shows the changed-staff count and a confirmation dialog summarises per-staff field diffs before committing.

Code: read `src/actions/staff/getStaffEmploymentForEdit.ts` (server-only; latest employment row per staff via the same two-query, latest-per-staff reduction as `getStaffDirectory` — includes inactive staff so the table can filter on "active"; staff with **no** employment row are omitted, there's nothing to edit); client `src/components/admin/bulk-edit-roles.tsx`; commit `src/actions/admin/commitBulkEditEmployment.ts` (+ `bulkEditEmployment.schema.ts`). The commit is `publicActionClient` + `assertLocalhost()` like the importers.

**The save behaviour is the load-bearing part — it deliberately extends ADR 0007:**

- **Effective date left BLANK → UPDATE the latest employment row in place** (semantics: correcting a data-entry mistake — no new historical fact). This is the *new* path; everywhere else, employment changes only ever insert.
- **Effective date provided → INSERT a new effective-dated row per staff** (semantics: a real change effective on that date). The date must be **strictly after** that staff's latest `effectiveFromDate` (re-validated server-side; rejected with the affected names otherwise).

The payload is never trusted: the commit re-reads each staff's latest row, **drops no-op changes** (a row where no editable fact differs), and enforces the billable invariant (`isBillable=false ⇒ utilizationTarget=0`). That invariant now lives in **one** pure, client-importable module — **`src/lib/staff/employment.ts`** (`isEmploymentInvariantSatisfied` + `normalizeEmploymentFacts`), mirroring how `line-of-business.ts` / `currency.ts` are the single source for their enums. It's imported by everywhere that authors or validates billability: `staff-import/transform.ts` and `staff-import/types.ts` (derive-on-import), `bulkEditEmployment.schema.ts` (the server `.refine`), and `bulk-edit-roles.tsx` (as-you-type derivation) — so the definition can't drift. See [ADR 0007 — In-place correction (bulk edit)](../decisions/0007-staff-employment-effective-dating.md).

**Compensation is not editable here (import-only).** When bulk-edit inserts a *new* effective-dated row it reads the latest row's comp and **carries it forward**, so advancing someone's role/LoB never clears their salary; the in-place-correction path leaves the existing row's comp untouched. See [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md).

## Key flows

- **Login gating** — on first authenticated request `getCurrentStaffAccess` resolves user → staff (auto-linking by email once), and the `(app)` layout admits only `ok`; `not_setup`/`incomplete` are bounced to the single `/profile-setup` block screen. See [flows.md](../flows.md).
- **Employment change** — insert a new `staff_employment` row with a new `effectiveFromDate` rather than mutating the prior row, preserving history. The **one** exception is correcting a wrong latest row in place via bulk-edit with a blank effective date (no new fact) — see *Bulk edit roles* above and [ADR 0007](../decisions/0007-staff-employment-effective-dating.md).
- **Profile read (by id — `/profile` and `/staff/[id]`)** — the per-person reads are now **parameterized by `staffId`** and not ownership-scoped: `getStaffProfile(staffId)` (`src/actions/staff/getStaffProfile.ts`), `getStaffHistory(staffId)`, `getStaffPto(staffId)`, `getStaffAvatar(staffId)`, `getStaffProjects(staffId)` (see *Projects on the profile* below), plus three **performance-domain** reads that own their own gates — `getFeedbackAboutStaff(staffId)`, `getStaffReviewNotes(staffId)` and `getStaffSelfEvaluations(staffId)` (see *Viewer-dependent tabs* below). `ProfileView` renders these in a **two-column layout** — a left rail (identity/meta card, Links card, Compensation card) beside a right-column tabbed card (Overview / Manual of Me / Ways of Working / Resume / **Peer feedback** / **Review notes** / **Self-evaluations** / History, the middle three conditional); see [ui.md](../ui.md). `getStaffProfile` returns latest employment via the ADR 0007 ordering — **including the compensation columns** (`base`/`hourlyRate`/`guaranteedBonus`/`currency`), which `ProfileView` renders in a **Compensation card only when its `canViewCompensation` prop is true** — and is wrapped in `React.cache` so `/staff/[id]`'s `generateMetadata` and page body share one query. Both pages wire the prop: `/profile` hard-codes `true` (own profile), `/staff/[id]` computes `canViewCompensation(user, id)` (alongside `canEditStaff`) and passes it both to `ProfileView` **and** as `getStaffHistory`'s `includeCompensation` arg. See [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md) and [ui.md](../ui.md). `getStaffProfile` also **self-joins `staff`** (drizzle `alias`) on `managerId` to project `{ managerId, managerName }`; `ProfileView` renders a read-only **"Reports to <link>"** line in the identity header linking to `/staff/[managerId]` (omitted when there's no manager). The manager is set by the import only — no editor (see [ADR 0026](../decisions/0026-staff-manager-self-reference.md)). `getStaffAvatar` reads the linked auth `user.image` (separate query because the avatar lives on `user`, not `staff`; null when unlinked).
  - **Self read** — there is **no separate "my" read** (`getMyProfile`/`getMyHistory`/`getMyPto` and the `MyProfile` alias are gone). Each own-profile page resolves its staff id inline via `getCurrentStaffId()` (`src/actions/staff/getCurrentStaffId.ts`, `React.cache`d, `staff.userId = user.id` → id or null) and calls the parameterized `getStaff*` cores directly (`getStaffProfile(staffId)`, `getStaffHistory(staffId, true)`, `getStaffPto(staffId)`, …). The single low-level "user → own staff id" lookup lives in `src/actions/staff/ownStaffId.ts` — the one place that query exists, shared by `getCurrentStaffId`, the **ownership** checks (`canEditStaff`/`canViewCompensation`/`canEditTimesheet`), and the **relationship/eligibility** checks that pass its **`activeOnly`** variant (the feedback gate, `getReviewNoteAccess`, `loadStaffProfileDrawer`). **Which variant to pass is an access-control decision, not a detail** — see [permissions.md](./permissions.md) → *Resolving the caller* before adding a new caller-identity check. The page never touches `db` (ADR 0010). See [ui.md](../ui.md) (`/profile`).
  - **Why not ownership-scoped:** the directory and `/staff/[id]` deliberately show other people, so profile/history/avatar reads can't filter by `userId`. Access is the `(app)` layout's session+staff gate, plus a capability check where data is sensitive — `getStaffPto` requires `pto.review` for non-owners (returns `null` otherwise). Its Mon–Fri working-day math is the shared pure module `src/lib/staff/pto-working-days.ts` (`countWorkingDays`, **extracted out of `getStaffPto`**) so the projects domain's `getProjectPto` counts leave the same way — see [projects.md](./projects.md#project-detail-page). This softens ADR 0010's "inherently self-scoped" property for cross-person data — see *Authorization* below, [permissions.md](./permissions.md), and [ADR 0014](../decisions/0014-rbac-better-auth-access-control.md).
- **Directory ("Browse staff", `/staff`)** — `getStaffDirectory()` (`src/actions/staff/getStaffDirectory.ts`) returns one `StaffDirectoryEntry` per staff member (identity + `isActive` + avatar + **`skills: StaffSkill[]`** + **`managerId`** + latest employment facts; employment fields null when no history). **This one read feeds both `/staff` views** — the card grid and the org chart at `?view=org` (see *Org chart* above); the grid ignores `managerId`. **Two queries, no N+1:** all staff (left-joined to `user` for the avatar; `skills` comes straight off the `staff` row), then the *entire* `staff_employment` table ordered newest-first and reduced in JS to keep the latest row per `staffId`. Includes inactive staff so the UI's "active only" toggle (defaults ON) can hide/show them client-side. `StaffDirectoryEntry` now also projects **`location`** (the `"City, CC"` label), for the location filter below. It also exports `staffDirectoryFilterOptions` (line-of-business / role / employment-type enum values) so the page gets filter options without importing the Drizzle schema. All search + filtering is **client-side** over this single server fetch (`StaffDirectory` component) — including the **skills filter** (multi-select, AND semantics, with an optional minimum-proficiency segment), which runs in-memory via the pure `matchesSkillFilter` (see *Skills* below), and a **location filter** (city picker + "Search nearby" switch, the shared `location-filter-control.tsx`). No URL params, no per-filter server query. **The location filter's one server touch is the "search nearby" set:** because the world-cities dataset can't bundle to the browser, the directory calls the **`nearbyCityLabels`** action (`src/actions/cities/nearbyCityLabels.ts` → `citiesNear`, auth-only, no capability gate) to resolve the labels within `NEARBY_RADIUS_KM` (~100 km) of the picked city, falling back to exact-city match while that's in flight — the rest of the match is in-memory `Set.has` over the projected `location`. This is the **client-side counterpart** to companies'/contacts' server-side location filters, which call `citiesNear` directly ([data-model.md](../data-model.md#location-filters), [crm.md](./crm.md#location)). See *Authorization* (whole-table scan tradeoff) and [ui.md](../ui.md).
- **Edit (links + client intro + résumé)** — the `secureActionClient` mutations `updateStaffLinks` (`src/actions/staff/updateStaffLinks.ts`), `updateStaffClientIntro`, and `updateStaffResume` (`src/actions/staff/updateStaffResume.ts`) all take an explicit **`staffId`** and edit that row by id, and all declare `metadata({ action, authorize: authorizeStaffEdit })` — the `authorizeStaffEdit` hook (`src/actions/staff/canEditStaff.ts`) reads `clientInput.staffId` and runs `canEditStaff` before the body (owner always; others need `staff.edit` — see *Authorization* and [permissions.md](./permissions.md)). The bodies hold no authz call. `.returning()` confirms a row matched (→ `UserSafeActionError` if not). `updateStaffClientIntro`/`updateStaffResume` stamp their `*UpdatedAt` column. All revalidate `/profile` and `/staff/${staffId}`. Schema rules: URL fields empty-string→null else valid URL; client intro trimmed, max 2000, empty→null; résumé trimmed, **max 50,000 chars**, empty→null; schemas in their own `.schema.ts` files so the dialogs import them for the resolver (never export a schema from a `'use server'` file — `.claude/rules/forms.md`). The edit dialogs (`edit-links-dialog.tsx`, `edit-client-intro-dialog.tsx`, `edit-resume-dialog.tsx`) take a `staffId` prop so `/profile` and `/staff/[id]` share them. UI in [ui.md](../ui.md).
- **Résumé PDF upload (parse only, no storage)** — the résumé dialog has an "Upload PDF" button that reads the file to base64 client-side (guarded to ~6 MB), calls the `parseResumePdf` `secureActionClient` action (`src/actions/staff/parseResumePdf.ts`), which extracts text server-side via the **`unpdf`** dependency and returns it for the user to review in the textarea; **no DB write and the PDF is never stored** (it only parses the caller's own upload, so it needs no `staff.edit` gate — the gated write is `updateStaffResume`). Scanned/image-only PDFs (no extractable text) and unreadable files return a `UserSafeActionError` telling the user to paste text manually. Saving goes through `updateStaffResume` as normal. Base64 inflates payload ~33%, so `next.config.ts` raises `experimental.serverActions.bodySizeLimit` to `"8mb"` to fit a ~6 MB PDF (client and server caps mirror each other). See [ADR 0013](../decisions/0013-resume-pdf-parse-not-store.md).
- **History feed (`/profile` + `/staff/[id]`)** — `getStaffHistory(staffId, includeCompensation = false)` (`src/actions/staff/getStaffHistory.ts`) is a server-only read returning a **category-agnostic** `HistoryEntry[]` (`{ id, date, category, summary }`, `HistoryCategory = "EMPLOYMENT" | "BONUS" | "ALLOCATION"`), newest first, for the given staff id (not ownership-scoped — see *Authorization*). **`EMPLOYMENT` and `BONUS` entries are mapped** — employment from `staffEmployment` rows (ordered per ADR 0007) with **compensation folded into the same entry's summary** for authorized viewers (see below), and `BONUS` from `staff_bonus_payment`, the feed's **first real second category** (a dated payment rather than a change of terms — and gated by the same `includeCompensation` flag, since the fact a bonus was paid is itself compensation information); `ALLOCATION` is still a stub. Entries are pushed into one array and merged by a single stable sort (date strings are `"YYYY-MM-DD"`, so lexicographic compare is chronological and equal-date entries keep per-source order). Adding a source needs no change to the consuming UI (`HistoryTimeline` is purely presentational). Rendered by `HistoryTimeline` inside the profile's **History tab** (formerly a slide-out `HistorySheet`, now deleted) — see [ui.md](../ui.md). For *why* the feed is category-agnostic and merged server-side, see [ADR 0011](../decisions/0011-category-agnostic-history-feed.md).
  - **Comp amounts are gated, folded into the employment entry.** `includeCompensation` (the caller passes `canViewCompensation`'s result — `true` for own profile) controls whether comp amounts are appended to each employment entry's summary **at all**; because history renders in a client component (the profile's tabbed panel), this gate is at the *read*, so salary never ships to an unauthorized browser. When on, each entry's summary gains `Base … · Hourly … · Guaranteed bonus …` (a zero guaranteed bonus omitted), **and the `BONUS` entries are fetched at all** — the flag gates that whole query, because the mere fact a bonus was paid is compensation information. There is still **no separate `COMPENSATION` category** — ongoing comp rides the employment entry it changed with. See [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md).
- **Projects on the profile (`getStaffProjects`)** — the **first staff→projects read in the app**. `src/actions/staff/getStaffProjects.ts` (server-only, not ownership-scoped — same posture as `getStaffProfile`) returns the projects a person is involved with: those where they hold a staffing line (`project_roles.staffId`) — **which now includes running one as delivery manager**, since a delivery manager is a `DELIVERY` role ([ADR 0067](../decisions/0067-delivery-managers-as-project-roles-and-coverage-gaps.md) dropped the `project_delivery_managers` junction and its second query). **One query** now, still merged in JS into **one `StaffProjectSummary` row per project** (`{ id, name, companyName, status, relationships[] }`, where `status` is **derived** from the project's roles via `deriveProjectStatus` — the project stores none) — a `Map` keyed by project id, `relationships` accumulated in a `Set` (so a person holding several roles of the same discipline lists the label once). `relationships` are human labels from `PROJECT_ROLE_TYPE_LABELS` alone, **delivery-first** then the other disciplines alphabetically — compared against `PROJECT_ROLE_TYPE_LABELS.DELIVERY` (sourced, not typed out, so it can't drift from the string the project's Roles table shows). ⚠️ **The label therefore changed from "Delivery manager" to "Delivery"**, and `DELIVERY_MANAGER_LABEL` is gone. Rows sorted by project name. Rendered by `StaffProjectsSection` in the Overview tab, where **each project name links to its `/projects/[id]` detail page** (covers both `/profile` and `/staff/[id]`). See [projects.md](./projects.md) and [ui.md](../ui.md).
- **Edit (skills)** — a dedicated page `/staff/[id]/skills` (not a dialog); see *Skills* above.
- **Profile surveys (Manual of Me + Ways of Working)** — two guided, autosaving surveys, each on its own page (`/staff/[id]/manual-of-me`, `/staff/[id]/ways-of-working`), both stored in the generic `responses` table via the same widened `upsertResponse` action and both sharing the `use-response-autosave` engine; readable by any profile viewer, editable via `authorizeStaffEdit` (no new permission). See *Manual of Me* / *Ways of Working* above and [ADR 0028](../decisions/0028-generic-responses-table-app-validated-question-ids.md).
- **Profile completeness (`/reporting/profile-completeness`)** — the cross-person roll-up of everything the flows above capture: one gated read (`getProfileCompleteness`, `staff.edit`) projecting presence/counts/dates only, rendered as a client-filtered, client-sorted read-only table. See *Profile completeness* above.
- **Profile maintenance** — keep skills, availability, and rates current. Links, client intro, résumé, **skills**, and the **Manual of Me** + **Ways of Working** surveys have a self-edit UI today; **compensation** is maintained via the Rippling import only (no edit UI — see [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md)); availability is still proposed.
- **Skill matching** — Allocations querying skills to find suitable People is still proposed. Note the inline-jsonb storage means this can't be an indexed join yet — see [ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md) for the tradeoff and the migration path if/when matching lands.

## Connects to

- **Allocations** — role and line of business drive staffing; `staff_pto` spans reduce available capacity over their date range (the planner's capacity meter subtracts them outright). ⚠️ **`utilizationTarget` is deliberately *not* read by the planner** — non-billable roles carry target 0 by invariant, so a target-relative capacity figure would mark every overhead person permanently over-allocated; the meter uses a flat 8h/day, 40h/week baseline for everyone. See [ADR 0060](../decisions/0060-allocations-capacity-meter.md).
- **Utilization reporting** — `/reporting/utilization` reads this domain for its whole cohort: `staff.joinDate`/`terminationDate` bound each person's employment window, the latest `staff_employment` supplies line of business, role, employment type and **`isBillable`** (overhead roles are excluded outright), and approved `staff_pto` spans (**dates only, never `type`**) take precedence over a role on the same day. ⚠️ **`employmentType` is load-bearing there:** available hours, PTO and bench are **full-time-only measures on both bases**, so an `HOURLY` person carries no capacity denominator and their PTO/bench cells read "n/a" rather than `0` — only their project hours count (and they now get their own *Part-time project hours* figure). Two things the report deliberately does **not** read: **`utilizationTarget`** (it measures capacity *use*, not attainment against a target) and **any compensation column** — which is why it needs no `viewMargin`-style gate. See [utilization.md](./utilization.md).
- **Timesheets** — `isBillable`/`billableType` turn logged hours into billing; **compensation** (cost side — base/hourly on `staff_employment`) feeds margin. External **charge** rates are still proposed.
- **Performance** — profile is the subject of reviews, and now **hosts three performance surfaces**: the **Peer feedback**, **Review notes** and **Self-evaluations** tabs, each gated by its own read (see *Viewer-dependent tabs*). All three panels also render inside the **profile drawer** the compensation-plan editor opens (self-evaluations `readOnly` there). Review notes make `staff.managerId` an authorization input — the only such gate in the codebase ([ADR 0049](../decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)); self-evaluations are the one performance surface a **non-manager can write**, and the one that reuses `ratings.view` *with* an owner path ([ADR 0058](../decisions/0058-self-evaluations-dated-records-with-snapshotted-answers.md)). See [performance.md](./performance.md).

## Open questions

- **External charge rates** (what we bill a client for a person) — still unmodelled. Would follow the same effective-dated pattern; the *cost* side (compensation) now lives on `staff_employment` (see below).
- **Cross-tenure identity:** no `person` entity links a human's multiple `staff` rows across leave/rehire stints (see *Nuances*). If tenure-spanning reporting or "have we worked with them before" becomes a need, this is the gap to fill.

> **Resolved:** compensation model + sensitivity — compensation is **effective-dated columns on `staff_employment`** (not a separate table), populated **import-only** and **required** (rows missing comp are skipped; no carry-forward on import), and **view-gated** by `staff.viewCompensation` (own always visible), shown on the profile Compensation card + folded into the history feed's employment entries. See [ADR 0020](../decisions/0020-compensation-effective-dated-import-only.md).

> **Resolved:** skill taxonomy + proficiency scale — skills are an inline `jsonb` list on `staff` picked from a hardcoded catalogue (`src/lib/staff/skills.ts`), with a fixed 3-value proficiency scale. See *Skills* above and [ADR 0018](../decisions/0018-skills-inline-jsonb-catalogue.md). (Deliberately not the normalized many:many table originally proposed.)

> **Resolved:** linking `staff` ↔ auth `user` is now the nullable, unique `staff.userId` FK (`onDelete: set null`) — an optional 1:1 link, null until first sign-in. Identity is no longer keyed off email (`staff.email` is no longer unique). See Key entities above.
