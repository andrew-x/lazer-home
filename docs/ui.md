## Component library

shadcn on **Base UI** primitives (`base-nova` preset, **Tabler icons**, Geist font). Config: `components.json` (`style: "base-nova"`, `baseColor: "neutral"`, RSC on, aliases `@/components`, `@/lib`, `@/components/ui`, `@/hooks`).

- **Icons: `@tabler/icons-react`** (`Icon*` components, e.g. `IconHome`, `IconSettings`). Lucide was **removed** (`lucide-react` uninstalled) — all app + vendored `src/components/ui/**` icons use Tabler, and `nav.ts` types icons via Tabler's `Icon` type. Don't add other icon libraries.
- **Add components, don't hand-write them:** `bunx --bun shadcn@latest add <name>` (e.g. `table`, `dialog`, `tabs`, `badge`). Re-add with `--overwrite` to update. **Gotcha:** the shadcn registry emits Lucide imports — after re-adding any `ui/**` component, re-swap its icons to Tabler.
  - **Exception — `dialog.tsx` and `textarea.tsx` were vendored by hand**, not via the CLI. The `shadcn add dialog` run wanted to **overwrite our hand-edited `button.tsx`** (which carries the deliberate `loading` prop) and pulls Lucide, so `dialog.tsx` was instead written to mirror the existing `sheet.tsx`: a centered modal on `@base-ui/react/dialog` with a Tabler `IconX` close. Treat both as vendored primitives all the same (don't hand-edit beyond the icon swap). The `<Dialog>`/`<DialogTrigger render={…}>`/`DialogContent`/`DialogHeader`/`DialogFooter`/`DialogClose` API matches the sheet's.
- **Vendored primitives** live in `src/components/ui/**` and are treated as generated code: don't hand-edit, and Biome skips linting them via an `overrides` block in `biome.json` (turns off a11y/exhaustive-deps/document-cookie rules that the registry code trips — extended with `useSemanticElements`/`useKeyWithClickEvents` off, still needed by `input-group`). Current set also includes `select`, `switch`, `toggle`/`toggle-group`, `popover`, `calendar`, a composed `date-picker`, `collapsible` (Base UI `Collapsible`; the projects list's status sections — `data-panel-open` on the trigger drives the chevron, the panel unmounts while closed), `tabs` (backs the **opportunity detail drawer** — Info / Notes / Project plan — **and** the CRM company/contact **detail pages**: company = Notes (default) / Contacts / Opportunities & Projects, contact = Activity (default) / Opportunities. The detail pages were de-tabbed in the shared-layout refactor, then **re-tabbed** once each grew enough sections to warrant it; the shared `detail-parts.tsx` skeleton stays tab-agnostic and the views render the `tabs` primitive directly. See [domains/crm.md](./domains/crm.md)), and (for the CRM company picker) `combobox` + `input-group` (icons swapped Lucide → Tabler as usual). The `combobox` is built on **Base UI's Combobox** — the right fit for the Base UI preset; it replaced the cmdk-based `command` primitive (now deleted), and `input-group` (formerly a `command` dependency) is now a `combobox` dependency. The **`date-picker`** (`src/components/ui/date-picker.tsx`) is our own composition of the vendored `popover` + `calendar` (built on `react-day-picker`, added for it) over the project's Base UI primitives, with Lucide icons swapped to Tabler; it takes/returns a `"YYYY-MM-DD"` string (timezone-agnostic, per `.claude/rules/database.md`) and formats the trigger label via `formatDate` from `@/lib/format/format` (**`date-fns` was removed** — no longer a dependency). Used by the bulk-edit save bar. **Exception — `Button`'s `loading` prop:** `button.tsx` carries a deliberate hand-edit. `<Button loading>` renders a leading `IconLoader2` spinner (inherits variant color/size), auto-disables (`disabled || loading`), and sets `aria-busy` — the canonical way to satisfy the forms rule's "drive button loading state from `isPending`/`isExecuting`" (used at the auth buttons, the shared `FormDialogFooter` Save button, and the shared `CsvImport` harness's confirm button). **Gotcha:** re-adding Button via `shadcn --overwrite` drops this prop; re-apply it after any overwrite.
  - **Escape hatch for the don't-hand-edit rule: override at the call site with class names**, not in `ui/**`. The canonical example is table density: the vendored `Table`'s cells are `p-2`, too tight for wide data tables (the tasks cell's owner disc ended up against the table edge), so the roomier padding lives in the shared **`ROOMY_TABLE`** constant (`src/components/table-density.ts`) — `[&_td:last-child]:pr-4 [&_td]:px-3 [&_th:last-child]:pr-4 [&_th]:px-3` — applied as `<Table className={ROOMY_TABLE}>`. **Reuse the constant rather than re-inlining the string;** its two current callers are `contacts-table.tsx` and the shared `DetailTable` (`crm/detail-parts.tsx`), so *every* CRM detail table (the company's Contacts / Opportunities / Projects / referred tables, the project detail page) inherits it. **Specificity gotcha:** these are descendant selectors on the `<Table>` element (0,1,1), so a plain class on an individual `<td>` (0,1,0) *loses* to `[&_td]:px-3` — per-cell overrides need matching-or-higher specificity, which is why the last-column padding is written as `[&_td:last-child]:pr-4` on the wrapper instead of a class on the cell. Reach for a descendant-selector class on the wrapper before touching the primitive.
  - **The same pattern, for field density: `COMPACT_META_FIELDS`** (`src/components/form/field-density.ts`) — `[&_[data-slot=field-value]]:min-h-7 [&_[data-slot=field-value]]:py-0.5 [&_[data-slot=form-field]]:gap-1`, applied to a **meta rail** container so the dozen short label/value rows in ~320px read as structure rather than air. `FormField` emits `data-slot="form-field"` and read-mode value boxes (`InlineEditField`'s display, `MetaField`'s value) emit `data-slot="field-value"` purely so this hook exists. Callers: `SidebarSection` (so every CRM/project detail sidebar) and the opportunity drawer's Info column. Rail density is a property of *where* a field renders, which is why it isn't a `variant` on `FormField`.
- **Polymorphism uses a `render` prop, NOT Radix's `asChild`.** Base UI is not Radix — your training data is likely wrong here. To render a button as a link: `<Button render={<Link href="/x" />}>` (see `not-found.tsx`).

### EditableTable — don't route draft state through TanStack `table.options.meta` (gotcha)

The shared `EditableTable` (`src/components/admin/editable-table.tsx`) hands each cell editor the per-row **draft** (read the current value, push a patch) via **React Context** — the `EditableDraftContext.Provider` wrapping the render, read with the **`useEditableDraft<TValues>()`** hook. This is deliberate and load-bearing; the obvious approach — passing the draft through TanStack's `table.options.meta` and reading it off `cell.getContext()` — is **broken** and caused a real, hard-to-see bug.

**Why `meta` fails.** TanStack memoizes `cell.getContext()` on `[table, column, row, cell]` — all referentially stable while the row's `data` is unchanged. `flexRender` passes that memoized context object straight into `React.createElement(cellComponent, context)`. The draft lives **outside** the table's row `data` (it's separate draft state in `useEditableRows`), so when only the draft changes, the cell element's props are referentially identical to the previous render and **React bails out of re-rendering the cell entirely** — the editor keeps showing the pre-change value. The floating save bar still updated (it's rendered directly by `EditableTable`, not through a table cell), which made it look like state was flowing when the cell alone was frozen. Confirmed at runtime: `onValueChange` fired with the new value and the draft updated (save bar appeared), yet the cell's own value read stayed stale.

**The fix (in code):** deliver the draft through context, not `meta`. A **context read re-renders its consumers even when a parent bails out**, so cells re-render on every draft change. `useEditableDraft()` is the API cells use (the old `editDraft(table)` helper and its `declare module "@tanstack/react-table"` augmentation were removed); cells no longer take a `table` prop. Applied across all three editable tables: `performance/edit-levels.tsx` (`LevelCell`), `admin/bulk-edit-roles.tsx` (`EnumCell`/`SwitchCell`/`UtilizationCell`/`BillableTypeCell`), `admin/manage-users.tsx` (`RoleCell`/`BannedCell`).

**General rule:** never route frequently-changing external state (state that lives outside the table's row `data`) through `table.options.meta` — the memoized `getContext` lets React skip the cell re-render. Use context (a subscribing hook like `useEditableDraft`) instead. (Incidental: these cells render the trigger label directly from the draft value, `<SelectValue>{label(value)}</SelectValue>`, which is a fine simplification — but that was **not** the fix; it doesn't matter if the cell never re-renders.)

### Save-on-edit vs. batch edit — two different table patterns

The app has **two** distinct editable-grid patterns. Pick by *when the write happens*, not by "which one is shared":

- **Batch edit (draft → confirm)** — the shared **`EditableTable`** / `useEditableRows` engine (`src/components/admin/editable-table.tsx`). Edits accumulate in a client draft, a **floating save bar** counts them, and a **confirm dialog** shows per-row diffs before one bulk commit. Used by `admin/bulk-edit-roles`, `admin/manage-users`, and `performance/edit-levels`. Right when a change is a *decision about many rows at once* that someone should review before it lands.
- **Save-on-edit (autosave)** — the shared **`useAutosaveQueue`** engine (below). Every field persists on its own; there is **no Save button** and no confirm step. Used by the profile survey editors and the compensation-plan editor. Right when the work spans sessions and losing it is worse than an un-reviewed write.

**They are not interchangeable, and the plan editor deliberately does not use `EditableTable`** — two independent reasons ([ADR 0046](./decisions/0046-compensation-change-plans-rating-writing-proposals.md)): its draft-then-confirm engine is the *opposite* of save-on-edit, and it renders exactly **one `<tr>` per row**, so there is nowhere for an expanded panel. Don't "unify" them.

**There is a third, simpler pattern, and it is often the right one: discrete saves.** A form with an explicit Save button, per-action **toasts**, and no queue. `review-notes-panel.tsx` (the profile's Review notes tab — see [domains/performance.md](./domains/performance.md)) is the reference: it sits *inside* an autosaving host (the plan-editor drawer) and still **deliberately uses neither `useAutosaveQueue` nor `SaveIndicator`**, because a review note is submitted as one whole thought and a half-written draft autosaving into a shareable row is the wrong default. Don't reach for the queue just because a neighbour uses it — autosave is for *fields of an existing record*, not for composing a document. Its `Share`/`Delete` actions go through the shared `ConfirmDialog`, and it takes an optional **`onChanged`** callback so a client-fetched host can re-load itself instead of `router.refresh()`ing a route it doesn't own.

### Expandable rows (the first in the app)

`src/components/performance/compensation-plans/plan-editor.tsx` is the **precedent for expandable table rows** — sitting alongside the existing precedent for hand-rolled planner grids. It uses the vendored `Table` primitives **directly** (no TanStack), with a `Set<string>` of expanded ids in the parent and each `PlanRow` rendering a fragment of **two** `<tr>`s: the row itself, then (when expanded) a full-width `<td colSpan={PLAN_COLUMN_COUNT}>` holding the panel.

- **Declare the columns once.** `plan-columns.ts` exports `PLAN_COLUMNS` + `PLAN_COLUMN_COUNT` so the header row and the panel's `colSpan` cannot drift — a mismatch there silently breaks the table layout.
- **A11y:** the chevron is an `IconButton` with `aria-expanded` + `aria-controls` pointing at the panel's `useId()`.
- **Flush before collapsing.** The panel owns textarea state, so collapsing unmounts it — the editor `await`s `flushRow(itemId)` *before* removing the id from the expanded set.
- Rendering real row components (rather than TanStack cells) also sidesteps the `cell.getContext()` memoization trap the `EditableTable` engine has to work around with context.
- The trailing column is **not** a per-row action slot: it carries only the committed-plan drift badge (`plan-columns` key `applied`). See the next section for why.
- Cells sit on `TableCell`'s default `align-middle` — the earlier `align-top` overrides were removed, so a row reads as one line even when a cell wraps.

### Membership belongs off the grid (the plan editor's split)

**Who is in a set** and **what you are deciding about each member** are two different jobs; the compensation-plan surface splits them across two routes rather than putting both in one table. `[planId]` is the editor (a pure comparison grid — no "Add staff" dialog, no per-row remove button); `[planId]/staff` is the membership roster (`manage-plan-staff.tsx`), reached from a *Manage staff* button and from the editor's empty state.

Why, and worth copying when a grid grows a destructive row control:

- **No destructive control next to the money columns.** A remove button living in the same row as an editable salary is a mis-click with real consequences and no undo — removing a plan item cascades away its proposal and notes.
- **Membership is one reviewable change, not a stream of side effects.** The roster holds a local `Set` of checked ids, shows a live "N to add · N to remove" counter, and submits the **whole set** at once. It confirms only when a row being removed actually holds work.
- **The set goes to the server whole** and is diffed there in one transaction — see [performance.md](./domains/performance.md) → `setCompensationPlanStaff`. The client never has to track adds and removes separately.
- **Dates as tooltips, not inline text.** The expanded panel's stats strip is a grid (`sm:grid-cols-2 lg:grid-cols-4`, matching the subratings grid under it), and "last evaluation" / "previous change" dates hang off an `IconInfoCircle` tooltip. They are occasional context; inline they made every fact two-line and ragged, defeating the grid.

### Shared autosave engine — `src/hooks/use-autosave-queue.ts`

The generic save-on-edit engine, **extracted out of `src/components/staff/use-response-autosave.ts`** when the compensation-plan editor became its second consumer. It owns only the hard part — a **dirty set of keys**, **per-key debounce timers**, and a **single-flight drain loop** — and knows nothing about what a key means or what gets sent. The caller supplies `save(key) => Promise<boolean>`, which reads the current value, decides whether it differs from what was persisted, sends it, and reports success. That split is the only clean seam between two surfaces whose value shapes have nothing in common.

The concurrency rules are the whole point; don't reimplement them per surface:

- **One save in flight at a time** — otherwise two edits to the same field can land out of order and the older value wins.
- **An edit during a save re-queues itself**, so a fast typist never loses the last keystroke.
- **A failed save stays queued** (and stops the drain) so a later edit, blur, or unmount retries it.
- **"Saved" only shows when the key is genuinely clean**, so typing through a save never flashes a stale tick.

API: `touch(key, { delayMs, immediate })`, `flush(key)`, `flushAll()` (returns `false` if anything failed — a caller can refuse to proceed), `abandon()` (drop queued work when retrying is *pointless*, not merely failed), plus per-key `state` and `isSaving`/`dirtyCount`. It best-effort `flushAll`s on unmount.

Two consumers today, and they show the two key-shapes: `use-response-autosave.ts` (key = `questionId`; profile surveys — see [staff-profiles.md](./domains/staff-profiles.md)) and `compensation-plans/use-plan-autosave.ts` (key = `itemId::field`, so two fields of a row — or the same field of two rows — never overwrite each other, and each write carries only what changed; discrete controls save `immediate`, text/numbers debounce). The plan hook adds one behaviour worth copying: a **specific, recognisable server error** (`PLAN_LOCKED_MESSAGE`) means retrying can never succeed, so it `abandon()`s the queue and `router.refresh()`es into a read-only render, rather than looping.

**`SaveIndicator` + `aggregateSaveState` live in `src/components/form/save-indicator.tsx`** — the shared subtle inline status (**never a toast**), so the wording and iconography of "your work is being kept" are identical on every autosaving surface; only the idle `label` differs. `src/components/staff/response-save-indicator.tsx` is now a **re-export shim** over it (same pattern as `admin/table-filters.tsx`), kept so the survey editors keep their import path.

### List filter bars

Four list pages carry a filter bar over a server-paginated read — **companies**, **contacts**, **opportunities**, **projects** (`*-list-filters.tsx` in `src/components/crm/` and `src/components/projects/`). They all share one shape, so build the next one the same way:

- **State lives in the URL, not the component.** Each control navigates with `router.replace` via **`buildListHref`** (`src/lib/core/list-href.ts` — rebuilds the current querystring with the given params changed and the page key dropped), so the server page re-fetches and the back button restores prior filters. Any filter change resets that list's page param to 1.
- **Current values come from the `params` the page already parsed**, passed down as a prop — deliberately **not** `useSearchParams`, which would force a Suspense boundary.
- **The text search is the shared `useUrlSearchFilter` + `SearchFilter`** (`src/components/form/search-filter.tsx`). The hook owns the local input state, the 300 ms `useDebouncedValue` debounce, the external-sync effect (Clear / back-navigation) and the `q` navigation; it returns `{ search, setSearch, currentQuery }`, where `currentQuery` (the URL value, not the keystroke value) is what a bar's `hasFilters` check should read. `SearchFilter` is just the magnifier-prefixed input. This was **extracted from four verbatim copies** of the same ~25-line debounce block; the subtle bit it preserves is the `if (debouncedSearch !== search) return` guard, which skips the transient window right after an external sync where `search` was reset but the debounced shadow still holds the old text.
- **Selects reuse `src/components/form/filters.tsx`** (`SelectFilter`, `SearchableSelectFilter`, `MultiSelectFilter`, the `ALL` sentinel …).
- **"Clear filters" is a `router.replace(basePath)`**, rendered only when something is active. Bars with many controls wrap: `/companies` and `/contacts` put search + Clear on the first row and the location filter on a second.

> **When *not* to use this pattern:** filters sitting **inside an uncontrolled `Tabs`** over an already-fetched list should filter **in memory** (the staff-directory approach), because URL-backed filters would force tab selection into the URL too. That's the deliberate choice in `feedback-about-reports-table.tsx` (For / Author / From / To over one manager's reports) — don't "upgrade" it to `buildListHref`. See [performance.md](./domains/performance.md).

## Theming & tokens

- Tokens are oklch CSS variables in `src/app/globals.css` (`:root`), surfaced to Tailwind v4 via `@theme inline`. Imports: `tailwindcss`, `tw-animate-css`, `shadcn/tailwind.css`.
- `--font-heading` maps to Geist sans.
- **Light mode only.** A `.dark` block and the `dark` custom variant exist (carried in from the registry) but are **unused** — there is no theme toggle. Don't wire one up without a decision.
- Use **semantic classes** (`bg-primary`, `text-muted-foreground`, `bg-sidebar-accent`, `border`), never raw hex or `indigo-600`. Conditional classes via `cn()` from `@/lib/core/utils`.

### Design language (current source of truth)

A deliberate, editorial look that **avoids the generic AI-app aesthetic** (rounded + shadowed + accent-heavy). This refines the theme described in [decisions/0005](./decisions/0005-ui-stack.md) — that ADR still holds for the stack and the indigo-light-mode choice, but the specifics below supersede its "indigo accent" framing.

- **Sharp corners.** `--radius` is `0.25rem` (4px); all the `--radius-*` steps derive from it. Don't bump radii per-component.
- **Flat surfaces.** No elevation shadows — a utility-layer rule in `globals.css` neutralizes every `shadow-*` to `box-shadow: none`. Hairline `border`s define edges; use `border` for separation, never a shadow.
- **Indigo, sparingly.** The UI is mostly **monochrome neutral grays**. The `--accent`/`--accent-foreground` and `--sidebar-accent`/`--sidebar-accent-foreground` tokens are neutral (not indigo). Indigo lives only in `--primary` and `--ring`, so it surfaces only on primary buttons, focus rings, links, and the active nav item's icon (`app-sidebar.tsx` adds `text-primary` to the active icon). Don't tint hovers/cards/backgrounds indigo — the accent reads as intentional precisely because it's rare.
- **Global `cursor-pointer`.** A rule in `globals.css`'s **`@layer utilities`** (deliberately **not** base — moved there by commit #51) gives `button`s and ARIA-interactive roles (`menuitem`, `option`, `switch`, `tab`, `checkbox`, `radio`, …) a pointer cursor — Base UI / shadcn omit it by default. The layer choice is load-bearing: a base-layer rule would lose to the `cursor-default` the vendored Base UI / shadcn primitives hardcode on their option/menu-item classNames (a utility beats a base rule regardless of specificity). Don't add `cursor-pointer` per component.
- **Minimal auth surfaces.** `(auth)/login/page.tsx` is a single centered column — logo mark + product name + one Google button + "Lazer staff only" — no card, no gradient. Keep auth/marketing screens uncluttered.

### Brand (intentionally off-accent)

The brand mark is `public/icon.svg` — **magenta** (`#FF00C5`) — exposed via `<LogoMark>` / `<LogoWordmark>` in `src/components/brand/logo.tsx`. The product name is `APP_NAME` ("Lazer Home") in `src/lib/core/constants.ts`. The magenta mark against the indigo UI accent is **intentional** — the logo is the brand, the indigo is the product chrome; don't "fix" the mismatch.

### Charts (hand-rolled SVG — no charting library)

Data viz is **hand-rolled inline `<svg>`**; **do not add a charting dependency**
(no Recharts/visx/Chart.js/etc.). This is deliberate — a library's default look
(rounded, shadowed, multi-color, boxed legends) fights the flat/editorial design
language, and our charts are simple enough to draw directly. Two instances live in
the Performance section, one per dashboard: the distribution **scatter**
(`compensation-scatter.tsx`, on `/performance/compensation`) and the
level-distribution **bar chart** (`level-distribution-bar-chart.tsx`, on
`/performance/levels`). **Follow the same approach for future charts** rather than
reaching for a library.

Dataviz styling rules (consistent with the design language above):

- **Thin marks, recessive gridlines.** Gridlines/axis baseline are hairlines
  (`stroke-border`, `strokeWidth={1}`); the mark is small (`r={3.5}`).
- **Indigo is the data-ink.** A single data series uses the **`--primary`** token
  (`fill-primary`) — the one place data earns the accent. Keep it to one series; a
  single-series chart needs **no legend** (the `<figcaption>` caption names the
  metric).
- **Detail via native `<title>`.** Per-mark hover/label is a `<title>` child of the
  element — no tooltip library, and it doubles as the accessible label (with a
  `role="img"` + `aria-label` on the `<svg>`).
- **Non-zero baseline is OK for scatters.** Dots carry no area-from-zero meaning
  (unlike bars), so padding the domain off zero to keep the spread legible is
  honest. **Bar charts must start at a zero baseline** — bar area encodes the value,
  so a clipped baseline lies (the level-distribution bar chart enforces this).
- **Interaction stays lightweight.** The scatter's per-dot detail is a native
  `<title>`; the bar chart adds a small hover-tooltip bubble (its own SVG `<rect>` +
  `<text>`, clamped inside the plot) — still no tooltip library.
- **Fixed `viewBox`, fluid width.** Draw in a fixed viewBox coordinate space that
  scales to the container (`className="h-auto w-full"`), and use
  `vectorEffect="non-scaling-stroke"` so hairlines stay crisp at any width.

## Routing & auth gating

Route groups split public from authenticated, and **route protection lives in a layout, not middleware** — consistent with the project's deliberate no-middleware stance (see ADR-0006).

- `src/app/(app)/**` — authenticated pages. `(app)/layout.tsx` is an async Server Component that calls `getCurrentUser()` and `redirect("/login")` when there's no session, **then** `getCurrentStaffAccess(user)` and redirects any non-`ok` status to the single `/profile-setup` route (status is `ok` = active staff record with employment — see [flows.md](./flows.md)). Every page under `(app)` is gated by this two-step check. The layout also computes **`visibleNavHrefs`** (see *App shell & sidebar* → permission-aware nav) and threads it into `AppShell`.
- `src/app/(onboarding)/**` — the post-login **block** screen for authenticated users who can't enter the app yet: a single `profile-setup/page.tsx` that resolves `getCurrentStaffAccess` itself and shows different title/body for the `incomplete` vs `not_setup` cases (same screen). There is **no group `layout.tsx`** — the page self-gates like `/login`: it redirects unauthenticated users to `/login` and bounces `ok` users back to `/` so a fixed-up profile is never stuck here. The screen uses `OnboardingNotice` (`src/components/auth/onboarding-notice.tsx`) — a login-styled full-screen notice (logo + title + message + `SignOutButton`).
- `src/app/(auth)/**` — public pages (currently only `/login`, which redirects to `/` if already signed in).
- The old default `src/app/page.tsx` was deleted; the home dashboard is now `(app)/page.tsx` served at `/`.

Pages today: `/login` (landing + Google button), `/` (home dashboard with placeholder stat cards), `/staff` ("Browse staff" — searchable/filterable directory of everyone) and `/staff/[id]` (a person's profile), `/profile` ("My profile" — your own staff profile, same presentation as `/staff/[id]`), `/companies` ("Companies" — the CRM company list, see below) and `/companies/[id]` (a company's detail page), `/contacts` ("Contacts" — the CRM people list, see below) and `/contacts/[id]` (a contact's detail page), `/opportunities` (the CRM pipeline kanban board, see below), `/projects` (client engagements + staffing, see below) and `/projects/[id]` (a project's detail page), `/allocations` (the standalone staffing **planner grid** — see below), `/timesheets` (weekly time capture) and `/timesheets/[week]` (a single week's sheet), `/feedback` ("Peer Feedback" — a **two-or-three-tab** list ("About you" / "You've given", plus **"Your reports"** *only* for a `feedback.review` holder linked to staff — the tab and its panel aren't rendered at all otherwise) + `/feedback/new` give-feedback page + `/feedback/[id]` detail; the route is unchanged, only the label/title were renamed from "Feedback", see [performance.md](./domains/performance.md) and [ADR 0047](./decisions/0047-feedback-reports-scoping-not-granting.md)), `/performance/compensation` ("Compensation dashboard" — headcount & comp analytics by role *and* by level, `staff.viewCompensation`-gated; ### `/admin` — localhost-only tooling surface

The admin area lives **outside the `(app)` route group on purpose**: the `(app)` layout gates on an active staff record, but the staff-upload tool is what *creates* those records (chicken-and-egg). `src/app/admin/layout.tsx` is the whole gate — it `notFound()`s the entire segment unless `isLocalhost()` (`src/lib/auth/admin.ts`), so there's no RBAC check here; being local *is* the boundary. Its own chrome (header + "Back to app" link) replaces the app shell. `admin/page.tsx` is a card grid linking to the four tools:

- `admin/manage-users` — edit application users' RBAC role + ban status inline, save all at once (`manage-users.tsx`; see [domains/permissions.md](./domains/permissions.md)). `promote-self-button.tsx` is a dev shortcut here.
- `admin/bulk-edit-roles` — edit staff employment facts (role, line of business, billability, management) across the team in one pass (`bulk-edit-roles.tsx`).
- `admin/upload-staff` — import staff from a Rippling CSV export (`staff-import.tsx`).
- `admin/upload-pto` — import leave records from a Rippling CSV export (`pto-import.tsx`).

The two CSV importers share the **`CsvImport`** harness (`csv-import.tsx`) — a file → preview → commit flow that owns the PapaParse config, file/reset lifecycle, badge summary, preview sections and commit orchestration; each page supplies only its columns, labels, transform, and the two next-safe-action hooks (preview + commit). Both importers render read-only previews via `data-table.tsx` (a TanStack React Table wrapper over the vendored `table` primitive). The two inline-edit tools (`bulk-edit-roles`, `manage-users`) instead share `editable-table.tsx` (its own TanStack-based editable grid) and the shared filter controls. Those generic filter controls now live app-wide in **`src/components/form/filters.tsx`** (`ALL` sentinel, `FilterLabel`, `SelectFilter`, `SearchableSelectFilter`/`SearchableOption`, `MultiSelectFilter`, `SegmentedFilter`, `TriStateFilter`/`TRISTATE`) so the staff directory and the performance dashboards can share them (the two dashboards wrap them in their own shared control bar, `components/performance/dashboard-filters.tsx`, whose CAD/USD toggle renders **iff** the caller passes `rates` — the levels dashboard has no money, so it passes none and gets no toggle); **`MultiSelectFilter`** is the flat, searchable Combobox-with-chips multiselect over enum options (mirrors the `SkillsFilter`/`entity-multi-combobox` pattern) — unlike `SelectFilter` it has **no `ALL` sentinel**, so an empty selection matches nothing and the caller decides what to render (used by the allocations planner's Role filter, which defaults to the billable disciplines via `isBillableRole`); **`SearchableSelectFilter`** is the searchable single-select sibling of `SelectFilter` — a clearable Combobox with in-memory filtering over an `{ id, name }` (`SearchableOption`) list, for long option sets like staff (used by the projects list's delivery-manager filter); **`src/components/admin/table-filters.tsx` is now a thin re-export shim** over that module, kept so the admin tables keep their existing import path.

### Profile pages — `ProfileView` (shared by `/profile` and `/staff/[id]`)

`ProfileView` (`src/components/staff/profile-view.tsx`) is the single presentation for a staff profile. **Both** `/profile` (own record) and `/staff/[id]` (anyone) render it; they differ only in which `staffId` they resolve and pass in.

**Two-column layout** (`max-w-6xl`, `lg:grid-cols-[20rem_1fr]`):

- **Left rail** — three stacked cards: a **meta/identity card** (avatar, name, an employment summary line — role · line of business · employment type · billable/non-billable, all via the label maps below — plus Email, Joined date, and a read-only **"Reports to" link** to `/staff/[managerId]` when set); a **Links card** (LinkedIn/GitHub/Portfolio, `CardAction` Edit when `canEdit`); and a **Compensation card**, rendered only when the `canViewCompensation` prop is true.
- **Right column** — a single card wrapping a **Base UI `Tabs` (`variant="line"`)**, default tab **Overview**. Tabs, in order: **Overview**, **Manual of Me**, **Ways of Working**, **Resume**, *(**Peer feedback**)*, *(**Review notes**)*, **History**. The **Overview** tab stacks flat sub-sections separated by hairline rules (`divide-y`) via the local `TabSection` helper (heading + optional action + content): **Skills** (Edit → `/staff/[id]/skills` page when `canEdit`), **Client intro** (`EditClientIntroDialog` when `canEdit`), **Projects** (`StaffProjectsSection`, see below), and **Time off** (only when `pto` is non-null; heading + external Rippling "Manage" link live in the tab wrapper, content is `PtoContent`). The **Manual of Me**, **Ways of Working**, **Resume**, and **History** tabs each hold one `TabSection` — each survey tab shows its read view (`ManualOfMeSection` / `WaysOfWorkingSection`), an "N of M answered" line, and an Edit/Fill-out link (only when `canEdit`) to its dedicated guided editor page. See *Ways of Working* in [domains/staff-profiles.md](./domains/staff-profiles.md).
  - **The tab set is viewer-dependent — 5 to 7 tabs.** The two parenthesised tabs render **only when their read returned non-null**: **Peer feedback** (`StaffFeedbackPanel`, from `getFeedbackAboutStaff` — the limited recipient tier on your own profile, full content for a `feedback.review` holder) and **Review notes** (`ReviewNotesPanel`, from `getStaffReviewNotes` — gated on the **reporting line**, and the profile's one *writable* performance surface). A `null` hides the trigger too, so a tab's presence never discloses that feedback or notes exist. **Anything keying off the tab set (deep links, tests) must tolerate the range**; tab state is uncontrolled and not in the URL, matching `/feedback`. `EditResumeDialog` on the Resume tab is now `canEdit`-guarded like every other section (it used to render unconditionally). See *Viewer-dependent tabs* in [domains/staff-profiles.md](./domains/staff-profiles.md), [ADR 0049](./decisions/0049-review-notes-reporting-line-as-authorization-boundary.md) and [ADR 0050](./decisions/0050-profile-peer-feedback-tab.md).

The pages don't touch `db` — they `await` actions-layer **reads** (server-only async functions, not `'use server'` actions; see [ADR 0010](./decisions/0010-actions-layer-owns-db-access.md)):

- **`/staff/[id]`** (`(app)/staff/[id]/page.tsx`) `Promise.all`s `getStaffProfile(id)` / `getStaffProjects(id)` / `getStaffPto(id)` / `getStaffAvatar(id)` / `getCurrentUser()` / `getManualOfMe(id)` / `getWaysOfWorking(id)` / **`getFeedbackAboutStaff(id)`** / **`getStaffReviewNotes(id)`** (the last three each return `null` when this viewer may not see that section — the reads are the gate, `ProfileView` just hides it), then resolves `canEditStaff` + `canViewCompensation` and awaits `getStaffHistory(id, canViewComp)` **separately** (its `includeCompensation` arg depends on the comp gate — comp entries must be filtered at the read since history renders in a client component). `notFound()`s on an unknown id, and uses `generateMetadata` to title the tab with the person's name (shares the `React.cache`d `getStaffProfile` query). Profile/projects/history/avatar reads aren't ownership-scoped — the `(app)` gate is the boundary — but `getStaffPto` returns `null` for non-owners without `pto.review` (so `ProfileView` hides the Time off section) and the Compensation card / comp history are gated by `canViewCompensation` (own always; others need `staff.viewCompensation`). See [domains/permissions.md](./domains/permissions.md) and [ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md).
- **`/profile`** (`(app)/profile/page.tsx`) is the same, with the id resolved from the session (`getCurrentStaffId()`) and then passed into the very same parameterized `getStaff*` cores — there's **no separate "my" read**. (Own profile always passes `canViewCompensation = true` and `getStaffHistory(staffId, true)`.) **It deliberately does *not* hard-code the feedback / review-notes props** the way it hard-codes `canEdit`/`canViewCompensation` — it passes the reads' answers, because "it's your profile" is exactly the case that must yield the *narrower* result (the recipient feedback tier; only the notes your manager has shared).

`getStaffProfile` returns the profile fields (incl. `resume`/`resumeUpdatedAt`) plus the **latest** `staffEmployment` row via the [ADR 0007](./decisions/0007-staff-employment-effective-dating.md) ordering. **Staff enums (role, employment type, billable type, PTO type) display via the label maps in `src/lib/staff/staff-enums.ts`** (`ROLE_LABELS` etc.), **not** `humanizeEnum()` — the label maps preserve acronyms like `QA` that `humanizeEnum` would mangle to "Qa". Calendar dates display via the timezone-safe `formatDate()`, instant `timestamp`s (e.g. `resumeUpdatedAt`) via `formatTimestamp(value: Date)`, and avatar fallbacks via `initialsFor()` — all from `src/lib/format/format.ts` (`initialsFor` was moved here to be shared; see the dates gotcha in [staff-profiles.md](./domains/staff-profiles.md)). (`humanizeEnum` is still fine for enums with no acronyms and no dedicated label map.)

**Edit (Links, Client intro, Résumé).** The **Links card** puts its Edit button in the card header via **`CardAction`** (`src/components/ui/card.tsx` — a header slot that right-aligns into the grid); **Client intro** and **Résumé** live in the right-column tabs, so their Edit buttons sit in the `TabSection` heading's `action` slot instead. Either way the buttons come from `edit-links-dialog.tsx` / `edit-client-intro-dialog.tsx` / `edit-resume-dialog.tsx` — client components taking a **`staffId` prop** and rendering the shared **`FormDialog`** (`src/components/form/form-dialog.tsx`), whose `children` is a render prop handed a `close` callback. `FormDialog` (via its `useRemountOnOpen` hook) **remounts the inner form on each open** — it bumps a `formKey` when opening so the form's `defaultValues` refresh from the latest server data after a save rather than going stale, while keeping the form mounted through the close animation (so the popup doesn't collapse to its header before fading out). `useRemountOnOpen` also takes an optional `controlled` `{ open, onOpenChange }` for dialogs driven by a parent (the CRM inline create-from-form dialogs). The form uses **`useHookFormAction`** (tight binding; see `.claude/rules/forms.md`) wired to the `updateStaff*` action with the imported `.schema.ts` as the `zodResolver`; the shared **`FormDialogFooter`** renders the server-error line + Cancel/Save, driving the Save button's `loading` off `action.isPending` and reading errors off `action.result.serverError`, and the action's `onSuccess` calls `close`. (Forms whose shape diverges from the action input instead use **loose binding** — plain `useForm` + `useAction` with a manual `onSubmit` that transforms the data; both patterns are documented in `.claude/rules/forms.md`.) The actions are gated server-side by the `authorizeStaffEdit` hook via `metadata({ authorize })` — backed by `canEditStaff` (own → always; other → `staff.edit`); the dialog UI is still rendered for everyone, so a non-permitted user clicking Save on someone else's profile gets the server error rather than a hidden button. See [domains/permissions.md](./domains/permissions.md), [ADR 0014](./decisions/0014-rbac-better-auth-access-control.md).

**Skills — edited on a dedicated page, not a dialog.** The Skills sub-section (Overview tab) shows its Edit link (only when `canEdit`) navigating to `/staff/[id]/skills` rather than opening a `FormDialog` — the three-bucket editor (`edit-skills-form.tsx`) is too large for a dialog. That page `notFound()`s any viewer who fails `canEditStaff`. The read view (`skills-section.tsx`) groups skills by proficiency level as `Badge` chips. See *Skills* in [domains/staff-profiles.md](./domains/staff-profiles.md) and [ADR 0018](./decisions/0018-skills-inline-jsonb-catalogue.md).

**Projects sub-section (Overview tab).** `StaffProjectsSection` (`src/components/staff/staff-projects-section.tsx`) — purely presentational over `getStaffProjects` (see [domains/staff-profiles.md](./domains/staff-profiles.md)) — lists each project the person is staffed on or delivery-manages as a row: name (an `InternalLink` to `/projects/[id]`) + `companyName · relationship labels` + a `ProjectStatusBadge` (reused from the projects domain). Empty → "No projects yet."

The **résumé dialog additionally** has an "Upload PDF" button: it reads the file to base64 (`FileReader`, guarded to ~6 MB), runs the `parseResumePdf` action via a separate `useAction`, and on success `setValue`s the returned text into the textarea (dirty + validated) for review before the user saves via `updateStaffResume`. The PDF itself is never uploaded for storage — only its extracted text. Upload errors render inline. The résumé card shows the text with `whitespace-pre-wrap` plus an "Updated …" line from `formatTimestamp(resumeUpdatedAt)`. See [ADR 0013](./decisions/0013-resume-pdf-parse-not-store.md).

**Compensation card — read-only, gated.** Rendered only when the `canViewCompensation` prop is true (own profile always; others need `staff.viewCompensation`). `CompensationSection` (`src/components/staff/compensation-section.tsx`) lists base / hourly rate / currency from the latest employment row, with the **guaranteed & discretionary bonus rows shown only when non-zero**; amounts are formatted via `formatMoney` from the pure `src/lib/format/currency.ts`, and the **currency shows as its bare code** (e.g. `CAD`, not a translated label — there is no currency-label map; the former `CURRENCY_LABELS` was dead and has been removed). There is **no edit affordance** — compensation is import-only (see [ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md)).

**`StaffProfileDrawer` — the second `Sheet` consumer in the app.** `src/components/staff/staff-profile-drawer.tsx` is a **read-only** review pane over one staff member, opened from a row elsewhere (today: a person's name in the compensation-plan editor) so a reviewer keeps their place in the list. It **follows the CRM opportunity detail sheet's pattern deliberately** — vendored `Sheet`, load-on-open via an action (`loadStaffProfileDrawer`), `data-[side=right]:sm:max-w-[56rem]` (narrower than the opportunity sheet's `80rem`: no planner grid to fit), a `flex flex-col gap-0 p-0` content with its own scrolling body, and `sr-only` `SheetTitle`/`SheetDescription` because the visible header is bespoke. Copy that shape for the next drawer rather than inventing a third one.

- **Three to seven tabs, mirroring the profile**: **Overview**, **Projects**, *(**Time off**)*, *(**Peer feedback**)*, *(**Review notes**)*, *(**Evaluations**)*, **History** — the four parenthesised ones render only when their read came back non-null (so the drawer's tab count is viewer-dependent too), History always present and last. **Projects, Time off and Evaluations are their own tabs rather than Overview sections**, because each is a history in its own right and a review pane is read a tab at a time. It reuses the *same* panels and sections as the profile — `CompensationSection`, `SkillsSection`, `StaffProjectsSection`, `PtoContent`, `HistoryTimeline`, `StaffFeedbackPanel`, `ReviewNotesPanel` — so the drawer and the profile can't drift in what they reveal. **`EvaluationHistory` is the one exception**: rating history has no profile-page equivalent (`/performance/levels` shows the *latest* row across everyone, never one person's history), so the drawer is the first and only surface for it.
- **Overview order:** a 3-column facts grid (**Location / Joined / Reports to** — email was dropped) → **Compensation** → Skills → Client intro. Compensation renders **only when its field is non-null** (as the Time off *tab* does), and `null` means *"you may not see this"*, not *"there is none"* — `CompensationSection` has its own "No compensation on file." for that, which is exactly why the drawer omits the whole `Section` instead of rendering an empty one. The header is the name plus a four-facet employment line (role · LoB · employment type · billable), absent entirely when there's no employment row.
- **Read-only apart from Review notes**, which is intentional: that's where the review conversation gets written up, so making it read-only would defeat the drawer's purpose. Everything else links out via a header **"Open full profile"** button to `/staff/[id]` — the drawer now carries near-parity of the profile's read-only *content*, and differs by having no edit affordances (bar notes) and no avatar/links rail.
- **It refreshes itself, not the route.** `ReviewNotesPanel` gets an `onChanged` that re-runs the loader — calling `router.refresh()` would re-render the plan editor underneath, mid-edit.
- **Mounted once per table, not per row** (the editor holds `profileStaffId` + `profileOpen`, kept as two pieces of state so the id survives the close animation). A per-row drawer would duplicate fetches and state.
- **The loader minimises in the projection, not the JSX** — a client-fetched drawer ships whatever the action returns, whether or not the JSX renders it. So every sensitive field is **gated at the read**: `compensation` is split out of the money-free employment facets and built only for a viewer who passes `canViewCompensation`, `pto`/`feedback`/`reviewNotes`/`evaluationHistory` come from self-gating reads, and `history` is fetched **sequentially after** the rest because the comp gate decides whether comp rides its employment entries. **Never gate by not rendering.** See [domains/staff-profiles.md](./domains/staff-profiles.md) → *The read-only profile drawer* and [domains/permissions.md](./domains/permissions.md), where this read is the worked example of five gate shapes in one payload.
- **`evaluationHistory` carries the strictest gate on the drawer — `ratings.view`, and it is the only one with *no owner fallback*.** Compensation falls back to "your own is always visible" and feedback to a limited recipient tier; a staffer never sees their own level at all ([ADR 0032](./decisions/0032-staff-rating-levels-effective-dated-manager-only.md)), so there is no self tier to degrade to and the tab simply doesn't exist for them. Don't add one "for consistency" with the neighbouring tabs.

**History tab.** History is now an **inline tab** (formerly a slide-out sheet — `history-sheet.tsx` was deleted). `HistoryTimeline` (`src/components/staff/history-timeline.tsx`) is a **purely presentational** component taking the `HistoryEntry[]` from `getStaffHistory()` and rendering each entry as a category `Badge` + date + summary in a left-border timeline. Category-agnostic: only `EMPLOYMENT` entries are wired today (allocation is still a stub); comp amounts are **folded into those entries' summaries** rather than forming a separate category (`CATEGORY_LABEL` has no `COMPENSATION` key). It renders inside a **client** component (the profile's tabbed panel), so comp is filtered upstream at the read (`getStaffHistory`'s `includeCompensation`), not here — see the history feed flow in [staff-profiles.md](./domains/staff-profiles.md).

### `/staff` — Browse staff directory

`(app)/staff/page.tsx` (Server Component) `await`s `getStaffDirectory()` once, then renders the `StaffDirectory` client component (`src/components/staff/staff-directory.tsx`) with the entries + filter options. **All search and filtering is client-side over that single server fetch** (no URL params, no per-filter server query): name search, plus line-of-business / role / employment-type filters (options from `staffDirectoryFilterOptions`), a **skills filter** (see below), plus an **"active only" toggle that defaults ON** — inactive staff are fetched but hidden until it's turned off. Results render as a card grid of `staff-card.tsx`, each linking to `/staff/[id]`.

**Skills filter (`SkillsFilter` + minimum level).** A grouped, searchable multi-select Base UI `Combobox` (chips) fed from `SKILL_CATEGORIES` — picking multiple skills applies **AND** semantics (a person must hold all of them). When ≥1 skill is selected, a "Minimum level" segmented `ToggleGroup` (Any / Intermediate+ / Senior) appears; it raises the required proficiency bar. Filtering delegates to the pure `matchesSkillFilter(entry.skills, skills, minimum)` from `src/lib/staff/skills.ts` (`"Any"` → `undefined` minimum → no level constraint). While a skill filter is active, each `StaffCard` gets a `highlightedSkills` prop and renders `Badge`s for the person's matched skills with their level label — so the card shows *why* it matched. All of this runs in-memory over the once-fetched list.

### `/companies` + `/contacts` — CRM companies and people (two pages)

Companies and contacts each get their **own page** (`(app)/companies/page.tsx`, `(app)/contacts/page.tsx`) — the old combined "Companies & Contacts" page was split so each entity has focused space. Both are Server Components with the same shape: one **server-side-paginated** table over a `get*Page` read `Promise.all`'d with `getCurrentUser()`, page in its own query param (`companiesPage` / `contactsPage`), and an "Add" dialog gated on one `canEdit = userHasPermission(user, { crm: ["edit"] })` flag. Both container columns are **`max-w-7xl`** (widened from `max-w-5xl` to give the tables room).

- **Pagination is server-side**, not client-side over one fetch (unlike `/staff`) — the datasets are expected to grow. `pagination-controls.tsx` renders `Link`-based prev/next **plus numbered page buttons** (windowed with ellipsis — always first/last + a ±1 window; ranges ≤7 pages show every page; the numbered strip is hidden below `sm`) that rebuild the URL preserving other params (it takes the full `searchParams` + its own `paramKey` + `basePath`); pages are clamped server-side. The numbered buttons are shared, so `/opportunities` and `/projects` lists get them too.
- **Both pages have a filter bar** (`companies-list-filters.tsx` / `contacts-list-filters.tsx`), built on the shared pattern in [List filter bars](#list-filter-bars). `/companies`: a **debounced name search** (`q`), a **status select** (Partner / Client / Prospect / All, `status`) and the **location filter** (`city` + `nearby`). `/contacts`: the same **debounced name search** (`q` — matched against first name, last name and the joined "First Last", see [domains/crm.md](./domains/crm.md)), an **"Include inactive" `Switch`** (`inactive=1`), and the **location filter**. Both lay out as search + "Clear filters" on one row with the location control below. **"Include inactive" is the one control that *widens* the list** rather than narrowing it — hence a plain switch (nobody wants "inactive only") with the param absent by default, like `nearby=1`; it counts toward "Clear filters" but deliberately **not** toward the table's `filtered` empty-state prop, since it can never cause an empty result. Any filter change resets `companiesPage`/`contactsPage` to 1, the read's `where` applies to **both** the count and the rows, and each table's empty state is filter-aware ("No companies/contacts match your filters."). See [domains/crm.md](./domains/crm.md#company-status-tags).
- **`companies-table.tsx` / `contacts-table.tsx`** are Server Components over a plain shadcn `table` (the companies rows use tighter row padding; the contacts table widens horizontal cell padding with `<Table className={ROOMY_TABLE}>` — the shared constant in `src/components/table-density.ts`, since the vendored primitive's `p-2` crowded the Next steps column's owner disc against the table edge, and `ui/**` isn't hand-edited). `ContactsTable` stays a Server Component even though its last column is interactive — only that **cell** crosses the client boundary (`ContactTasksCell`). The companies table shows **Name · Status**, where Status is a set of **derived tags** — Partner / Client / Prospect `secondary` badges from `companyStatusTags` (`EmptyCell` when none apply); it has no Website column (that moved to the detail page) and no standalone Partner column (folded into the tags). See [domains/crm.md](./domains/crm.md#company-status-tags) and [ADR 0034](./decisions/0034-company-status-derived-tags.md). The companies table **deliberately shows no tasks column** — a company's tasks live on its own detail page, and rolling contact-level tasks up onto the list was intentionally declined (contact-level tasks appear only on the company *detail* page). The contacts table shows **Name · Company · Location · Next steps** ([ADR 0043](./decisions/0043-tasks-entity-replaces-crm-next-steps.md)): the **job title rides as muted small text under the name** (no Role column), the Company cell shows the joined `companyName`, and **Next steps is editable in place** — `ContactTasksCell` (below), not the read-only `OpenTasksCell`. The name cell also shows an **"Inactive" `secondary` Badge** for `!isActive` contacts — the word comes from `INACTIVE_LABEL` (`src/lib/crm/contact-status.ts`), imported rather than hardcoded, which is the drift guard across all four badge sites (see [domains/crm.md](./domains/crm.md#contact-status-active--inactive)) — because they're hidden unless "Include inactive" is on, so an appearance needs explaining. When the row has a `successor` it also gets **a third muted line, "Moved to \<link to the newer contact\> at \<their company\>"** (the company clause is dropped when the successor has no employer). Rationale: an inactive row is otherwise a dead end, and where the person went is the one thing worth knowing without opening the page. Email/phone/LinkedIn moved off the table to the detail page. **Both tables now drill into the detail pages:** the name cell links to `/companies/[id]` / `/contacts/[id]`, and the contacts table's company cell links to `/companies/[id]` (falling back to `EmptyCell` when the contact has no company). Small top-level shared components back these cells: **`src/components/empty-cell.tsx`** renders the muted `—` placeholder, and **`src/components/external-link.tsx`** the new-tab outbound link (still used on the detail pages). **`src/components/contact-link.tsx`** adds **`MailLink`** (`mailto:`) and **`PhoneLink`** (`tel:`) for rendering email/phone as click-to-contact links (now on the contact detail page, not the table). The reads build a contact's display name via the shared **`contactNameSql`** helper in `src/actions/shared/contactName.ts`.
- **"Add company" / "Add contact" dialogs** (`add-company-dialog.tsx` / `add-contact-dialog.tsx`) render **only when the user holds the `crm.edit` capability** — each page computes the `canEdit` flag and conditionally renders its trigger. The server actions are gated regardless, so this is an affordance, not the boundary. Forms use the tight `useHookFormAction` binding (see `.claude/rules/forms.md`); the contact form's company picker is the shared `CompanyComboboxField` (below).
- **The contact form is create *and* edit** — `add-contact-dialog.tsx` and `edit-contact-dialog.tsx` share the same field layout (the edit one is opened from the contact detail page's identity `action` slot), so `linkedinUrl` and the employer can be changed after creation.
- **The Active/Inactive Status lives in the *edit* dialog only** — a `FormField label="Status"` holding a `Switch` whose label is `contactStatusLabel(field.value)` ("Active" / "Inactive", from `src/lib/crm/contact-status.ts`), `Controller`-bound to the schema's required `isActive`. It sits **directly under the company combobox** on purpose: status is an occasional, deliberate decision about a person, not a quick in-place tweak like owner/location/rating, and it usually changes *with* the employer. Its helper line is **conditional**, and both strings come from that module — `INACTIVE_BY_SUCCESSION_EXPLANATION` when the loaded `contact.successor` is set ("Set to inactive automatically because a newer record for this person exists elsewhere.", so flipping it back on doesn't look like the obvious fix for a record that only *looks* wrong), else the longer `INACTIVE_EXPLANATION`, which names **both** reasons a record can be inactive (see [domains/crm.md](./domains/crm.md#contact-status-active--inactive)). **`AddContactDialog` deliberately has no Status field** — a brand-new contact is always active. Because this is a **full-record** save, `isActive` round-trips exactly like `ownerId`/`relationshipStrength`; the practical consequence is documented in [domains/crm.md](./domains/crm.md) (a stale dialog can undo a succession's auto-flip — ordinary last-write-wins).
- **Neither contact form has a relationship picker.** `manager-combobox-field.tsx` was **deleted** with `contacts.managerId`: every person-to-person link is now a `contact_relationships` row, added from the contact's own page (see the Relationships group below and [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md)). The edit dialog does warn inline, under the company combobox, when changing the employer of a contact who has a manager — `updateContact` drops that link, since a manager is a colleague by definition.
- **Shared company picker — `company-combobox-field.tsx` (`CompanyComboboxField`).** The single "pick or create a company" control, used **identically by both the contact form (`add-contact-dialog.tsx`) and the opportunity form (`add-opportunity-dialog.tsx`)**. It composes the `company-combobox` search-picker with a **"New company" button** that opens the small `CreateCompanyInlineDialog`. Creation is **persist-first**: the inline dialog runs `createCompany`, and only on success reports `{ id, name }` back so the field auto-selects the freshly-persisted company — no nested transaction and no refetch round-trip. It reports the chosen `{ id, name } | null` and is clearable, so it serves both the contact form's optional company and the opportunity form's required one (which passes an `error`). (Website is an optional field; the inline dialog has no partner subtitle.)
- **`company-combobox.tsx`** — a debounced, searchable company picker built on the vendored `combobox` (Base UI Combobox). Built-in filtering is disabled (`filter={null}`) — filtering is server-side: it runs `searchCompanies` via `useAction`, keyed off the input debounced through `useDebouncedValue` (`src/hooks/`, 250ms). It **only searches once the user has typed** (a blank query returns nothing and clears results), and is clearable (a contact's company is optional). The selected company is kept in the item list even when absent from current results, so its label/selected state render. Selecting reports `{ id, name }`. See [domains/crm.md](./domains/crm.md).

### `/companies/[id]` + `/contacts/[id]` — CRM detail pages

The app's **first drill-down detail views**. Both are Server Components that `await` a `get*Detail` read (server-only, not a `'use server'` action) and `notFound()` on a miss; each has a `generateMetadata` titling the tab (company name / contact name). Reads are open; the only mutations are the **Edit dialog** (which for a contact also owns the Active/Inactive **Status** switch), the **inline owner + location fields**, and (contact only) the **inline relationship-strength star rating** and the sidebar **Relationships** group's add/edit/remove (all `crm.edit`-gated — see [domains/crm.md](./domains/crm.md)).

**Shared two-column layout — `detail-parts.tsx`.** Both views are built from the same presentational skeleton, so the two pages are deliberately visually consistent (previously they diverged — company used an inline header + tabs, contact a "Details" card + tabs, with mismatched widths and owner placement). **It is no longer CRM-only** — the **project detail page** (`/projects/[id]`) consumes the same primitives, so changing one of these ripples across company, contact *and* project views.

- **`DetailLayout`** — the two-column frame: a fixed `md:w-80` meta **sidebar** (`<aside>`) beside the **main column**, centred at `mx-auto max-w-6xl`, collapsing to one stacked column (sidebar first) on narrow screens. A **`fullWidth`** prop swaps that centring cap for `w-full` so the main column takes the whole page; the sidebar keeps its fixed width either way. The **company** and **project** detail pages are both full width — the project's Gantt timeline needs the width, and the company's Contacts tab carries wide tables; the **contact** page stays centred.
- **`DetailIdentity`** — the top of the sidebar: icon/avatar on one row with an optional `action` slot (the Edit-dialog button) pushed to the right, then the name (+ any adornment) and optional subtitle beneath.
- **`SidebarSection`** — a hairline-`border-t`-divided `gap-4` group; used for the scalar fields and, separately, the owner beneath them. **It owns the sidebar's label styling** (small / uppercase / muted) **and its row density** (`COMPACT_META_FIELDS`, below) via `[&_[data-slot=…]]:…` descendant selectors rather than each field applying them: both `MetaField` and `FormField` (through `InlineEditField`) emit labels in these sidebars, so per-field styling would mean threading a prop through both, and a `variant` on `FormField` would push a sidebar-only concern onto the app's most-used form primitive. That mixed-label design is **load-bearing, not hypothetical**: the contact sidebar's first section stacks four `MetaField`s and the `InlineLocationField` editor in one block (below), and they line up because the section, not the field, styles the label. It targets `[data-slot=label]` (**not** `label`) so a checkbox/switch label inside some future edit control can't get swept up. *(`inline-relationship-strength-field.tsx` used to hand-roll its own `Label` + stack; it now renders `FormField` so it can't drift out of the rail's rhythm.)*
- **`MetaField`** — a stacked `Label` + value pair (em dash when empty). Geometry (`gap-1.5`, a `min-h-8 py-1` value box) deliberately **matches `FormField`/`InlineEditField`**, so read-only rows and inline-editable rows in the same sidebar share one vertical rhythm — and it carries the same `data-slot="form-field"` / `data-slot="field-value"` markers, so `COMPACT_META_FIELDS` tightens both kinds of row at once. It renders a `Label` even though it labels no control — that's what carries the `data-slot="label"` styling above; a `<span>` would be better a11y but would fork the sidebar back into two label-styling paths.
- **`SidebarGroup`** — the narrow rail's counterpart to `DetailSection`: a `Label` heading (styled by `SidebarSection`'s `[data-slot=label]` selector, which is why it emits a `Label`) with an optional right-aligned `action` slot, then stacked rows. Deliberately unlike `DetailSection`: **no count in the heading** (a rail group holds several heterogeneous collections, so one total means nothing), **no table** (`DetailTable`'s columns don't fit 320px), and no border of its own (`SidebarSection` owns that). Its first consumer is the contact page's Relationships group (below).
- **`DetailSection`** — a titled main-column section with an optional count in the heading and an optional **`action`** slot right-aligned on the heading row (e.g. the project Roles tab's "Add role" button), mirroring the staff profile's `TabSection`.
- **`DetailTable`** — the bordered `Table` wrapper for a detail section: a header row of the given column labels over the caller's `<TableRow>` body cells. The shared scaffold behind the company/contact detail tables (only the columns + row cells differ). It applies **`ROOMY_TABLE`** (see above), so **every** detail table — the company's Contacts / Opportunities / Projects / referred tables, the project detail page — gets the roomier padding, not just the contacts list. Sibling of `TableEmpty`.
- **`TableEmpty`** — the "No … yet" placeholder shown inside the same bordered container for an empty collection (headers are dropped when empty).

(The old `TabLabel` export and the bespoke `Tabs`-based *interface* are **gone** from `detail-parts.tsx` — the skeleton is tab-agnostic. The pages were later **re-tabbed** by rendering the vendored `tabs` primitive directly in each view.)

- **`company-detail-view.tsx`** — sidebar: building-icon identity (name + optional "Partner" badge + Edit button), then **three separate `SidebarSection`s** — a Website `MetaField` (`ExternalLink`), `InlineLocationField`, `InlineOwnerField`. **This page kept one section per field**; only the *contact* sidebar merged location into its contact-method block (next bullet), so `InlineLocationField` is placed differently on each page despite being one shared component. The page is **`fullWidth`** (it passes that flag to `DetailLayout`, dropping the default `mx-auto max-w-6xl`) so the wider Contacts tab fits and the tasks cell stays one line per task — same choice the project detail page already made. Main column is **three tabs** (`variant="line"`): **Notes** (default), **Contacts**, and **Opportunities & Projects**. The **Notes** tab holds the company's *own* `DetailSection title="Next steps"` (its `TaskList`, `variant="company"`) and `DetailSection title="Notes"` (its `EntryLog`, `variant="company"`) — these used to sit *below* the tabs behind a `<Separator />`; that block and the `Separator` import are gone, and the pair is now the landing tab. The **Contacts** tab is one always-present `DetailSection` — the company's people directory, each person linked to `/contacts/[id]`, columns **Name · Location · Next steps** — the job title sits as muted small text under the name (matching the contacts list; the Role column is gone), Location is the contact's free-text `"City, CC"` home base (`EmptyCell` when unset), and Next steps renders each contact's open tasks via the **editable** `ContactTasksCell`. The name cell also carries an **"Inactive" `secondary` Badge** (`INACTIVE_LABEL`) when `!isActive` — a company's inactive people deliberately **stay listed** here (a `succeeds` predecessor's employer *is* the old company, and that history is the point of the link), so they're **badged rather than hidden**, unlike the contacts list which hides them behind "Include inactive" — the same in-row task editor the contacts list uses, handed `contactId` / `openTasks` plus the `canEdit` and `currentStaff` props the view already receives. **Email/Phone columns were dropped** here in the re-tab. **Beneath that directory the same tab carries `RelatedContactsSection`** (`related-contacts-section.tsx`) — the [non-employee relationships](./domains/crm.md#relationships), columns **Name · Employer · Relationship** plus an actions column present only for `canEdit`; the **Employer** column links to that person's *own* company, which is what distinguishes it at a glance from the directory above. Its name cell carries the same **"Inactive" Badge** as the directory (`related-contacts-section.tsx`), for the same reason. Its "Add relationship" button sits in the `DetailSection` `action` slot, and each row carries pencil / trash `IconButton`s (trash → `ConfirmDialog`). The **Opportunities & Projects** tab stacks **Opportunities / Projects / Referred opportunities / Referred projects**, each rendered only when non-empty, with a combined "Nothing in the pipeline for this company yet." empty state when all four are empty. Opportunities have no detail page yet so they render as plain rows; **project names in both the Projects and Referred projects sections link to `/projects/[id]`** (`InternalLink`).
- **`contact-detail-view.tsx`** — sidebar, top to bottom: `Avatar`-initials identity (name + an **"Inactive" `secondary` Badge** (`INACTIVE_LABEL`) when `!isActive`, an optional role subtitle, and — on an inactive record *with* a successor — a "Moved to X at Y" line under it; plus the Edit button), **one** `SidebarSection` holding **Email · Phone · LinkedIn · Company · Location** (the first four read-only `MetaField`s — all optional, empty → em dash, company links out — then `InlineLocationField` as the inline editor at the bottom of the same block), the **Relationships** group (`ContactRelationshipsSection`), the **relationship-strength star rating** (`InlineRelationshipStrengthField`), then `InlineOwnerField`. *(The old read-only "Manager" `MetaField` is gone — see the Relationships group.)* **Location deliberately shares the contact-method section instead of getting one of its own:** it's another "where to find them" fact and reads as one block with Company directly above it. That mixing works with no styling fork because `SidebarSection` already owns the label styling for `MetaField` *and* `FormField`-via-`InlineEditField` (see `SidebarSection` above) — this is the live example of the case that docstring anticipates. (The **company** page still gives location its own section; only the contact sidebar merged them.) **There is no Status control in the sidebar** — Active/Inactive is edited in the Edit dialog (below); an earlier `inline-active-field.tsx` / `InlineActiveField` write-on-toggle switch lived here and was **deleted**. The "Moved to" line sits in the identity rather than four sections down because an inactive record is a dead end someone reached by accident (a stale link, an old note) and "where did they go" is the only question worth answering there; **the reverse case gets nothing extra** — if you're on the active record you're already in the right place. Note the badge and the "Moved to" line are **independent**: an inactive contact with no successor (deactivated by hand) is badged with no forwarding line, which is the common case for anything the seed didn't create as a succession predecessor.
- **Relationships group — `contact-relationships-section.tsx` + `contact-relationship-dialog.tsx`.** The single place every contact ↔ contact link is read, added and removed, built on `SidebarGroup` (not `DetailSection`/`DetailTable` — three columns of names don't fit the rail) plus local `RelationshipGroup`/`RelationshipRow`. Five captioned groups — *Reports to · Direct reports · Previously · Moved to · Also connected* — all phrased from the **viewed** contact's point of view, which is what makes a bare list of names unambiguous: **direction lives in the caption, never in the row**. Direct reports preview 5 then a `Collapsible` (a nested `overflow-y-auto` inside a page column reads as broken; note the `group` class on the trigger is load-bearing for the "Show all / Show fewer" label swap, which keys off `group-data-[panel-open]`). The two **reverse** groups are read-only — their authoritative row belongs to the other contact — and **Edit exists only for `related`**, the only kind with a description. The dialog is one component for all three kinds, ordered **contact first, then type** — you pick the person, then say how they relate. Three consequences of that order, all deliberate: the picker's label stays a neutral "Contact" (it can't name a role before the type is known); it searches **one neutral candidate set** (everyone but this contact, inactive contacts included — hence the placeholder "Search contacts, including inactive…" — always labelled with their employer) rather than three per-kind scopes; and the chosen contact is **kept** across a type change rather than cleared, since it was picked first. The narrower rules — a manager must be a colleague, a predecessor must be at a different company — are therefore enforced on submit by `assertValidContactRelationship`, not by hiding candidates. The `EnumSelect` "Type" sits beneath, with **unavailable kinds omitted, not disabled** (a muted hint says why), and its `succeeds` option is worded *"Same person at a previous company"* — the two rows are one human, and "record" is the part a reader has to decode. Picking a `succeeds` target shows a pre-submit warning (`successionSideEffectSentence` — "Adding this marks X as inactive.") because that's the one write with a side effect on another record. The remove-confirm for the same link says the record **stays** inactive, matching what `deleteContactRelationship` actually does. See [domains/crm.md](./domains/crm.md#contact--contact-relationships) and [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md).
- **`contact-detail-view.tsx` main column** — **three tabs**: **Activity** (default, `defaultValue="activity"` — a **Next steps** `TaskList` section and a **Notes** `EntryLog` section), **Companies** (`RelatedCompaniesSection` — the [companies they're linked to without working there](./domains/crm.md#relationships), columns **Company · Relationship** + a `canEdit`-only actions column, each company linked and badged "Partner" when `isPartner`; their *employer* stays a sidebar `MetaField` and never appears here), and **Opportunities** (an **Opportunities** section split into two labelled subsections, "Referred by this contact" / "Also involved in", plus a **Projects** section listing projects *derived* from the contact's referred opportunities — contacts don't attach to projects directly). **Companies sits in the middle**, mirroring the company page's people-before-pipeline order. Opportunity/project rows link their company, and project rows also link the project name to `/projects/[id]` (`InternalLink`). **Naming divergence:** the two detail pages give the *same* Next-steps + Notes pairing different tab names — contact calls it **Activity** (`defaultValue="activity"`), company calls it **Notes** (`defaultValue="notes"`).
- Both share **`opportunity-status-badge.tsx`** — renders a leaf status as its pipeline **group** label (`groupOfStatus(...).label`), `default` variant for `closed_won`, `secondary` otherwise. Tables reuse `EmptyCell` / `ExternalLink` / `InternalLink`.

### `/opportunities` — Opportunities kanban board (CRM)

`(app)/opportunities/page.tsx` (Server Component) `await`s `getOpportunitiesBoard()` (non-paginated — the pipeline is small) `Promise.all`'d with `getCurrentUser()`, computes `canEdit = userHasPermission(user, { crm: ["edit"] })`, and renders `OpportunityBoard` (was a paginated `opportunities-table.tsx`, now **removed**) plus a `canEdit`-gated "Add opportunity" dialog. **dnd-kit** (`@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` — new deps) powers the drag-and-drop.

- **`opportunity-board.tsx`** (`OpportunityBoard`) — the client board. **Cards are the canonical state; columns are derived** from `OPPORTUNITY_GROUPS` (`src/lib/crm/opportunity-pipeline.ts`) + which groups are locally expanded, so toggling collapse never re-keys stored state. Multi-substatus groups (Scoping/Allocating/Closing) render **collapsed by default** into one column (cards show a substatus `Badge`) with an expand toggle, or **expanded** into subcolumns; single-status groups are plain columns. Two **client-side filters** — a **name search box** and a **line-of-business `SelectFilter`** — narrow the cards client-side, but drag math uses the *full* (unfiltered) column neighbours, so reordering while filtering can't corrupt order against hidden cards. Both are loaded-only (they can't reveal cards past a capped column's cap); an active LOB filter is threaded into the capped column's "Show more" list-view deep-link. Drags are **optimistic**: `onDragEnd` computes an absolute `{ status, position }` (via `resolveTargetStatus` + `computePosition` over the destination column's neighbours), applies it locally, and runs `updateOpportunityPosition`; on error it reverts to a pre-drag snapshot (the failed write left the DB unchanged). A `useEffect` re-adopts fresh server data only when the payload *signature* changes, so a post-move revalidation doesn't clobber in-flight moves. Cards sort by `(position, createdAt)` — same tie-break as the server. When `!canEdit` the board renders **without** the `DndContext` (static). Dropping onto a collapsed group picks the group's first substatus (dragged from earlier) or last (from later).
- **`opportunity-board-column.tsx`** / **`opportunity-card.tsx`** — a droppable column (dnd-kit) with an optional expand/collapse toggle, and the draggable card (company name, source, owner names, optional substatus badge, and a **compact list of the opportunity's open tasks** when any exist; a `DragOverlay` clone renders while dragging). A **collapsed multi-status group** is wrapped in the same bordered `bg-muted/30` panel the expanded state uses, so it reads as a group that opens in place rather than a plain single-status column.
- **`opportunity-detail-sheet.tsx`** (`OpportunityDetailSheet`) — the card-click **detail drawer**: a **wide `sm:max-w-[80rem]`** right-side `Sheet` (widened for the planner + the two-column Details layout), lazy-loaded via `loadOpportunityDetail` and re-fetched after each save. Two `Tabs`: **Details** — a responsive two-column layout (`lg:grid-cols-[18rem_1fr]`, stacking below `lg`) that **merged the former Info and Notes tabs**. Its left meta column holds the Info fields (Line of business, Source + referral, Company, Contacts, Owners), each read-first with a per-field pencil, editing inline with Confirm/Cancel and saving *just that field* through the field-scoped `updateOpportunityField`; **company is an editable field here** (`CompanyField`, reusing `CompanyCombobox`) rather than a header label — the `SheetDescription` is now a visually-hidden generic a11y string; Source + its referral picker edit as one unit. The right column holds the Tasks (`TaskList`, owner-prefilled with the viewer's staff identity from `loadOpportunityDetail`'s `currentStaff`) + Notes (`EntryLog`) lists (see below). Name + Status live in the drawer **header** (Status mirrors the client delivery-stage guard). The second tab is **Project plan** (`opportunity-project-plan.tsx`, loaded via `loadOpportunityPlan` — a **weekly Gantt-like staffing planner**: **one row per role** (with sticky Role + Staff lead columns) × week grid, this opportunity's tentative roles editable — selectable for **bulk delete/duplicate/bump** and inline **staff assignment**, with a staffed person's other-project commitments greyed in — confirmed/other-opportunity roles greyed; empty state associates an existing project or creates one; write controls gated `projects.edit`. Grid math is the pure `src/lib/projects/project-planner-grid.ts`. See [domains/projects.md](./domains/projects.md)). A **left-edge control strip** (a popup-child, so it escapes the drawer bounds and stays put while content scrolls) holds Close plus, when the opened card has column siblings, **prev/next** (chevron-up/down) buttons — they step through the *visible* (search-filtered) cards of that kanban column, are disabled at the first/last card, and are hidden when the column has one card. The board (`opportunity-board.tsx`) computes the neighbours from its `visibleByColumnId` map and passes `onPrev`/`onNext` that just change `selectedId` (re-triggering the drawer's load). Only **mounts for `crm.edit`** users (gated on the board). Built on the shared `InlineEditField` primitive.
- **`entry-log.tsx`** (`EntryLog`, `src/components/crm/`) — the shared **notes** log (now notes-only) used on the company/contact detail pages and the opportunity drawer's Details tab. A `variant` (`contact` | `company` | `opportunity`) prop selects the matching add/update/delete action set (all parents' hooks are instantiated every render for stable hook order, then chosen by variant). Renders a `Textarea` composer (for `canEdit`, Enter = newline) plus a newest-first list, each note with author + `formatShortDate` timestamp, an "edited" marker, and inline edit/delete. (The old per-`kind` `Input`+Enter-submits sizing for next steps is gone.) An optional `onChanged` callback lets the client-fetched drawer re-load; server-rendered pages rely on the action's `revalidatePath` + `router.refresh()`. See [domains/crm.md](./domains/crm.md#notes).
- **`task-list.tsx`** (`TaskList`, `src/components/crm/`) — the shared **tasks** list (modelled on `EntryLog`) used on the company/contact detail pages and the opportunity drawer, backing the [Tasks](./domains/crm.md#tasks) entity that replaced next steps. A `variant` selects the create action's parent kind. Renders a composer — a description `Textarea` + an **owner staff-picker** (`EntityCombobox` + `searchStaff`, defaulting to the `currentStaff` prop) — plus a list where each task has a completion `Checkbox` (→ `setTaskDone`), struck-through done text, owner + created/completed `formatShortDate` dates, and inline edit/delete. The description + owner field pair itself lives in **`task-fields.tsx`** (`TaskFields`, extracted from `TaskList`) — Enter submits, Escape cancels (optional `onCancel`), and a **`stacked`** prop forces the two fields onto separate rows for narrow containers like a table cell, where the `sm:` breakpoint would read the viewport rather than the container.
- **`open-tasks-cell.tsx`** (`OpenTasksCell`) is the compact **read-only** tasks cell (a parent's incomplete tasks, one line each: truncated `text-xs` description + a `TaskOwnerAvatar` on the right) — **no page renders it directly**; its one caller is `ContactTasksCell`, as the non-editor fallback (the kanban card mirrors the same shape inline). Its layout deliberately **mirrors the editable cell row-for-row** so the read-only and editable "Next steps" columns read identically.
- **`task-owner-avatar.tsx`** (`TaskOwnerAvatar`, `src/components/crm/`) — a shared client leaf: a task owner as a **size-5 initials disc** (`initialsFor`) named in a tooltip, with an **empty dashed disc for unassigned** so the column still lines up and the gap reads as "nobody owns this". **Gotcha:** it sizes off the *default* avatar plus a `size-5` class, **not** `size="sm"` — the variant's `data-[size=sm]:size-6` out-specifies a plain `size-5` override.
- **`contact-tasks-cell.tsx`** (`ContactTasksCell`, `src/components/crm/`) — the **Next steps cell, editable in place**, used by **both** contact tables (the contacts list and the company detail page's Contacts tab): complete / edit / delete / add a task straight from the row via the four `crm.edit`-gated task actions, without opening the contact. A client island inside the server-rendered `ContactsTable` / `CompanyDetailView`, given `canEdit` + the viewer's staff identity by `/contacts/page.tsx` and `/companies/[id]/page.tsx`; non-editors get `OpenTasksCell`. **Each task is one compact line** — `Checkbox` · truncated `text-xs` description · `TaskOwnerAvatar` — and **the description text is itself the trigger for an edit popover**, so the row never grows (that was the point). The local `TaskEditorPopover` wraps `TaskFields stacked` plus Cancel/Save, with **Delete living inside that popover** (its `secondary` slot) — there are no hover-revealed pencil/trash icon buttons. The always-visible **"Add"** affordance opens the same popover empty (a contact with no tasks would otherwise show an empty cell with no affordance). Note `PopoverTrigger`'s Base UI `render` prop takes an *element*, so `TaskEditorPopover` takes `trigger: ReactElement`. **Gotcha — each task row owns its own `useAction` hooks**: `useAction` keeps a single in-flight request and discards superseded results, so one cell-wide hook would swallow the first row's error (and clear its pending state) as soon as you touched a second row. Errors are toasts (no room for inline text in a cell). **Ticking a task doesn't remove it:** completed tasks keep rendering below the open ones, struck through and **not editable** (plain text, no popover trigger — the cell only holds the last copy it saw of a task the server no longer returns), so unticking is a one-click undo. The cell tracks this as a **`Map<id, { task, done }>` of overrides** — session-scoped, cleared by navigation/reload — rather than a plain completed list, because the server data carries only open tasks and lags a `router.refresh()`, so the gap needs covering in both directions. See [domains/crm.md](./domains/crm.md#tasks).
- **`inline-edit-field.tsx`** (`InlineEditField`, `src/components/form/`) — a **new shared primitive**: a single detail field that reads as plain text (value + pencil) until edited, then swaps in the control (`children`) with Confirm/Cancel. Built on `FormField`, reusing its `labelAction` slot for the affordances (so rows line up with other form primitives) and its `error` slot (surfaced only while that field is the one editing). `editing` is **caller-controlled**, so a field stays open on a validation error and closes only once its async save succeeds. ### SuggestInput vs EntityCombobox

Three superficially similar controls, picked by **what the stored value is**:

| Control | Value | Options come from | Can the user invent a value? |
|---|---|---|---|
| `EntityCombobox` | `{ id, name } \| null` | a server search action | **No** — only what the search returned |
| `EnumSelect` | one enum member | a static tuple + labels record | No — closed set |
| **`SuggestInput`** | a **plain `string`** | a static suggestion list | **Yes** — the typed text *is* the value |

**`SuggestInput`** (`src/components/form/suggest-input.tsx`) is the app's first freeform-with-suggestions field: the dropdown is a shortcut, not a constraint, so a novel entry persists verbatim. Built on the vendored `Combobox` primitives (no new dependency). Its first consumer is the CRM [relationship](./domains/crm.md#relationships) description ("CSM", "FDE", … or anything else).

**The typed text appears as its own option** — `Use “Fractional CTO”`, appended below the curated suggestions — whenever it isn't already one of them (compared case-insensitively, so typing `csm` offers only the canonical `CSM`, not both). That row *is* the discoverability affordance: an empty dropdown that merely *says* custom wording is allowed is easy to miss and leaves the user unsure the field will accept what they typed, whereas a clickable row makes it obvious. It always survives filtering, since an item trivially contains its own query, so the `ComboboxEmpty` state is now near-unreachable (kept only for the no-suggestions-and-no-input case). Pressing it also **normalises the field to the trimmed text**.

Three implementation notes worth keeping, all non-obvious:

- **`value` drives both `value` and `inputValue`.** Controlling `inputValue` is what makes freeform safe: Base UI's two "reset the input back to the selected item's label" effects are *both* guarded on the input being **un**controlled (`!hasInputValue` in its `AriaCombobox`), so controlling it disables them and a novel entry can't snap back on blur or Escape. Keeping the two props in lock-step also means picking a suggestion and typing it by hand converge on the same state.
- **Built-in filtering stays on** (no `filter={null}`, unlike `EntityCombobox`) — the items are a local list, so there's no server round-trip to debounce and nothing to defeat stale responses for.
- **Filtering is deliberately *not* active until the user types.** Base UI picks `createSingleSelectionCollatorFilter` and computes `shouldBypassFiltering` only while `!queryChangedAfterOpen`; because our `value` and query are the same string, that bypass fires on open and the **whole** suggestion list stays browsable even when the field already holds a value. Once a keystroke lands, `queryChangedAfterOpen` flips and normal `contains` filtering takes over. Don't "fix" the unfiltered-on-open list — it's the intended browse affordance.

Don't reach for `@base-ui/react/autocomplete` (present in `node_modules` but unvendored) — hand-writing a `src/components/ui/**` primitive is against the shadcn convention above.

## App shell & sidebar

`src/components/app-shell/`:

- `app-shell.tsx` — Client Component; wraps `SidebarProvider` and renders the sidebar plus the page content in a padded (`p-4 md:p-6`) `<div>`. **There is no global header bar** — the old `<header>` showing a `titleForPath(pathname)` page title was removed, so `AppShell` no longer reads `usePathname()`. Each page owns its own in-page `<h2>` title (and sets the browser-tab title via `export const metadata`). It sets `defaultOpen={false}` so the sidebar starts **collapsed as a floating icon island**. Takes **`isLocal`** and **`visibleNavHrefs`** props and passes them straight through to `AppSidebar`. (`TooltipProvider` is no longer here — it now lives in the root layout; see below.)
- `app-sidebar.tsx` — the sidebar itself; uses `<Sidebar variant="floating" collapsible="icon">` (floating icon rail), `size-5` icons. The open/close **toggle lives in its footer** — a `SidebarMenuButton` (Tabler `IconLayoutSidebar`) calling `useSidebar().toggleSidebar` (label toggles Expand/Collapse). It renders only the `NAV_ITEMS` whose href is in the **`visibleNavHrefs`** prop (the permission-aware nav filter — see *Add a nav item* → permission-gated). It also takes an **`isLocal`** prop that drives the **localhost-only Admin footer entry** (`IconTool` → `/admin`, rendered only when `isLocal`). The prop originates in the server `(app)/layout.tsx`, which computes `await isLocalhost()` (`src/lib/auth/admin.ts`) and threads it **server-layout → `AppShell` → `AppSidebar`** — the same loopback-host boundary that gates the `/admin` segment itself, so the nav affordance and the segment agree.
- `nav-user.tsx` — the user dropdown in the sidebar footer.
- `nav.ts` — the nav source of truth (no JSX, so it's importable anywhere). Exports `NAV_ITEMS`, the `NavItem`/`NavSubItem` types, and two active-path helpers (`isActivePath` prefix-match for parents, `isActiveSubPath` exact-match for sub-items — below).

Collapsed nav items get tooltips automatically via `SidebarMenuButton`'s `tooltip` prop (set to `item.title`).

**Add a nav item:** edit `NAV_ITEMS` in `src/components/app-shell/nav.ts` (`{ title, href, icon }` with a **Tabler** icon, typed as Tabler's `Icon`). It drives the sidebar entries; `isActivePath()` (also in `nav.ts`) highlights the active one. Nothing else to touch. (There's no longer a `titleForPath` helper — the page-title header was removed.)

**Submenus (`children`).** A `NavItem` may carry an optional **`children?: NavSubItem[]`** — a `{ title, href, permission? }` list with no icon of its own (children inherit the parent's icon context). Each child's `permission` gates it **independently** of the parent. The Performance entry is the first (and only) submenu: Compensation (`/performance/compensation`) + Levels (`/performance/levels`, gated on `ratings.view`) + Edit levels (`/performance/levels/edit`, gated on `ratings.edit`) + Compensation plans (`/performance/compensation-plans`, gated on the **composite** `COMPENSATION_PLAN_ACCESS` — a child's `permission` is a plain `PermissionCheck`, so a two-resource conjunction works here with no change to the nav machinery). Rendering (`NavMenuItem` in `app-sidebar.tsx`) depends on the count of *visible* children:

- **≤1 visible child → a plain link** (the original single-entry behavior). This is the graceful-degradation path: **finance** holds only `staff.viewCompensation`, so Levels and Edit levels are both hidden and it sees a lone Compensation child → a plain link to the parent href `/performance`, which **redirects** to `/performance/compensation`. (That redirect exists precisely because the parent href must work for every audience — see [ADR 0044](./decisions/0044-performance-dashboards-split-by-permission.md).)
- **≥2 visible children, sidebar collapsed (the default icon rail)** → a **flyout `DropdownMenu` anchored to the icon** (`side="right"`), because the indented sub-list is CSS-hidden in the collapsed rail. This is the state users see most, since the sidebar defaults to collapsed.
- **≥2 visible children, sidebar expanded** → an indented **`SidebarMenuSub`** beneath the parent link. The parent link still navigates to its own `href` (its section home); children render below.

Active state: the parent uses **`isActivePath`** (prefix match), the sub-items use **`isActiveSubPath`** (exact match) — so the "Levels" child (`/performance/levels`) does not read as active when you're on its sibling `/performance/levels/edit`, whose path it is a prefix of.

**Permission-gated nav items.** A `NavItem` (or a `NavSubItem`) may carry an optional **`permission?: PermissionCheck`**. The server `(app)/layout.tsx` evaluates each item against the current user via `userHasPermission` and **flat-maps** parents + their permission-visible child hrefs into **`visibleNavHrefs: string[]`** (the hrefs the user may see), threading it **server layout → `AppShell` → `AppSidebar`**. The sidebar renders only items/children whose href is in that set. **Only serializable hrefs cross the server→client boundary** — the icon components stay client-side, so we can't just filter the item objects on the server. This is a **generic, reusable gate** for any future protected page (the Performance parent uses `permission: { staff: ["viewCompensation"] }` — the section's *loosest* gate, sound only because every `ratings.view` role also holds it — with its Levels child on `{ ratings: ["view"] }` and Edit-levels child on `{ ratings: ["edit"] }`). It's an **affordance only** — hiding the link is not the security boundary; **every page still gates itself**: `/performance` redirects or `notFound()`s per capability, `/performance/compensation` `notFound()`s non-`viewCompensation` users, `/performance/levels` `notFound()`s non-`ratings.view` users, `/performance/levels/edit` re-checks `ratings.edit`, and each read re-checks with `requirePermission`. Mirrors the localhost-only Admin footer entry's server-threaded pattern.

## Icon-only buttons (tooltip convention)

Icon-only controls must use **`IconButton`** (`src/components/icon-button.tsx`): it requires a `label`, which renders a **tooltip** and sets `aria-label` — so every icon button is discoverable and accessible. Don't ship a bare icon-only button. (Use it for standalone icon-only controls.)

`TooltipProvider` lives in the **root layout** (`src/app/layout.tsx`), not `AppShell`, so tooltips work app-wide (auth screens included). `IconButton` must render inside it — the root provider covers everything.

The root layout's `<body>` carries **`suppressHydrationWarning`** — browser extensions (e.g. ColorZilla's `cz-shortcut-listen`, Grammarly) inject attributes onto `<body>` before hydration, and this silences the resulting attribute-only mismatch warning. It's scoped to `<body>`'s own attributes; children still hydrate normally. Don't remove it, and don't broaden it to other elements.

## Auth UI (Google-only)

- Sign in: `authClient.signIn.social({ provider: "google", callbackURL: "/" })` (`src/components/auth/google-sign-in-button.tsx`). On success the browser is redirected to Google, so the component only handles the error path.
- Sign out: `authClient.signOut()` then `router.replace("/login")` (`src/components/auth/sign-out-button.tsx`).
- Email/password is intentionally disabled server-side — see [decisions/0006](./decisions/0006-google-only-auth-and-layout-gating.md).

## Error / not-found / loading (Next 16 specifics)

This is a **modified Next.js build** — these conventions differ from public Next. Verify against `node_modules/next/dist/docs/` before changing them.

- `error.tsx` — **Client Component.** The retry prop is **`unstable_retry`** in this build, NOT `reset`. Call `unstable_retry()` to re-render the segment. There's a **root `error.tsx`** and an **`(app)/error.tsx`**: the latter is a segment boundary nested *inside* the authenticated layout, so an error in an authenticated page renders its fallback **with the AppShell (sidebar/nav) still intact** rather than blowing away the whole shell. Both use `unstable_retry`.
- `global-error.tsx` — replaces the root layout, so it renders its own `<html>`/`<body>` with inline styles (app CSS isn't available). Also takes `unstable_retry`. Keep it minimal and self-contained.
- `not-found.tsx` — Server Component; trigger with `notFound()` from `next/navigation`.
- `(app)/loading.tsx` — a Skeleton-based suspense fallback for the authenticated segment.
