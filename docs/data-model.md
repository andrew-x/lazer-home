# Data model — the spine

The five domains share one model. This is the most important doc for understanding the system: changes here ripple everywhere.

**Status: mostly proposed.** Entities and relationships below are the intended design. Realized so far: the **Person** anchor (auth `user`), the **Staff profiles** tables (`staff`, `staff_employment`, `staff_pto`), the **CRM** slice (`companies`, `contacts`, `opportunities` + four opportunity junction tables + the `contact_entries`/`company_entries`/`opportunity_entries` **notes** logs + the `tasks` entity), the **Projects** slice (`projects` — now carrying a billing model + budget, `project_delivery_managers`, `project_roles` — the first cut of Allocation), the **Timesheets** slice (`timesheets`, `time_entries` — weekly actuals), the first **Performance** slices (`feedback` — peer feedback; `staff_rating` — overall levels L0–L4; `compensation_plan`/`compensation_plan_item` — compensation change plans), and a generic **`responses`** survey store (two consumers: the staff-profile **Manual of Me** and **Ways of Working** surveys) — see "What's realized in code".

## What's realized in code

> **Migrations have been squashed more than once — treat the filenames as disposable.** The whole drizzle history most recently collapsed into a single fresh baseline **`drizzle/0000_lethal_rictor.sql`** (commit `ba60c36`, superseding the earlier `0000_light_shape.sql` baseline and the incrementals that had accumulated on it — the CRM entries tables, the Opportunity↔Project inversion, and `staff_rating`, all now folded into the baseline). The substance of every past migration lives in `0000` and the schema modules under `src/lib/db/`. **Sixteen incremental migrations** currently sit on top (in apply order): **`drizzle/0001_past_agent_zero.sql`** (adds `contacts.relationship_strength` — see [domains/crm.md](./domains/crm.md#relationship-strength)), then **`drizzle/0002_gray_corsair.sql`** (the LoB-to-role + derived-project-status change — adds `paused`/`cancelled` to `project_role_status`, adds `project_roles.line_of_business` (backfilled from the parent project), then drops `projects.status`/`projects.line_of_business` and the `project_status` type — [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md)), then **`drizzle/0003_gifted_kylun.sql`** (a single `RENAME COLUMN` on `project_roles`: the role's optional free-text label `name` → `description`, still nullable text, max 200 in the schema), then **`drizzle/0004_blue_terrax.sql`** (adds `company_entries` — the company-level notes log, mirroring `contact_entries`; see [domains/crm.md](./domains/crm.md#notes)), then **`drizzle/0005_secret_zarek.sql`** (adds a nullable **`location`** text column to `companies`, `contacts`, and `staff` — the free-text `"City, CC"` home-base label, see [Location](#location-free-text)), then **`drizzle/0006_empty_whirlwind.sql`** (adds a nullable **`allocation_notes`** text column to `staff` — the manager/admin-only staffing note edited inline in the allocations planner, see [ADR 0041](./decisions/0041-allocation-notes-on-staff.md) and [domains/allocations.md](./domains/allocations.md)), then **`drizzle/0007_high_mister_sinister.sql`** (adds a nullable **`subratings`** jsonb column to `staff_rating` — per-role performance subratings co-dated with the overall level, shape app-owned + zod-validated, see [ADR 0042](./decisions/0042-per-role-subratings-app-owned-jsonb.md) and [domains/performance.md](./domains/performance.md)), then **`drizzle/0008_eminent_mandroid.sql`** (the **Tasks** entity replacing CRM "next steps" — creates `tasks`, then deletes `next_step` rows and **drops the `kind` column + `crm_entry_kind` enum** from all three `*_entries` tables, leaving them notes-only; see [ADR 0046](./decisions/0046-compensation-change-plans-rating-writing-proposals.md) and [domains/performance.md](./domains/performance.md)), then the **plan-item status ladder** pair **`drizzle/0010_large_zaran.sql`** (creates the `compensation_plan_item_status` enum + `status` column, then a **hand-added** `UPDATE` collapsing the three workflow booleans onto the ladder — highest set flag wins, deliberately lossy for the non-monotone combinations the exclusive column exists to make unrepresentable) and **`drizzle/0011_black_captain_stacy.sql`** (drops `rating_done`/`meeting_done`/`is_complete`; **must run after 0010's backfill**), then **`drizzle/0012_icy_excalibur.sql`** (**non-employee company ↔ contact relationships** — creates `company_contact_relationships` with a named unique `(company_id, contact_id)` pair and a reverse-lookup index on `contact_id`; see [ADR 0048](./decisions/0048-company-contact-relationships-beyond-employment.md) and [domains/crm.md](./domains/crm.md#relationships)), then **`drizzle/0013_simple_leader.sql`** (**performance review notes** — the `performance_review_note_status` enum + `performance_review_note` table; see [ADR 0049](./decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)), and finally the **contact ↔ contact relationship** pair: **`drizzle/0014_nasty_krista_starr.sql`** (the `contact_relationship_kind` enum + `contact_relationships` — two CHECKs, **four named partial unique indexes**, two plain read-path indexes — plus `contacts.is_active`) and **`drizzle/0015_rainy_wrecking_crew.sql`** (**hand-added**: an `INSERT … SELECT` backfilling `contacts.manager_id` into `reports_to` rows, *then* `DROP COLUMN manager_id` — it must run in that order or the data is gone; see [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md)), and finally **`drizzle/0016_violet_whistler.sql`** (**project budgets & margin** — creates the `project_billing_type` enum and adds `projects.billing_type` / `budget_amount` / `budget_currency` behind the `projects_budget_shape` CHECK; **all three columns nullable, so no backfill was needed**, and there is deliberately **no rate-card table** — the one company-wide rate card lives in code, see [ADR 0053](./decisions/0053-project-budgets-and-margin.md) and [domains/projects.md](./domains/projects.md#budget--margin)). Below we cite the **schema file** for each slice rather than a migration.

- **Person** is realized by better-auth's **`user`** table (`src/lib/db/auth-schema.ts`) — the _login/identity_ anchor. (`user`/`session`/`account`/`verification` live in our schema and migrations, not better-auth's.) A logged-in user maps to its staff record via the nullable, unique **`staff.userId`** FK (`onDelete: set null`) — see [domains/staff-profiles.md](./domains/staff-profiles.md). The user's **`role`** (a `text()` column owned by better-auth's `auth-schema.ts`) drives RBAC; valid values and the role→permission matrix live in `src/lib/auth/permissions.ts`, validated app-side by `roleSchema` (a `pgEnum` would be clobbered by `auth:generate`). See [domains/permissions.md](./domains/permissions.md).
- **Staff profiles domain** (`src/lib/db/staff-schema.ts`, barrelled by `src/lib/db/schema.ts`):
  - **`staff`** — the durable person record (notNull/unique external `ripplingId`, name, non-unique email, optional `userId` link to auth `user`, an optional self-referential **`managerId`** → `staff.id` (`onDelete: set null`) — "reports to", populated **exclusively by the staff CSV import** (matched on the `Manager - Work email` column) with **no in-app editor**, so a re-import never fights a manual edit — see [ADR 0026](./decisions/0026-staff-manager-self-reference.md). It was modelled on `contacts.managerId`, but **that column is gone** (folded into the `contact_relationships` junction, [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md)), so **`staff.managerId` is now the schema's only self-referential FK** — and unlike the CRM side it still has **no cycle guard**, which is why every reader guards itself — most visibly the **org chart** at `/staff?view=org`, whose `buildOrgForest` normalises self-references, dangling ids and loops into badged roots and is the **only surface that shows those data problems** ([ADR 0054](./decisions/0054-staff-org-chart-dom-tree.md)). **Four readers, escalating:** the profile's read-only "Reports to" line **and the org chart** (display); the feedback **"Your reports"** tab, which reads it in the *inverse* direction to **scope** a reviewer's list to their direct reports inside an unchanged capability ([ADR 0047](./decisions/0047-feedback-reports-scoping-not-granting.md)); and — since 2026-07-29 — **`performance_review_note`, where it is an authorization *input*** deciding read *and* write access with no capability involved ([ADR 0049](./decisions/0049-review-notes-reporting-line-as-authorization-boundary.md)). So it is **no longer true that no permission check consults it** — exactly one does, in `src/actions/performance/reviewNoteAccess.ts`, which makes a bad CSV import a privacy risk rather than a cosmetic one. Also: profile links, `clientIntro` (+ `clientIntroUpdatedAt`), free-text `resume` (+ `resumeUpdatedAt`), an inline **`skills`** jsonb list, an optional free-text **`allocationNotes`** (a manager/admin-only staffing note edited inline in the allocations planner — nullable `text`, no `updatedAt` sibling, `drizzle/0006_empty_whirlwind.sql`; read- and write-gated on `staff.edit` — see [ADR 0041](./decisions/0041-allocation-notes-on-staff.md)), lifecycle dates, `isActive`). Both `*UpdatedAt` instants are stamped **explicitly by their update action** when the text changes, not via `$onUpdate` (which would fire on every row write, e.g. an import re-sync). `skills` is the schema's **first jsonb/array column** — `StaffSkill[]` (`{ name, level }[]`, NOT NULL default `[]`) picked from the hardcoded catalogue in `src/lib/staff/skills.ts`, deliberately **not** a normalized `skill` table; see [ADR 0018](./decisions/0018-skills-inline-jsonb-catalogue.md).
  - **`staff_employment`** — time-varying employment facts (line of business, role, employment type, billability, `utilizationTarget`, `billableType` (NOT NULL, default `HUB`), a boolean `isManagement`, and **compensation** — `base`/`hourlyRate`/`guaranteedBonus`/`discretionaryBonus` (`numeric(12,2)`, all **NOT NULL**) + `currency` (**NOT NULL**)), as **one effective-dated row per change**; current state = latest `effectiveFromDate`. FK → `staff.id` cascade. `isManagement` and `billableType` are **orthogonal to `role`** (someone can hold a working role *and* be management for it) and set in-app only. **Compensation lives here** rather than a separate table (comp changes coincide with employment changes) — it's **import-only** (no edit UI), **required** (the importer skips a row it can't supply comp for; **no carry-forward on the *import* path** — every imported row must carry full comp), and **view-gated** by `staff.viewCompensation` (own comp always visible). The no-carry-forward rule is specific to the import path; the **bulk-edit path** (a *non-comp* change spawning a new effective-dated row) *does* **carry comp forward** from the previous row, so advancing someone's role/LoB never clears their salary. See [ADR 0007](./decisions/0007-staff-employment-effective-dating.md), [ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md), and [domains/staff-profiles.md](./domains/staff-profiles.md).
  - **`staff_pto`** — leave spans (`startDate`/`endDate`, `type`, `isPending`, **notNull/unique `ripplingId`** = Rippling "Leave request ID"). FK → `staff.id` cascade. Discrete rows, **not** effective-dated; reduces a person's available capacity for allocations. Populated by a second local-only importer (`/admin/upload-pto`) — see [domains/staff-profiles.md](./domains/staff-profiles.md).
- **`responses`** — a **generic survey-answer store** (`src/lib/db/responses-schema.ts`, barrelled by `schema.ts`), keyed by **`(staffId, questionId)`** with a `unique` on the pair (→ upsert, one **current** answer per person per question — *not* history like `staff_employment`, and the opposite of the append-only `feedback` log). FK `staffId` → `staff.id` cascade. `questionId` is plain **`text`** validated in app code (**not a `pgEnum`**), so a new survey needs **no migration**. Three nullable payload shapes (`listResponse` jsonb `string[]`, `textResponse`, `jsonResponse`) — a question uses whichever fits, and `upsertResponse` writes the used column and **nulls the other** so a row never carries a stale value from the wrong shape. **Two consumers today**, both staff-profile surveys and both a code-only add (no migration — exactly what ADR 0028 anticipated): **Manual of Me** (`src/lib/staff/manual-of-me.ts`, 7 free-text ids → `textResponse` only) and **Ways of Working** (`src/lib/staff/ways-of-working.ts`, 30 `WOW_`-prefixed ids → `textResponse` for free-text/single-select, `listResponse` for multi-selects and the AI usage/savings matrix buckets). The write schema's `questionId` is now `z.union([manualOfMeQuestionId, waysOfWorkingQuestionId])`; each new survey adds its enum to that union. See [ADR 0028](./decisions/0028-generic-responses-table-app-validated-question-ids.md) and [domains/staff-profiles.md](./domains/staff-profiles.md).
- **`lineOfBusinessEnum`** (`line_of_business`: `CORPORATE`, `CORE`, `FINTECH`, `COMMERCE`, `DESIGN`) is a **shared/global enum**, not a staff-specific type. It's carried by **three entities: `staff_employment`, `opportunities`, and `project_roles`** (all NOT NULL) — the practice that a person works in / a deal belongs to / a staffing line bills under. It **moved back onto `project_roles`** and is **no longer on `projects`** (a project's LoBs are *derived* from its roles, so one project can span practices — [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md), reversing the project-level placement of [ADR 0025](./decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)). Its value tuple + labels live in a pure, client-importable module **`src/lib/crm/line-of-business.ts`** (`LINE_OF_BUSINESS`, `LINE_OF_BUSINESS_LABELS`), the single source the `pgEnum` in `staff-schema.ts` and the CRM/projects zod schemas + forms all import — the same single-source pattern opportunities uses for its `source`/`status` enums (see [ADR 0016](./decisions/0016-junction-table-and-shared-enum-conventions.md)).
- **Local-only CSV import tools** are the only things that write the staff domain so far: `/admin/upload-staff` (Rippling export → `staff` + effective-dated `staff_employment`) and `/admin/upload-pto` (Rippling leave export → `staff_pto`). See [domains/staff-profiles.md](./domains/staff-profiles.md).
- **CRM slice** (`companies` + `contacts` + `contact_relationships` + `company_contact_relationships` + `contact_entries` + `company_entries` in `src/lib/db/crm-schema.ts`; `opportunities` + its four junction tables + `opportunity_entries` + `source`/`status` pgEnums now in **`src/lib/db/opportunities-schema.ts`** — split out of `crm-schema.ts`, [ADR 0025](./decisions/0025-line-of-business-on-opportunity-and-project-not-role.md); the `tasks` entity in **`src/lib/db/tasks-schema.ts`**; all barrelled by `schema.ts`):
  - **`companies`** — organisations we deal with. `isPartner` is a **standalone boolean** flag (default false) marking partners — not a client/partner split; a company need be neither. `name` notNull, optional `websiteUrl`, and an optional **`ownerId`** — the accountable staff owner (FK → `staff`, `onDelete: set null`; a second CRM ↔ staff link, deliberately set-null not cascade). We chose *Company* over the narrower *Client* the spine originally named — see [ADR 0015](./decisions/0015-crm-company-over-client.md). A company's **status (Partner / Client / Prospect) is *derived*, not stored** — `isPartner` is the only stored relationship signal; Client (a confirmed project) and Prospect (an open opportunity) are computed from the pipeline ([ADR 0034](./decisions/0034-company-status-derived-tags.md), [domains/crm.md](./domains/crm.md#company-status-tags)).
  - **`contacts`** — people, optionally employed by a company (`companyId` FK → `companies`, `onDelete: set null`; null when unknown or once the company is removed). `firstName`/`lastName`/`email` notNull, **`email` unique**, optional `phone`, optional free-text `role`, optional `linkedinUrl`, an optional **`ownerId`** → `staff` (`onDelete: set null`), the accountable staff owner (like `companies.ownerId`), an optional **`relationshipStrength`** — a plain **`integer`** on a **1–5** scale (1 New/Unestablished … 5 Champion/Trusted Partner), **null = not yet rated** (level meanings in the pure, client-importable `src/lib/crm/relationship-strength.ts`, mirroring `feedback-rating.ts`; edited inline as a star rating) — and **`isActive`** (boolean, notNull, default true), mirroring `staff.isActive`: an **inactive** contact stays in the CRM for its history but drops out of the default `/contacts` list and every picker. **"Inactive", not "former"** — the flag covers both "they left that company" and "this record is no longer relevant or valid", and doesn't record which; the display words live in the pure `src/lib/crm/contact-status.ts` (see [domains/crm.md](./domains/crm.md#contact-status-active--inactive)). **There is no `managerId` column any more** — it was folded into `contact_relationships` below ([ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md), superseding [ADR 0022](./decisions/0022-contact-manager-self-reference.md)).
  - **`contact_relationships`** — **one typed junction for every person-to-person link**, replacing the old `contacts.managerId` self-FK. `kind` is the `contact_relationship_kind` pgEnum (tuple in the pure `src/lib/crm/contact-relationship.ts`): **`reports_to`** (directional, `contactId` reports to `relatedContactId`, both at the *same* company, ≤1 per contact — the reverse read is that person's direct reports), **`succeeds`** (directional, the same human as two rows: `contactId` = the NEW record at the new employer, `relatedContactId` = the OLD one; ≤1 each way, so the chain is a linked list, and creating one marks the predecessor `isActive = false`), and **`related`** (**symmetric**, with a required free-text `description`, stored once and read from either side). A **data-carrying junction** (it holds `description` + a full `updatedAt`) with both FKs `cascade`, id prefix `crel`. Its cardinality lives in **four named partial unique indexes**, not app checks — a table `unique()` can't carry a `WHERE`, and the `related` one is keyed on `(least(a,b), greatest(a,b))` so (A,B) and (B,A) are the same link; two CHECKs cover no-self-link and "`description` iff `related`". Cross-row rules a constraint can't express (same-company for `reports_to`, *different*-company for `succeeds` with NULL permissive, and cycle prevention via a bounded 32-hop walk) live in `src/actions/crm/contactRelationshipChecks.ts`. See [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md) and [domains/crm.md](./domains/crm.md#contact--contact-relationships).
  - **`opportunities`** — pipeline deals, each **required** to belong to a company (`companyId` FK → `companies`, **`onDelete: restrict`** — contrast the contacts' set-null; a company with live opportunities can't be deleted). `source` + `status` pgEnums (`status` is a **flat 14-value leaf enum in pipeline order**; the two-level kanban grouping is derived in code in `src/lib/crm/opportunity-pipeline.ts`, not in the DB), a **required `lineOfBusiness`** (the shared enum — which practice the deal belongs to; a project created from it defaults to the same, [ADR 0025](./decisions/0025-line-of-business-on-opportunity-and-project-not-role.md)), a nullable **`projectId`** (the CRM → delivery link — **many opps → one project**, FK → `projects`, `onDelete: restrict`; see the Projects slice below) and **`position`** (`doublePrecision`, a single global fractional index for manual kanban ordering — a drag writes the midpoint between neighbours, one-row update; index `opportunities_status_position_idx` on `(status, position)`). The old scalar `nextSteps` column is **gone** — replaced by the `opportunity_entries` log ([ADR 0030](./decisions/0030-crm-timestamped-entries-notes-next-steps.md)). See [ADR 0021](./decisions/0021-opportunity-pipeline-groups-and-fractional-ordering.md). Their related people (contacts, owners, referral sources) live in **four junction tables** — the repo's first many-to-many pattern (see [below](#junction-tables--the-first-many-to-many-pattern)). `owners` and `source_staff` link to **`staff`**, the first CRM ↔ staff FK.
  - **`contact_entries` / `company_entries` / `opportunity_entries`** — running logs of authored, timestamped free-text **notes** ("what happened") per parent, one **concrete table per parent** (a real FK, `onDelete: cascade` — no polymorphic FK); same shape (`body`, `authorStaffId` FK → `staff` set-null = attribution not ownership, timestamps, index on `(<parent>Id, createdAt)`). **Append logs** (like `feedback`, unlike the upserted `responses`), any `crm.edit` holder may edit any note. The old **next-step** kind and the shared `crm_entry_kind` pgEnum were **removed** when tasks landed — the logs are now notes-only ([ADR 0030](./decisions/0030-crm-timestamped-entries-notes-next-steps.md), [ADR 0043](./decisions/0043-tasks-entity-replaces-crm-next-steps.md)).
  - **`tasks`** — assignable, completable to-dos on a CRM entity, which **replaced the old free-text "next steps"** ([ADR 0043](./decisions/0043-tasks-entity-replaces-crm-next-steps.md)). One table with `description`, `ownerStaffId` (assignee) + `creatorStaffId` (both FK → `staff`, `onDelete: set null`), `done` + a nullable `completedAt`, timestamps, id prefix `task`. Parent is **exactly one** of `companyId`/`contactId`/`opportunityId` (all `onDelete: cascade`), enforced by a DB `CHECK (num_nonnulls(...) = 1)` — concrete FKs, no polymorphic parent; indexed per parent on `(parent, done)`. Any `crm.edit` holder may create/edit/complete/delete any task (no per-task ownership). A parent's open tasks ride into the contacts table / company-detail contacts / kanban card via a shared grouped read. See [domains/crm.md](./domains/crm.md#tasks).
  - Open reads + `crm.edit`-gated create **and edit** mutations (one capability gates all CRM writes — companies, contacts *and* opportunities) + `/companies`, `/contacts` and `/opportunities` pages exist (companies and contacts are on **separate pages** now). Opportunities now have a two-tab **detail drawer** (a **Details** tab whose meta-column fields edit **one at a time in place** via `updateOpportunityField` — company/status/line of business/owners/source/contacts/referral sources — with the Tasks + Notes lists in its right column; and a **Project plan** tab that is a **weekly Gantt-like planner** over the linked project's roles). The **Opportunity → Project handoff** links `opportunities.projectId` (**many opps → one project**) when a project is created from or associated to an opportunity, and a delivery-stage rule requires one before advancing ([ADR 0024](./decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md)). See [domains/crm.md](./domains/crm.md).
- **Projects slice** (`src/lib/db/projects-schema.ts`, barrelled by `schema.ts`; imports `opportunities` from `./opportunities-schema`):
  - **`projects`** — billable work that always belongs to a company (`companyId` FK → `companies`, **`onDelete: restrict`** — like opportunities, a company with live projects can't be deleted). `name` (notNull), `companyId`, **three budget columns**, timestamps. id prefix `proj`. The budget columns (`drizzle/0016_violet_whistler.sql`, [ADR 0053](./decisions/0053-project-budgets-and-margin.md)) are **`billingType`** (new `project_billing_type` pgEnum `FIXED_FEE`|`TIME_AND_MATERIALS`, values from the pure `src/lib/projects/project-billing.ts`), **`budgetAmount`** (`numeric(12,2)`) and **`budgetCurrency`** — **all nullable, and `billingType: null` is a real permanent state** ("No budget set", every pre-budget project; required in both create paths going forward). A **`check("projects_budget_shape")`** makes the shape a DB invariant — all three null, *or* `FIXED_FEE` with amount+currency, *or* `TIME_AND_MATERIALS` with **neither** (a T&M project has no total; its money is the rate card) — mirrored by the zod **discriminated union** in `projectBudget.schema.ts`, so a half-written budget is unrepresentable at both ends. It has **no stored `status` and no stored `lineOfBusiness`** — both were **dropped** and are now **derived from its roles** (`src/lib/projects/project-derived.ts`: `deriveProjectStatus` "least-committed wins" over role statuses; `deriveProjectLinesOfBusiness` = distinct role LoBs), so a project can span practices ([ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md); the `project_status` pgEnum and `project-status.ts` are gone). The CRM → delivery link lives on the opportunity: `opportunities.projectId` (nullable FK → `projects`, **`onDelete: restrict`**), **many opportunities → one project**. **Same-company is server-enforced** at the link entry points (`associateOpportunityProject` + the company-scoped `searchProjects`) **and at the one write that could break it afterwards** — `updateProjectField`'s `company` variant refuses to re-parent a project whose linked opportunity belongs to a different company (nothing else re-checks the invariant post-association). See [ADR 0019](./decisions/0019-project-opportunity-link.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md), [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md).
  - **`project_delivery_managers`** — junction (many staff per project) following the CRM junction convention exactly ([ADR 0016](./decisions/0016-junction-table-and-shared-enum-conventions.md)): surrogate `text` PK, `unique(projectId, staffId)`, index on `staffId`, both FKs cascade.
  - **There is no rate-card table.** A `TIME_AND_MATERIALS` project stores nothing about pricing: it bills hours at the company's **one standard rate card, which lives in code** (`BILL_RATES` in `src/lib/projects/bill-rates.ts` — policy, revised centrally, ⚠️ currently a placeholder). A per-project `project_role_rates` table **was built and then dropped before shipping** (its create-then-drop migration pair was collapsed into the single `drizzle/0016_violet_whistler.sql` on merging `main`, so no migration mentions it) — per-project copies invite two projects silently disagreeing about what an engineer-hour is worth, for no product benefit. Consequences worth knowing: no rate *history* either (revising the card re-prices every T&M plan retroactively), and "a role type with no bill rate" is **unrepresentable** because the map is total over `ProjectRoleType`. See [ADR 0053 §1–2](./decisions/0053-project-budgets-and-margin.md).
  - **`project_roles`** — a **staffing line** (NOT a pure junction — carries columns): `projectId` → projects (cascade), **`staffId` → staff (restrict, NULLABLE)**, `roleType` (NOT NULL, `projectRoleTypeEnum`), **`lineOfBusiness`** (NOT NULL, the shared enum — **moved back onto the role**, a project's LoBs derive from these; defaults from the opportunity in the planner — [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md)), optional `description` (free-text label, nullable, max 200), `startDate`/`endDate` (date, string mode), `hoursPerDay` (numeric(4,2), default 8), plus two provenance/planning columns: **`status`** (`projectRoleStatusEnum`, NOT NULL, DB default `tentative` — now **four states** `tentative`/`confirmed`/`paused`/`cancelled`; the last two are enum-only, no UI yet; tuple + labels + badge variants in the pure module `src/lib/projects/project-role-status.ts`) and **`opportunityId`** (nullable FK → `opportunities`, `onDelete: set null`, indexed — which deal created the role). Indexed on all three FKs; **no `unique` on the FK pair** (a person can hold multiple lines on one project). A **null `staffId` is a placeholder / open position** (identified by `roleType` + optional `description`); dates and hours are required on every role. `status`/`opportunityId` are **server-controlled provenance, never user input**; a role auto-confirms when its opportunity is won ([ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md)). **`roleType` (discipline — `ENGINEER`/`DESIGNER`/`ARCHITECT`/`QA`/`SPECIALIST`) is orthogonal to `lineOfBusiness`** (what kind of work vs. which practice bills it); its tuple + labels live in the pure module `src/lib/projects/project-role-type.ts`. This is the **first concrete cut of the proposed Allocation entity** — stored as simple mutable rows, *not* effective-dated history. See [domains/projects.md](./domains/projects.md), [domains/allocations.md](./domains/allocations.md), [ADR 0017](./decisions/0017-project-roles-as-first-allocation-cut.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md), and [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md).
  - **The Opportunity → Project link is populated on the opportunity side** (`opportunities.projectId`, **many opps → one project**). `createProject` sets the originating opportunity's `projectId` (and tags created roles with that opportunity + `tentative`); `associateOpportunityProject` links an opportunity to an **existing** project (same-company enforced). A `requiresProject(status)` rule still blocks advancing an opportunity into delivery stages (Allocating+) without one, and at most one project per opportunity (single-valued FK). See [ADR 0019](./decisions/0019-project-opportunity-link.md), [ADR 0024](./decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md).
  - **Margin is where the projects domain first touches compensation.** Revenue comes from `projects.budgetAmount` (fixed fee) or `BILL_RATES[roleType] × hours` (T&M, from the code-owned card); **cost** comes from each role's assignee's latest **`staff_employment`** comp restated hourly (`base ÷ HOURS_PER_YEAR`, bonuses excluded), or — for an *open* role — the company-wide average for the matching `staff_employment.role`. Hours are `countWorkingDays(start,end) × hoursPerDay`, **never** the planner grid's bucket percentages ([ADR 0040](./decisions/0040-allocations-planner-granularity.md): a grid column is a nominal *rate*, not a quantity). Because a role's cost **is a salary**, cost/margin are gated on the **new `projects.viewMargin`** capability while **revenue stays open**, and the masking happens **inside the reads** (`getProjectCostBasis` returns `null`, so nothing compensation-derived is ever sent to a client that merely hides it). Cross-currency figures convert via the live FX rates ([ADR 0029](./decisions/0029-external-fx-rates-and-currency-normalization.md)) — client-side, from native amounts, with the conversion stated **once per panel and naming the rates used** (`ProjectMargin.convertedFrom`), not flagged per figure. See [domains/projects.md](./domains/projects.md#budget--margin), [domains/permissions.md](./domains/permissions.md), and [ADR 0053](./decisions/0053-project-budgets-and-margin.md).
  - Open reads + `projects.edit`-gated writes + `/projects` list page + a **per-project detail page** (`/projects/[id]`, backed by the server-only `getProjectPlan`/`getProjectPto`; the latter masks each PTO record's leave *type*/pending state **and returns approved leave only** unless the viewer has `pto.review`, and the former withholds the whole cost basis without `projects.viewMargin`) exist. Projects are **create** (standalone `createProject`, or `createProjectFromOpportunity` — which inherits name + company and asks only for the budget, so it is **no longer one-click**) **+ price** (`updateProjectBudget`, a dedicated action so a rename never re-submits the price) **+ edit** (`updateProject` edits name + delivery managers; the field-scoped `updateProjectField` also edits the **company** — a project **can** be re-parented to another client, refused while a linked opportunity belongs to a different company, and revalidating both companies' pages; there is no status/LoB to edit since those derive), and **role CRUD from two editors**: the **opportunity planner** (`createProjectRole`/`updateProjectRole`/`deleteProjectRole`/`extendProjectRole` + `associateOpportunityProject` — scoped to this opportunity's *tentative* roles by `assertRoleEditable`) and the **project detail page** (`createProjectRoleOnProject`/`updateProjectRoleOnProject`/`deleteProjectRoleOnProject` — scoped to this *project's* roles, **any status incl. confirmed**, by `assertProjectRoleEditable`, reachable from **both** its Roles table and its Timeline Gantt; see [ADR 0045](./decisions/0045-project-page-as-delivery-side-role-editor.md)), plus a **detach/delete** flow (`removeProjectFromOpportunity` and `deleteOpportunity` share `detachProjectFromOpportunity` — a sole-owned project is deleted, else its roles are removed and it's unlinked). See [domains/projects.md](./domains/projects.md) and [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md).

The rating enum's values/labels live in the pure, client-importable **`src/lib/performance/feedback-rating.ts`** (same single-source pattern as `line-of-business.ts`). Privacy is enforced **by the read projections, not the table** — three tiers (give = open to active staff via the `authorizeFeedbackCreate` hook; recipient sees only giver name + `messageToRecipient`; `feedback.review` = manager/admin see all in full). Cross-currency comparison normalizes via live FX rates ([ADR 0029](./decisions/0029-external-fx-rates-and-currency-normalization.md)). See [domains/performance.md](./domains/performance.md).

Level values live in the pure module **`src/lib/staff/staff-rating.ts`** (mirrors `feedback-rating.ts`; [ADR 0016](./decisions/0016-junction-table-and-shared-enum-conventions.md)); the **per-role subrating rubric** lives in the pure module **`src/lib/performance/rating-rubric.ts`** (app-owned, no DB enum — shape validated at the zod/action layer, so adding a rubric is a code-only change, like `responses`; only `ENGINEER` populated so far; [ADR 0042](./decisions/0042-per-role-subratings-app-owned-jsonb.md)); the current-row ordering fragment is `latestRatingFirst`. Surfaced on its **own route — the Levels dashboard at `/dashboards/levels`** (its own filter bar, no currency toggle since the page shows no money; the read-only aggregates include an **anonymized per-role average-subrating-by-category breakdown**; the comp-**by-level** cut lives on the Compensation dashboard instead — [ADR 0044](./decisions/0044-performance-dashboards-split-by-permission.md) split both out of the merged `/performance` page, which the nav restructure later renamed), gated by the **`ratings.view`/`ratings.edit`** capability — **manager/admin only, NO self-view** (stricter than compensation; not finance). **It now has two writers** — the bulk `saveStaffEvaluation` grid and `commitCompensationPlan` (below), which share the hardening helpers in `rating-rubric.ts`. See [domains/performance.md](./domains/performance.md), [ADR 0032](./decisions/0032-staff-rating-levels-effective-dated-manager-only.md), and [ADR 0042](./decisions/0042-per-role-subratings-app-owned-jsonb.md).
  - **`compensation_plan` + `compensation_plan_item`** — the Performance domain's fourth slice (`drizzle/0009_jittery_wolfsbane.sql`): a **named, effective-dated *proposal*** covering a cohort of staff. **Neither table is effective-dated** — a plan is a *document*, not a fact about a person; the history it produces lands on `staff_rating`.
    - **`compensation_plan`** — `name`, `status` (new `compensation_plan_status` pgEnum `DRAFT`|`COMMITTED`, values from the pure `src/lib/performance/compensation-plan.ts`, [ADR 0016](./decisions/0016-junction-table-and-shared-enum-conventions.md)), `effectiveDate` (`date`, string mode — the date committed ratings are dated with), `createdByUserId`/`committedByUserId` (FK → `user`, `set null`), **`committedAt`** (null while draft; the **idempotency guard** — a second commit is rejected), timestamps.
    - **`compensation_plan_item`** — one row per staff member per plan: `planId` (FK → plan, **cascade**) + `staffId` (FK → `staff`, **cascade**), with `index(planId)` and **`uniqueIndex(planId, staffId)`** (makes a membership reconcile idempotent — `setCompensationPlanStaff` submits the whole desired set). The **proposed rating** mirrors `staff_rating` exactly — `level` (`integer`, nullable, same `0..4` CHECK) + `subratings` (jsonb) — so commit copies it straight across. The **proposal**: `plannedAmount` (`numeric(12,2)`) + `plannedCurrency`, **one figure per person**, mapped to `base` for `FULL_TIME` and `hourlyRate` for `HOURLY` (bonuses untouched). A **`status`** ladder (`compensation_plan_item_status` pgEnum `NOT_STARTED`→`RATING_DONE`→`MEETING_DONE`→`COMPLETE`) tracking how far the review conversation has got — this **replaced three independent booleans** (`ratingDone`/`meetingDone`/`isComplete`) that made nonsense states representable; `drizzle/0010` backfills highest-set-flag-wins and `0011` drops the columns, **deliberately lossily** ([ADR 0051](./decisions/0051-plan-editor-status-ladder-display-units-and-level-targets.md)). Plus `evaluationNotes`/`compensationNotes` and three **commit-time snapshot** columns — `snapshotAmount`/`snapshotCurrency`/**`snapshotEmploymentType`** (the last disambiguates an annual base from an hourly rate years later).
    - **Committing writes `staff_rating` rows and nothing else.** Compensation stays a proposal: **Rippling remains the sole writer of `staff_employment`** ([ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md) **stands**, not superseded). The snapshot exists so a committed plan shows a stable before/after and can flag rows whose change hasn't been applied upstream ("Applied" / "Not applied · $X"). Gated by the conjunction **`staff.viewCompensation` AND `ratings.edit`** (no matrix change) — and unlike the aggregate dashboard reads, **its rows are identity-bearing by design**. See [domains/performance.md](./domains/performance.md), [domains/permissions.md](./domains/permissions.md), and [ADR 0046](./decisions/0046-compensation-change-plans-rating-writing-proposals.md).

    - **This is the one table whose readers are decided by the *reporting line*, not a role capability.** `staff.managerId` is an authorization **input** for it: the subject's **current, active** manager (or an admin) may read/write everything including drafts, the **subject** sees `SHARED` notes only, and an **author** keeps access to what they wrote after they stop being that person's manager — a **team change, not a departure**: that path is keyed on `user.id` but still requires an *active* linked staff row, so a terminated author can't reach back in and delete the record of a review conversation. `authorUserId`'s `set null` **fails closed** (a lost author row narrows access, never widens it). Role capabilities are not consulted at all, and **the permission matrix is unchanged** — the decision lives in `src/actions/performance/reviewNoteAccess.ts`. Surfaced as a **Review notes tab** on the staff profile and in the compensation-plan profile drawer; sharing is **one-way** (no un-share — delete is the retraction path). See [domains/performance.md](./domains/performance.md), [domains/permissions.md](./domains/permissions.md), and [ADR 0049](./decisions/0049-review-notes-reporting-line-as-authorization-boundary.md).

See [domains/timesheets.md](./domains/timesheets.md) and [ADR 0027](./decisions/0027-timesheet-weekly-model-and-edit-window.md).

## Core entities

- **Person** — an employee/contractor. Anchors most of the system. Realized as **`staff`** (durable identity) + **`staff_employment`** (effective-dated role/billability facts); login identity is the auth `user`, linked via the optional `staff.userId` (1:1, null until first sign-in).
  - **Skill** — capability + proficiency. _(Realized, but **not** as the many:many table this originally proposed:_ an inline `jsonb` array on `staff` (`skills`), catalogue-driven from `src/lib/staff/skills.ts`. The staff directory now **filters people by skill (+ minimum level) client-side** over the once-fetched list — no indexed query. Cross-staff skill matching for *allocations* is still proposed and would need an indexed rework — see [ADR 0018](./decisions/0018-skills-inline-jsonb-catalogue.md).)
  - **Compensation** (base/hourly/bonuses + currency) is **realized** as effective-dated columns on `staff_employment` itself, not a separate table — import-only, required, view-gated. See [ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md). **Proposed** compensation is a strictly separate thing: it lives on `compensation_plan_item` and **never writes back** to `staff_employment` ([ADR 0046](./decisions/0046-compensation-change-plans-rating-writing-proposals.md)) — so no read of "current comp" can ever pick up a proposal. **External charge rates (what we bill a client) are now realized — but not as a table at all**: one company-wide hourly rate per discipline, in code (`BILL_RATES`), the same code-as-policy pattern as `compensation-targets.ts`. A per-project rate table was built and dropped before shipping ([ADR 0053](./decisions/0053-project-budgets-and-margin.md)). So there is **no rate history**: revising the card re-prices every T&M plan retroactively, and making rates invoice-accurate means dating the card — a deliberate reopening of that ADR, not a column.
- **Company** — an organisation we deal with (CRM); an `isPartner` flag marks partners (standalone, not a client/partner split), plus an optional staff **owner** (`ownerId`, set-null). _(Realized — `companies`; create/read/edit.)_ Chosen over the narrower *Client* the spine first named; see [ADR 0015](./decisions/0015-crm-company-over-client.md).
  - **Contact** (optional company per contact) — a person, optionally at a Company, with an optional staff **owner** (`ownerId`, set-null) and an **`isActive`** Active/Inactive flag. _(Realized — `contacts`; create/read/edit; `companyId` nullable, `onDelete: set null`.)_ **Person-to-person links live in `contact_relationships`**, one typed junction covering "reports to" (same-company), "succeeds" (the same human's earlier record at a previous employer) and free-text "related" — the old self-referential `managerId` is gone. See [ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md) (superseding [ADR 0022](./decisions/0022-contact-manager-self-reference.md)).
  - **Opportunity** — a pipeline deal that always belongs to a Company; when it reaches delivery stages, links to a Project. _(Realized — `opportunities` + junction tables; `companyId` required, `onDelete: restrict`. The Project link is now **`opportunities.projectId`** (nullable FK, `restrict`, at most one project per opportunity, but **many opps → one project**), populated by the handoff/planner flow — see [ADR 0019](./decisions/0019-project-opportunity-link.md), [ADR 0024](./decisions/0024-opportunity-project-handoff-and-placeholder-roles.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md).)_
- **Project** (a.k.a. engagement) — billable work for a Company. The hub linking CRM ↔ delivery, and a **shared delivery vehicle** several opportunities can feed roles into. _(Realized (first slice) — `projects`; name + required `companyId` (`onDelete: restrict`) + **a billing model & budget** (`billingType`/`budgetAmount`/`budgetCurrency`; T&M stores no rates — it bills at the code-owned card — [ADR 0053](./decisions/0053-project-budgets-and-margin.md)) + timestamps; the opportunity link lives on `opportunities.projectId` (**many opps → one project**), populated when a project is created from or associated to an opportunity; delivery managers via `project_delivery_managers`. **Status and line of business are derived from its roles, not stored** (`project-derived.ts`). `updateProject` edits name + delivery managers; the project detail page's inline fields (`updateProjectField`) also **re-parent the project to another company** (guarded so it can't strand a linked opportunity). Roles are edited from the opportunity planner **or** the project detail page; a sole-owned project is deleted via the detach/delete flow.)_ See [domains/projects.md](./domains/projects.md) and [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md).
- **Allocation** — a _time-ranged_ assignment of a Person to a Project (start/end, % or hours, project role). The heart of capacity planning. _(Partially realized — `project_roles` is the first cut: a staff member (or a **placeholder/open position** when `staffId` is null) of a given role type + **line of business** for a date range at N hours/day, carrying a **`status`** (`tentative` → `confirmed`, auto-confirmed on the opportunity's win = soft vs. hard; plus enum-only `paused`/`cancelled`) and an **`opportunityId`** provenance FK. Simple rows, not effective-dated history yet — see [ADR 0017](./decisions/0017-project-roles-as-first-allocation-cut.md), [ADR 0031](./decisions/0031-opportunity-project-planner-and-role-status.md), [ADR 0033](./decisions/0033-line-of-business-on-role-derived-project-status.md). A **company-wide allocations planner** (`/allocations`) now surfaces this data as a staff × time-bucket grid at a **selectable day/week/month granularity** — a **view over `project_roles` + `staff`/`staff_employment` + `staff_pto`, no new allocation table**, read-only except for two manager-gated writes — a per-row **Allocate** action assigning a person to an open role (`allocateStaffToRole`, `projects.edit`) and an inline notes column backed by the one added `staff.allocationNotes` column (`staff.edit`) — see [domains/allocations.md](./domains/allocations.md), [ADR 0038](./decisions/0038-allocations-planner-pto-disclosure.md), [ADR 0040](./decisions/0040-allocations-planner-granularity.md), and [ADR 0041](./decisions/0041-allocation-notes-on-staff.md).)_
- **TimeEntry** — hours a Person logged against a Project (or a non-billable bucket) on a date. Grouped into a **Timesheet** = one Person's week (`draft`→`submitted`). _(Realized — `time_entries` + `timesheets`; per-day rows, whole-week save, submit-locks. Approval + billing deferred — see [domains/timesheets.md](./domains/timesheets.md) and [ADR 0027](./decisions/0027-timesheet-weekly-model-and-edit-window.md).)_
- **Feedback** — point-in-time peer feedback from one Person about another (rating + context + keep/stop/start + optional recipient message). _(Realized — `feedback`; staff↔staff, tiered visibility — see [domains/performance.md](./domains/performance.md) and [ADR 0023](./decisions/0023-feedback-privacy-tiers.md).)_
- **Rating / Level** — a Person's overall performance level (L0–L4) at a point in time, plus optional per-role **subratings** (per-category L1–L4). _(Realized — `staff_rating`; effective-dated (level + subratings co-dated), nullable level, subratings as app-owned jsonb, manager/admin-only with no self-view — see [domains/performance.md](./domains/performance.md), [ADR 0032](./decisions/0032-staff-rating-levels-effective-dated-manager-only.md), and [ADR 0042](./decisions/0042-per-role-subratings-app-owned-jsonb.md).)_
- **CompensationPlan / CompensationPlanItem** — a named, effective-dated **proposal** covering a cohort: per person a proposed rating, a proposed comp figure, workflow state, and notes. _(Realized — `compensation_plan` + `compensation_plan_item`; **committing writes `staff_rating` only and never `staff_employment`**, freezing a comp snapshot so the plan can reconcile against Rippling. Gated by `staff.viewCompensation` **AND** `ratings.edit`; identity-bearing, unlike the aggregate dashboard reads. See [domains/performance.md](./domains/performance.md) and [ADR 0046](./decisions/0046-compensation-change-plans-rating-writing-proposals.md).)_
- **ReviewCycle / PerformanceReview / Goal** — periodic assessment of a Person, often informed by their project work and utilization. _(Proposed.)_

## Key derived concepts

- **Utilization** = billable hours ÷ available hours for a Person over a period. Drives capacity (for allocations) and feeds performance.
- **Forecast vs. actuals** — Allocations (`project_roles`) are the _plan_; TimeEntries (now realized) are the _actuals_. Both exist; **reconciling them is still unbuilt** and a central reporting need.
- **Margin** = revenue − cost over a project's roles. **Realized for the *plan*** ([ADR 0053](./decisions/0053-project-budgets-and-margin.md), math in the pure `src/lib/projects/project-margin.ts`): revenue from the fixed fee or the code-owned standard rate card, cost from `staff_employment` (assignee) or a per-discipline average (open role), hours from real Mon–Fri weekdays × `hoursPerDay`. Three limits worth knowing: it costs the **allocation, not the logged time** (so it is *not* forecast-vs-actual — see below); a **fixed fee has no per-role revenue**, so its margin exists only at project level; and PTO is deliberately **not** netted off hours (cost accrues on leave, so netting would move revenue without cost). **Per-*Person* margin doesn't exist yet.**

## Nuances to respect

- Everything time-bound (allocations, rates, reviews, **employment**) needs effective-dated handling — a person's role or rate changes over time. The realized pattern is **history-as-rows** (`staff_employment`): a new row per change, current state = latest `effectiveFromDate`. See [ADR 0007](./decisions/0007-staff-employment-effective-dating.md). **Two deliberate exceptions:** (1) **Skills** are stored inline and edited in place, with no per-skill history — see [ADR 0018](./decisions/0018-skills-inline-jsonb-catalogue.md); (2) the first Allocation cut (`project_roles`) also stores simple mutable rows rather than effective-dated history, so it can't reconstruct a past plan — a deliberate scope call for the first slice, see [ADR 0017](./decisions/0017-project-roles-as-first-allocation-cut.md).
- Rates and salaries are highly sensitive. **Compensation** is now realized (on `staff_employment`) and access-gated by `staff.viewCompensation` (own always visible) — see [ADR 0020](./decisions/0020-compensation-effective-dated-import-only.md), authorization in [architecture.md](./architecture.md), and the RBAC model in [domains/permissions.md](./domains/permissions.md).
  - **Compensation now leaks out of its own domain, so watch for derived exposure.** A project role's **cost** is its assignee's pay restated hourly, which is why it needs its own gate (`projects.viewMargin`) rather than riding on `projects.edit`, and why the numbers are withheld **in the read** ([ADR 0053](./decisions/0053-project-budgets-and-margin.md)). Any *new* number computed from `staff_employment` — cost, margin, utilization value, a per-project average — inherits that sensitivity even when it looks like an aggregate: on a one-role project the aggregate *is* the salary.
  - **Bill rates (what we charge) are now realized — in code, not in the database** (`BILL_RATES`, one company-wide card). They are **not** compensation and are deliberately ungated. They are also **not** history-as-rows, unlike everything else time-bound below — a revision applies retroactively to every T&M plan.
- **Dates and times are timezone-agnostic.** Calendar dates (effective-from, PTO spans, join/termination) are `date()` strings (`"YYYY-MM-DD"`, no zone); instants are plain `timestamp` _without_ time zone — treat all stored datetimes as wall-clock and convert zones only at the UI edge. See [`.claude/rules/database.md`](../.claude/rules/database.md).

### Location (free text)

**`companies`, `contacts`, and `staff` each carry a nullable `location`** — where the entity is based, stored as a **free-text `"City, CC"` label** (e.g. `"Toronto, CA"`), **not a FK or `pgEnum`** (migration `0005_secret_zarek.sql`). Valid values come from a **static world-cities dataset**, `src/lib/cities/world-cities.json` (a column-oriented parallel-array JSON carrying `lat`/`lng` per city; currently a small US/CA sample, swappable for the full set at the same path — the loader is size-agnostic), parsed once at module load by the pure module **`src/lib/cities/cities.ts`**. That module exports `searchCities(query)` (case-insensitive substring match, capped at `SEARCH_LIMIT`, `id === name === label`), `cityLabelsForCountries(codes)` (used by the seed), and **`citiesNear(label, radiusKm = NEARBY_RADIUS_KM)`** — the labels within a great-circle (haversine) radius of a given city, inclusive; it degrades to `[label]` for an unknown label (stale param / label absent from the dataset), so a "nearby" filter never matches nothing. The exported const **`NEARBY_RADIUS_KM = 100`** is the default radius — the rough "fly into one metro, meet people in the adjacent ones" ballpark (Ottawa/Gatineau, NYC/Newark). The index now carries `lat`/`lng`, plus a `byLabel` Map for O(1) origin lookup. It has **no `import "server-only"`** so the Bun seed can import it, but must **never** be imported by a client component (it would bundle the whole dataset). The label string itself is what's stored — there's no city id. **Editing UI exists on contacts and companies only** (inline picker, [domains/crm.md](./domains/crm.md#location)); **staff displays `location` read-only on the profile sidebar but has no editor** (column + seed only). **Display surfaces:** the staff profile sidebar ("Location" meta row), the contacts list table, and the companies list table each show `location`. **Location is now a filter on all three list pages** ([Location filters](#location-filters) below); it is still not part of the company name-search or status filter. Seeded values are drawn from `cityLabelsForCountries(["US","CA"])` so they match what the picker offers.

#### Location filters

All three list surfaces — **companies**, **contacts**, and the **staff directory** — carry a **location filter**: a city picker (reusing `searchCities`) plus a **"Search nearby"** switch that widens the match to every city within `NEARBY_RADIUS_KM` of the picked one (via `citiesNear`). The shared control is `src/components/form/location-filter-control.tsx` (presentational, state-agnostic — the caller owns `city`/`nearby`). **Two filtering models coexist, matching each surface's existing pattern:**

- **Companies & contacts filter server-side** (URL-param → server `WHERE`). The pages parse `city`/`nearby` search params; the reads (`getCompaniesPage`, `getContactsPage`) push `inArray(location, nearby ? citiesNear(city) : [city])` into their `where` (AND-combined with companies' existing name/status filters), calling `citiesNear` directly on the server. This gave **contacts its first-ever filter** (a new `ContactListFilters` + `contactsWhere`). See [domains/crm.md](./domains/crm.md#location).
- **The staff directory filters client-side in-memory** (its established pattern — the whole roster is fetched once, all filters run in JS, no URL params). Because the world-cities dataset must never bundle to the browser, "search nearby" is resolved through the **`nearbyCityLabels`** action (`src/actions/cities/nearbyCityLabels.ts`, auth-only, no capability gate — static public data, same justification as `searchCities`), which wraps `citiesNear` server-side; while that resolves, the directory falls back to exact-city match. This action exists **only** as that bridge — companies/contacts don't need it (their reads are already server-side). See the *Directory* flow in [domains/staff-profiles.md](./domains/staff-profiles.md).

### Junction tables — the first many-to-many pattern

The four `opportunity_*` join tables (`src/lib/db/opportunities-schema.ts`) are the repo's **first** many-to-many relations and set the convention future join tables should copy (`project_delivery_managers` follows it exactly; `project_roles`, `company_contact_relationships` and `contact_relationships` are all **data-carrying** lines rather than pure junctions — see [domains/projects.md](./domains/projects.md), [domains/crm.md](./domains/crm.md#relationships) and [domains/crm.md](./domains/crm.md#contact--contact-relationships)):

- **Surrogate `text` PK** via `generateId(prefix)` (e.g. `opp-contact`), not a composite PK — consistent with the app-minted-CUID2 ID convention everywhere else ([`.claude/rules/database.md`](../.claude/rules/database.md)).
- **`unique(...)` on the FK pair** — gives set-semantics (a row can't be linked twice). Writers still dedupe input id arrays before insert so a repeat can't trip this index (see `createOpportunity`). **`contact_relationships` is the one deliberate divergence:** its uniqueness is per-`kind` and, for the symmetric kind, per *unordered* pair, which a table-level `unique()` cannot express — so it uses **four named partial `uniqueIndex`es** instead, and no pair-unique at all ([ADR 0052](./decisions/0052-contact-relationships-one-typed-junction.md)). Name any such index explicitly: Postgres reports the index name in a 23505, which is what lets each rule carry its own message.
- **`index(...)` on the *non-owning* FK** (e.g. the `contactId`/`staffId` side) for efficient reverse lookups ("which opportunities is this contact on?").
- **Both FKs `onDelete: "cascade"`** — a link row is meaningless without both endpoints.

Reading the "other side" cheaply: resolve the linked names with a **single grouped follow-up query** over the relevant ids, not a per-row query (see `getOpportunitiesBoard`'s owner-name resolution) — avoid N+1.

**Data-carrying junctions diverge on two points.** `project_roles` and `company_contact_relationships` both keep the FK/index halves above but add payload columns, and they part ways on the rest depending on whether *multiple rows per pair* is legitimate:

- **`project_roles`** drops the `unique(...)` — several roles for the same (project, person) are valid — and keeps `createdAt` only.
- **`company_contact_relationships`** keeps a **named** `unique(companyId, contactId)` (one relationship per pair, so editing its `description` is unambiguous, and the name lets `isUniqueViolation` map a duplicate to a friendly message) and adds a full **`updatedAt`**, because the row is editable — unlike the pure junctions, which are only ever inserted and deleted. Name the constraint whenever an action needs to translate its violation.

**A company and a contact are linked two different ways, on purpose.** `contacts.companyId` is the single optional **employer** (`set null` — an optional attribute of the contact). `company_contact_relationships` carries every **non-employment** link (both FKs `cascade` — the row's whole identity *is* the pair). Neither subsumes the other, and the write action forbids a relationship that merely restates the employer link. See [domains/crm.md](./domains/crm.md#relationships).
