# Architecture

**Status: actively built out on the scaffolded stack.** The core technical stack and architectural patterns are committed and in code. What exists is the foundation (env, db, auth, action layer), the **authenticated UI shell + auth screens** (see [ui.md](./ui.md)), the **staff schema + post-login staff-record gate** (the first real data-model slice; the earlier `StaffProfileForm`/`updateStaffProfile` demo has been deleted), and a growing **CRM slice** (`companies`/`contacts`/`opportunities` data, reads, create actions, and `/companies` + `/opportunities` pages — see [domains/crm.md](./domains/crm.md)). The first real data-backed authenticated pages are **`/profile`** ("My profile") and the **browse-staff** feature — a directory (`/staff`) and per-person profiles (`/staff/[id]`) that show *other* people via the same shared `ProfileView` (see [ui.md](./ui.md)) — the first place all three call-site patterns from ADR 0010 appear together (server-only read, next-safe-action mutation, presentational client UI). Browse-staff is also the first **cross-person** data access: its reads aren't ownership-scoped, and its link/intro/resume edits are now gated by RBAC (own → always; other → the `staff.edit` permission) — see Authorization, [domains/permissions.md](./domains/permissions.md), and [ADR 0014](./decisions/0014-rbac-better-auth-access-control.md). The resume edit is a **two-step parse-then-store** flow (upload a PDF → server extracts text for review → user saves), which never persists the file — see [ADR 0013](./decisions/0013-resume-pdf-parse-not-store.md). The profile has since been **redesigned into a two-column, tabbed layout** (#33) with dedicated sections (skills, compensation, PTO, projects, history timeline, and the **Manual of Me**). That last slice rides a **generic `responses` survey store** (`responses-schema.ts`, `getManualOfMe`/`upsertResponse`, `src/lib/staff/manual-of-me.ts`) — a `(staffId, questionId)` upsert store whose question ids are app-validated (no migration per new survey); its first and only consumer is the seven free-text Manual-of-Me questions — see [ADR 0028](./decisions/0028-generic-responses-table-app-validated-question-ids.md) and [data-model.md](./data-model.md). The CRM slice adds the first **server-side-paginated** reads (`src/lib/core/pagination.ts`) and the first type-ahead search (`src/lib/core/search.ts`), plus the first flat (non-ownership) write gate: a single `crm.edit` capability gates all CRM writes (companies, contacts *and* opportunities), while reads stay open to any signed-in user. Opportunities also bring the repo's first **many-to-many junction tables** (see [data-model.md](./data-model.md#junction-tables--the-first-many-to-many-pattern)) and the first CRM ↔ staff link. A **Projects slice** (`projects`/`project_roles` data, a server-paginated read, a `projects.edit`-gated create, and the `/projects` page — see [domains/projects.md](./domains/projects.md)) follows next: it reuses the junction/shared-enum conventions, adds the first **data-carrying junction** (`project_roles`, the first cut of Allocation — [ADR 0017](./decisions/0017-project-roles-as-first-allocation-cut.md)), a second flat write capability (`projects.edit`), and shares its staff/company search query bodies with CRM via `src/actions/shared/entitySearch.ts`. The first **Performance** slice — **peer feedback** — has also shipped: a `feedback` table (`performance-schema.ts`), give/read actions, and a `/feedback` page, with **three privacy tiers enforced in the read projections** (giving is open to any active staff, recipients see a limited view, `feedback.review` sees everything) — see [domains/performance.md](./domains/performance.md), [data-model.md](./data-model.md), and [ADR 0023](./decisions/0023-feedback-privacy-tiers.md). That page has since gained a reviewer-only third tab, **"Your reports"**, which is the repo's first read **scoped by the `staff.managerId` reporting line** — on the *unchanged* `feedback.review` gate, so the relationship only narrows an already-permitted set and never grants access ([ADR 0047](./decisions/0047-feedback-reports-scoping-not-granting.md)). A **Timesheets slice** has also shipped: `timesheets`/`time_entries` (`timesheets-schema.ts`), the `/timesheets` weekly grid, and save/submit/reopen actions — the first **actuals** capture (per-day rows, whole-week transactional replace, submit-locks-the-week, a ±1-week owner edit window with the `timesheets.edit` capability bypassing it). No approval or billing yet — see [domains/timesheets.md](./domains/timesheets.md) and [ADR 0027](./decisions/0027-timesheet-weekly-model-and-edit-window.md). The Performance domain has grown a second slice — a **compensation & headcount analytics dashboard** (now `/reporting/compensation`): an anonymized aggregate read (`getCompensationSummaryData`) over the latest `staff_employment` comp per active person, with role breakdowns, line-of-business/employment-type/role filters, and a CAD/USD currency toggle. and a fixed fee now has a **comparator** (`BudgetTotals.hourlyValue` + delta/percent — the same roles priced hourly) rendered *outside* the `projects.viewMargin` branch, because it is revenue-side. **No capability, matrix or RBAC change.** **Most recently the app gained its first *secret-bearing* external integration — Slack channel links** (`drizzle/0026_wide_marten_broadcloak.sql`, [ADR 0067](./decisions/0067-slack-channel-links-bot-token-denormalized-pairs-and-record-scoped-gate.md), [domains/slack.md](./domains/slack.md)): a **private scoping channel** on an opportunity and a **public project channel** on a project, each a **denormalized column pair** (no `slack_channel_links` table — both relationships are 1:1, and a polymorphic table would need an untyped `recordId` with no FK, losing the cascade) with create / link / unlink and an inline "we found this one" suggestion. **Five things to hold onto.** (1) It authenticates as **one workspace bot token, not per-user OAuth**, and the consequence is the feature's defining limitation: `groups:read` only returns private channels the app was **added to**, so scoping-channel search and suggestions are structurally incomplete — the UI states this (`/invite` guidance) rather than working around it. (2) **The gate is `metadata.authorize`, not a static capability, and no capability was added**: `crm.edit` and `projects.edit` are **disjoint** in the matrix, so `authorizeSlackChannel` resolves the requirement from the channel `kind`, and `SLACK_CHANNEL_TARGETS` is the single entry the hook *and* every action body read table/columns/capability from — making "checked `crm.edit`, wrote a `projects` column" unrepresentable. `permissions.ts`, `permissions.test.ts` and [domains/permissions.md](./domains/permissions.md) are **untouched**. (3) There is **no naming-convention filter** on the picker: any channel the bot can see is linkable (channels predating the convention are exactly the ones people need to link), so a **private channel's name is disclosed** to `crm.edit`/`projects.edit` holders — accepted, bounded by the bot being blind to a private channel until someone `/invite`s it and by search requiring a non-blank query, and turned into an operational rule ("don't invite this app to sensitive private channels"). *(Corrected 2026-08-04: ADR 0067 §5 and domains/slack.md previously described a `disclosableSlackChannels`/`isConventionChannelName` filter that never existed in the code.)* (4) **Creating a channel is not transactional with the DB write and Slack has no `conversations.delete`**, so the step order in `createSlackChannel` is the design: everything reversible first (including invitee resolution, the flakiest step, moved *before* the irreversible call) → `conversations.create` → persist under an `isNull` guard → **on persist failure `conversations.archive` as the compensating action** (safe precisely because nobody has been invited yet) → invites last, best-effort. (5) It introduces the repo's **first Next cache tags**, and uses **`updateTag`, not `revalidateTag`** — in this build the single-arg form is deprecated and the two-arg form is stale-while-revalidate, which would keep serving a channel list without the just-created channel in it. `src/lib/slack/` is the `format/fx.ts` case under [ADR 0036](./decisions/0036-lib-organized-by-domain-subfolders.md) (the module spans CRM *and* projects, so neither domain folder owns it), and the whole thing **extends [ADR 0029](./decisions/0029-external-fx-rates-and-currency-normalization.md)**'s outbound-HTTP pattern — which had deliberately picked a keyless API — to the first authenticated one. **The commercial layer also got its portfolio view — the Finance report** at `/reporting/finance` ([ADR 0070](./decisions/0070-finance-report-fee-proration-and-server-side-aggregation.md), [domains/finance.md](./domains/finance.md)): revenue, margin, blended rates and pricing exposure over a date window, optionally narrowed to one line of business. **No table, no migration, no capability and no matrix change** — it is gated on the *existing* `projects.viewMargin` through a named constant (`FINANCE_REPORT_ACCESS`, the `PROFILE_COMPLETENESS_ACCESS` pattern), because the roles that hold it already read a project's cost and margin on its own page and this **re-aggregates the same compensation-derived disclosure** rather than exposing a new *kind* of fact. **Five things to hold onto.** (1) **Everything is plan, nothing is invoiced.** `time_entries.projectId` points at a **project**, never a `project_role`, so no hour is ever attached to the rate it would bill at and **nothing in this app can price logged time** — hence there is deliberately **no `Planned | Logged` toggle** (the utilization report has one because hours need no rate), an `InlineNotice` says so in words, and closing the gap needs a **`time_entries → project_role` link** first, not UI work. (2) **A fixed fee is prorated by billable hours** into the window, defined by the property that **contiguous windows partition the fee exactly** — which **refines ADR 0066** (a fee is now attributable to *time*, still **never** to a *role*, so §5's ban on apportioning stands and the per-discipline *blended* rate is `null` for fixed-fee-only hours). Straight-line-by-calendar-days was rejected (it recognizes revenue in months with almost no staffing) as was excluding fees (it understates the book without saying by how much). (3) ⚠️ **The share always divides by the whole plan, never the slice** — a real bug caught in testing: with the filtered roles as denominator every share came out 1, so filtering a multi-practice fixed-fee project to one line of business reported the **entire fee** against that practice and the five per-practice views each claimed all of it. Both time bases are sliced this way, which is also what makes an unfiltered project row agree **to the dollar** with that project's own budget panel. (4) **One margin engine, called twice** — clip each role's dates, scale the fee, call the existing `computeProjectMargin`, with **zero changes to `project-margin.ts`**: a report that computed its own revenue would eventually disagree with the projects it aggregates. It now quietly depends on two properties of that module (hours derived from `startDate`/`endDate`, and `budgetAmount` reported as-passed), and it makes `project-margin.ts` a **four-surface** shared module. (5) **All aggregation is server-side, both currencies precomputed** — a deliberate departure from the utilization report's in-browser filtering, because **a role's cost ÷ its hours *is* that person's hourly compensation**, so a filterable projection would put the whole portfolio's pay rates in the page HTML; this follows `getProjectsList`'s `listMargin` posture instead, with **both** filters in `searchParams` (the window bounds which projects are read; the practice decides which roles count and therefore how a fee prorates) and currency as client state over two finished aggregates. Partiality is **stated** rather than inferred (`unknownCostRoleCount`, `projectsWithoutBillingType` in `ReportSection` captions — a partial total must not read as a small one), and the report deliberately counts **everything but `cancelled`**, so tentative roles carry revenue where the utilization report drops them — the two pages can legitimately disagree about the same window. One refactor rode along: **`lib/utilization/utilization-range.ts` was promoted to `lib/reporting/report-range.ts`** (`parseUtilizationRange` → `parseReportRange`, gaining a **`maxDays`** parameter; `UtilizationRange` is now an alias of `ReportRange`) so both reports round "this quarter" identically while capping the span from what each read actually costs — 366 days for utilization's per-person day scan, 1096 for finance's bounded row query. Newest slice: **Google Drive folder links + Files tabs** (`drizzle/0029_tense_jocasta.sql`, [ADR 0071](./decisions/0071-google-drive-folder-links-per-user-oauth-and-the-privacy-invariant.md), [domains/drive.md](./domains/drive.md), runbook [guides/google-drive.md](./guides/google-drive.md)): a **sales folder** on an opportunity (`Lazer Home/Sales/<name>`) and a **project folder** on a project (`Lazer Home/Projects/<name>`), the same denormalized-column-pair + record-scoped-`authorize` shape as Slack, plus a **Files** tab on each surface that browses the folder and adds files to it. **Five things to hold onto.** (1) **The privacy invariant is the feature**, and it is structural, not policy: `driveList()` **hardcodes** `corpora=drive` + `driveId=GOOGLE_DRIVE_ROOT_ID` so scope is *not a parameter any call site could widen*; the only path touching a file outside the shared drive is `copyDriveFile`, whose `fileId` comes from a **Google Picker click**; and it **copies, never moves** — nothing anywhere rewrites `parents`. (2) It is the repo's **first per-user OAuth integration** (Slack is one bot token): the Google login gained `scope: [DRIVE_SCOPE]` + `accessType: "offline"` + `prompt: "select_account consent"` and `account.encryptOAuthTokens`, every Drive call runs **as the signed-in person** (so Google enforces shared-drive membership and Drive's audit trail names the real human), and all token access goes through `auth.api.getAccessToken` — a Drizzle read of `account.accessToken` now returns **ciphertext**. **Existing users must sign out and back in once**; the scope grants nothing retroactively (`linkSocial` incremental consent is the non-destructive fix). (3) **No Drive read is cached, and that is a security decision** — the exact opposite of Slack's cache tags, because a per-user token in a shared cache entry is a cross-user disclosure. This feature adds **zero** cache tags. (4) Uploads use **the Google Picker, not our own uploader** — conceding a full-Drive token in the browser (`setOAuthToken` is the only way to authorize it) — as **two single-view Pickers** ("Upload" writes straight into the folder; "From my Drive" hands back ids we copy), because a combined Picker returns one undifferentiated PICKED list and inferring upload-vs-pick wrong silently duplicates files. (5) **No capability was added**: `authorizeDriveFolder` resolves `crm.edit` vs `projects.edit` from the folder kind exactly like Slack, and browse/copy/search/picker-token carry **no** capability deliberately (they run on the viewer's own token, so a gate would be theatre) — `getDrivePickerToken` takes `z.object({})`, and a `userId` parameter there would be a vulnerability. Still pending: a real per-person capacity **model** (both the meter's and the report's baseline is a flat 8h × Mon–Fri week for everyone — no `utilizationTarget`, part-time hours, joiners/leavers within a day, or holidays) plus capacity rollups/sorting and conflict *resolution*, timesheet approval/billing, **invoiced/actual revenue — which needs a `time_entries → project_role` link before any of it is buildable** — weighted pipeline forecasting (no `opportunities.value` column, no per-stage probability — the dashboard prices a deal from its project's plan or calls it unpriced), forecast-vs-actual as a **workflow** (the two reports measure the gap; nothing re-forecasts or writes back, and margin still costs the *plan*, not logged time), and the rest of performance (review cycles, goals, growth).

## Modified Next.js 16 — concrete deltas

This is a **modified** Next.js 16 build (see [decisions/0002](./decisions/0002-modified-nextjs.md)); your training data is likely wrong about it. Always confirm against `node_modules/next/dist/docs/` (the version-16 upgrade guide is the fastest index). The deltas we've actually hit and verified this session — keep this list current as more surface:

- **`params` / `searchParams` are Promises.** Route Handlers and pages receive them as promises — `await` them (`const { slug } = await props.params`). Verified in `.../upgrading/version-16.md`.
- **`cookies()` and `headers()` from `next/headers` are async.** `await` them before use.
- **`error.tsx` retry prop is `unstable_retry`, not `reset`.** (Also applies to `global-error.tsx` — see [ui.md](./ui.md).)
- **`next/image`: `priority` is deprecated → use `preload`,** and `next.config` must declare a `qualities` array (default is now only `[75]`; a `quality` prop outside the array is coerced to the nearest listed value).
- **`redirect()` must be called OUTSIDE try/catch** — it works by throwing `NEXT_REDIRECT`, so a surrounding catch will swallow it.
- **Cache tags: `updateTag`, not `revalidateTag`, when you need read-your-own-writes.** In this build (16.2.10) the **single-argument `revalidateTag` is deprecated**, and the two-argument form is **stale-while-revalidate** — so after a write the next read can still serve the *old* payload. **`updateTag(tag)` is immediate-expiry** and **Server-Actions-only**. First real case: `createSlackChannel` must not serve a channel list missing the channel it just created ([ADR 0067](./decisions/0067-slack-channel-links-bot-token-denormalized-pairs-and-record-scoped-gate.md) §7).
- **An authenticated `fetch` DOES cache if you give it an explicit cache config.** Next normally applies `autoNoCache` to a request carrying an `Authorization` header — but `patch-fetch.js` only does so when there is **no** explicit config, so `next: { revalidate, tags }` wins. Verified against the bundled source, not assumed; it's what makes the cached Slack GETs (`conversations.list`, `users.lookupByEmail`) actually cache.

Two deliberate choices:

- **Outside the `(app)` route group, on purpose.** The `(app)` layout redirects users without an active staff record to `/profile-setup`; the staff-upload tool is exactly what *creates* those records (chicken-and-egg). So admin must NOT require auth/staff — it requires only that the request is local.
- **The security boundary is the host, not auth.** `src/lib/auth/admin.ts` exports `isLocalhost()` / `assertLocalhost()`, which check the request `host` header against loopback hosts (`localhost`, `127.0.0.1`, `::1`). `admin/layout.tsx` calls `isLocalhost()` and `notFound()`s the whole segment for non-local requests; **every admin action calls `assertLocalhost()` itself** (no middleware does it for them). The importers + bulk-editor use `publicActionClient` (local seeding must run before any staff/admin exists). The one exception is `commitUserChanges` (manage-users): it adds `secureActionClient` + `metadata({ role: "admin" })` because it mutates through the Better Auth admin API, whose endpoints require the *caller* to be an admin — so that tool also needs a signed-in admin (bootstrapping caveat in [permissions.md](./domains/permissions.md)). Enforced server-side only — never trusted from the client. Reachable by direct URL; there's no sidebar nav entry. See [ADR 0008](./decisions/0008-localhost-only-admin-area.md).

## Env

`src/env.ts` validates `process.env` once at import with zod. It is **server-only by convention** but deliberately omits `import "server-only"` — drizzle-kit and the better-auth CLI run in plain Node and import the module chain (db → env), so the marker would break them. Client code must read `NEXT_PUBLIC_*` directly. Optional vars use a preprocess that coerces **blank entries (`FOO=`) to `undefined`** rather than failing on a zero-length string. Required: `DATABASE_URL`, `BETTER_AUTH_SECRET`. Optional: `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` — both must be set for sign-in to work, since Google is now the only auth method — the Slack pair, **`SLACK_BOT_TOKEN`** + **`SLACK_TEAM_ID`**, and the Drive trio, **`GOOGLE_DRIVE_ROOT_ID`** + **`NEXT_PUBLIC_GOOGLE_PICKER_API_KEY`** + **`NEXT_PUBLIC_GOOGLE_PICKER_APP_ID`**. Real Google OAuth creds and a Neon-hosted Postgres `DATABASE_URL` are configured in `.env`; that DB is migrated and up to date.

**`SLACK_BOT_TOKEN` is the app's first *secret* beyond the DB URL / auth secret / Google pair**, and the only optional var that is **refined, not just typed**: it must start with `xoxb-`, so the classic "pasted a *user* token" mistake fails at import instead of surfacing much later as an opaque `missing_scope` on the first channel create. Setting it **turns the Slack channel integration on** (`isSlackConfigured()`); absent it, the channel controls hide themselves but an already-stored link still renders, because the deep link needs no bot. `SLACK_TEAM_ID` is an optional companion that scopes those deep links to one workspace. Required scopes and the Slack-app setup steps live in [domains/slack.md](./domains/slack.md).

**The three Drive vars are one flag, not three** — `isDriveConfigured()` requires **all of them**, because browsing needs only `GOOGLE_DRIVE_ROOT_ID` while the Picker needs its own two, and a half-configured install where files list yet nothing can be added is worse than a feature that's plainly off. `GOOGLE_DRIVE_ROOT_ID` is the **Lazer Home shared drive id**, and it is more than configuration: `driveList` hardcodes it as the boundary on everything the app can ever enumerate ([ADR 0071 §1](./decisions/0071-google-drive-folder-links-per-user-oauth-and-the-privacy-invariant.md)). The two **`NEXT_PUBLIC_*`** values are public by design (the Picker runs in the browser; the API key should be restricted to the Picker API in the Cloud console, and the app id is just the Cloud **project number**) — client code reads them from `process.env` directly, never from `env.ts`, and in practice they arrive via `getDrivePickerToken` so a half-configured install fails in one place with one message. **Point dev at a *separate* shared drive**; that's why there's no `test-` name prefix here, unlike Slack. Setup steps: [guides/google-drive.md](./guides/google-drive.md).

## Auth

better-auth with the **admin** plugin — wired with the RBAC access controller and roles from `src/lib/auth/permissions.ts` (`admin({ ac, roles, adminRoles: ["admin"], defaultRole: "user" })`; see [domains/permissions.md](./domains/permissions.md), [ADR 0014](./decisions/0014-rbac-better-auth-access-control.md)); **Google-only sign-in** — `emailAndPassword` is disabled and Google is the sole social provider (see [decisions/0006](./decisions/0006-google-only-auth-and-layout-gating.md)). Server instance (`src/lib/auth/auth.ts`) uses the Drizzle adapter over our singleton `db`; **the better-auth tables (`user`, `session`, `account`, `verification`) live in our own schema/migrations** (`auth-schema.ts`), regenerated via `bun run auth:generate`. **The Google provider now also requests Drive** ([ADR 0071](./decisions/0071-google-drive-folder-links-per-user-oauth-and-the-privacy-invariant.md)): `scope: [DRIVE_SCOPE]` + **`accessType: "offline"`** + **`prompt: "select_account consent"`**, with **`account: { encryptOAuthTokens: true }`**. Four consequences worth knowing before touching this block. (1) `accessType` and `prompt` are **load-bearing, not cosmetic** — Google issues a refresh token only on an explicit consent with offline access, so dropping either leaves a one-hour access token and no way to renew it. (2) **A Drizzle read of `account.accessToken` now returns ciphertext** (keyed on `BETTER_AUTH_SECRET`); go through **`auth.api.getAccessToken`**, which decrypts *and* refreshes — see `src/actions/drive/driveToken.ts`. (3) **No `auth:generate` was needed** — `account` already had `refreshToken`/`accessTokenExpiresAt`/`scope`, and note Better Auth stores `scope` **comma**-joined. (4) **The scope grants nothing retroactively:** every pre-existing session must sign out and back in once, or use the `linkSocial` incremental-consent reconnect affordance (`src/components/drive/drive-reconnect-button.tsx`), which adds Drive to the existing grant **without** ending the session. Two helpers gate the app:

- `getCurrentUser()` — reads the session, returns the user or `null`.
- `checkAuth(role)` — throws a `UserSafeActionError` if unauthenticated or under-privileged; **admins satisfy any role requirement** (admin override). Used by the secure action middleware.

`nextCookies()` must be the last plugin so Set-Cookie flushes from server actions. The whole auth API is mounted by one catch-all route (`src/app/api/auth/[...all]/route.ts`).

**Auth UI is built.** `/login` (in the `(auth)` group) shows a single "Continue with Google" button; the `(app)` route-group **layout** (`src/app/(app)/layout.tsx`, a Server Component) gates every authenticated page by calling `getCurrentUser()` and `redirect("/login")` when there's no session — **route protection is in the layout, not middleware** (consistent with the no-middleware posture). Sign-in via `authClient.signIn.social({ provider: "google" })`, sign-out via `authClient.signOut()`. See [ui.md](./ui.md) for the screens and [decisions/0006](./decisions/0006-google-only-auth-and-layout-gating.md) for the why. Layout gating guards navigation only — server actions still authorize independently (see Authorization below).

**Beyond a session, the app gates on a usable staff record.** After the session check, the `(app)` layout calls `getCurrentStaffAccess(user)` (`src/actions/staff/getCurrentStaffAccess.ts` — formerly `src/lib/staff.ts` `getCurrentStaff`, now in the actions layer per ADR 0010), which resolves the user to a `staff` row and returns a discriminated `StaffAccessStatus` (`ok` | `incomplete` | `not_setup`). Only `ok` (active staff record with ≥1 employment row) enters the app; the others redirect to the single `/profile-setup` block screen (`(onboarding)` route group, no group layout — the page self-gates). On first login it auto-links the email-synced staff row by writing `staff.userId` (guarded on `userId IS NULL`). See [flows.md](./flows.md) (auth flow), the [staff-profiles domain doc](./domains/staff-profiles.md), and [decisions/0006](./decisions/0006-google-only-auth-and-layout-gating.md).

## Data access — the actions layer is the only door to the DB

`db` is imported **only from `src/actions/**`**. Pages, layouts, and components — **including SSR Server Components** — never import `db` or query Drizzle directly; they call into the actions layer. This keeps every read and write in one place to authorize, project columns, and apply domain rules. See [ADR 0010](./decisions/0010-actions-layer-owns-db-access.md), `.claude/rules/server-actions.md`, `.claude/rules/database.md`.

- **Mutations** → next-safe-action actions (the action layer below / [ADR 0004](./decisions/0004-action-layer.md)).
- **Reads (incl. SSR)** → a plain **server-only** async function in the domain folder: `import "server-only"`, named `get<Thing>.ts` (e.g. `src/actions/staff/getStaffProfile.ts`, which `/staff/[id]` `await`s). **Not** a `'use server'` action — that would force the `{ data, serverError }` envelope and re-run session checks, awkward for SSR. It exports its return type. Personal reads resolve the user inside and filter by ownership (inherently scoped); **cross-person reads** (the staff directory and `/staff/[id]`) take an id and are **not** ownership-scoped — the `(app)` layout gate is their boundary, with capability checks layered where data is sensitive (e.g. `getStaffPto` requires `pto.review` for non-owners — see Authorization, [domains/permissions.md](./domains/permissions.md)).

**Legitimate `db` importers outside `actions/`:** framework wiring (the Better Auth Drizzle adapter in `src/lib/auth/auth.ts`) and pure compute helpers an action delegates to (`src/lib/*-import/plan.ts`, reached only through an action). The **synthetic-data seed** (`scripts/seed/**`, run via `bun run db:seed`) is a **deliberate exception**: as a one-off CLI it constructs and owns its own `postgres` client (`scripts/seed/client.ts`) so it can close the connection and exit, rather than reusing the app's long-lived singleton — see [development.md](./development.md#seeding-synthetic-data). (The former `getCurrentStaff`/`src/lib/staff.ts` straggler is **resolved** — it now lives in the actions layer as `getCurrentStaffAccess`.)

## Authorization — RBAC declared in action metadata

Most data is sensitive (rates, salaries, reviews), so authz is first-class. There's
a full **role-based access-control model** ([ADR 0014](./decisions/0014-rbac-better-auth-access-control.md),
[domains/permissions.md](./domains/permissions.md)) on Better Auth's native access
control, with `src/lib/auth/permissions.ts` as the single source of truth (the statement,
the roles, the role→permission matrix, and the `userHasPermission` / `requirePermission`
helpers). Authorization is **declared in action metadata, never hand-written in
action bodies**. There is **one** `secureActionClient`; its middleware runs all three
declarative forms, in order, *before* the body (see `.claude/rules/server-actions.md`
and `.claude/rules/permissions.md`):

1. **Coarse role** — `metadata.role` → `checkAuth(role)` (admin-override).
2. **Static capability** — `metadata.permission` (a `PermissionCheck`) →
   `requirePermission`. Use for capabilities that don't depend on the input.
3. **Input-dependent / ownership** — `metadata.authorize`, an **`ActionAuthorize`**
   hook (`{ user, clientInput } => void | Promise<void>`) that reads the raw
   `clientInput` (the target id, cross-field rules) and throws `UserSafeActionError`
   to deny. This is a **generic, reusable mechanism**, not staff-specific — any
   domain supplies its own hook. Mandatory wherever a target id could be acted on
   across users; a route-level gate alone is not enough.

`metadata.authorize` replaced the earlier "compose a bespoke client" approach — the
hook lives on the single `secureActionClient`, so there's no per-feature client to
build. (Reads are plain server-only functions, not actions — they call the helpers
inline, e.g. `getStaffPto` requiring `pto.review` for non-owners, or
`getProjectCostBasis` returning `null` for a viewer without `projects.viewMargin`
**before it queries `staff_employment` at all**. When a read ships to a client
component, the gate has to live in the read — hiding the value in the UI would still
put it in the payload. See [ADR 0053](./decisions/0053-project-budgets-and-margin.md).)

Helpers **fail closed** (unknown/null role → least privilege). The matrix is the
contract — asserted by `src/lib/auth/permissions.test.ts` (runs in `bun run check`) and
audited by `/audit-rbac`. **Never weaken or bypass a permission check; flag any gap
as a vulnerability** (`.claude/rules/permissions.md`).

The earlier open-staff-edit gap is **now closed** ([ADR 0014](./decisions/0014-rbac-better-auth-access-control.md)):
staff link/intro edits declare `metadata({ authorize: authorizeStaffEdit })`
(`src/actions/staff/canEditStaff.ts`), which gates via `canEditStaff` (own → always;
other → `staff.edit`), and `getStaffPto` requires `pto.review` to read another
person's PTO.

## Running the DB

The DB is not auto-provisioned. Dev uses a **remote Postgres** (e.g. Neon) — there is no local DB. Set `DATABASE_URL` (get it from the team), then `bun run db:migrate` to apply migrations. Iterate with `db:generate` → `db:migrate` (or `db:push` for quick dev), browse with `db:studio`. See `.claude/rules/database.md`.
